# Redis用途及其关注场景

Redis 是一个高性能的内存数据库，以“快”著称。它的核心用途可以概括为：**缓存、高速存储、轻量级消息代理**。作为测试总工程师，你需要关注 Redis 在不同场景下的关键数据指标，以保障系统的性能、稳定性和数据一致性。

---

## 一、Redis 一般用来干什么？

### 1. 缓存（最核心）
- **场景**：数据库查询结果、页面片段、会话数据（Session）。
- **价值**：降低后端 DB 压力，将响应时间从毫秒级降至微秒级。

### 2. 分布式锁
- **场景**：防止重复下单、定时任务重复执行、库存扣减。
- **特性**：利用 `SETNX` + 过期时间实现，常见框架如 Redisson。

### 3. 计数器和限流
- **场景**：网站 PV/UV、点赞数、关注数、API 调用频率限制（滑动窗口）。
- **结构**：`INCR` + 过期时间，或使用 `Redis Cell` 模块。

### 4. 排行榜 / 有序集合
- **场景**：游戏积分榜、热门文章排名、社交关系链推荐。
- **结构**：`ZSET`（有序集合），按得分自动排序。

### 5. 消息队列 / 发布订阅
- **场景**：轻量级异步任务、实时通知、系统解耦。
- **结构**：`LPUSH/RPOP`（List 队列）、`PUB/SUB`、`Streams`（更可靠）。

### 6. 实时数据分析
- **场景**：实时统计（最近 1 小时活跃用户）、在线用户列表、地理围栏（GEO）。
- **结构**：`HyperLogLog`（去重计数）、`Bitmap`（日活）、`GEO`。

### 7. 临时数据存储
- **场景**：短信验证码、Token 黑名单、临时状态标识。
- **特性**：利用 `EXPIRE` 设置自动失效。

## 二、测试总工程师需要关注的 Redis 场景与数据

测试总工程师既要看功能正确性，更要看**性能、稳定性、一致性**。以下是典型的观测场景及对应的关键数据：

### 场景 1：缓存穿透/击穿/雪崩验证
- **观测数据**：
  - 缓存命中率（`info stats` → `keyspace_hits / (keyspace_hits + keyspace_misses)`）。
  - 热点 key 的 QPS（可通过 `MONITOR` 或 slowlog 抓取）。
  - 下游 DB 的瞬时请求量（对比 Redis 失效前后的 DB 负载）。
- **关注点**：是否因缓存缺失导致大量请求直接打到数据库。

### 场景 2：数据持久化可靠性
- **观测数据**：
  - RDB 快照时间（`last_save_time`）、AOF 重写状态（`aof_current_size`）。
  - 持久化错误数（`rdb_last_bgsave_status`、`aof_last_rewrite_status`）。
  - 内存与磁盘写入速率（`used_memory` vs `aof_base_size`）。
- **关注点**：宕机后能否恢复数据，恢复时间是否符合 RPO/RTO。

### 场景 3：内存淘汰与 OOM 风险
- **观测数据**：
  - `used_memory / maxmemory` 占比（超过 80% 需预警）。
  - 淘汰策略命中数（`evicted_keys`）。
  - 内存碎片率（`mem_fragmentation_ratio`，>1.5 需优化）。
- **关注点**：是否因内存写满导致数据被意外驱逐或写入失败。

### 场景 4：主从复制与读写分离一致性
- **观测数据**：
  - 复制延迟（`master_last_io_seconds_ago`，或计算主从 offset 差值）。
  - 从库状态（`slave_read_only`、`master_link_down_since_seconds`）。
  - 复制缓冲区大小（`repl_backlog_size`），是否出现全量重同步（`sync_full`）。
- **关注点**：从库读取到的数据是否过时，切换主从后数据是否丢失。

### 场景 5：慢查询与热点 key
- **观测数据**：
  - `slowlog` 中的命令、执行耗时、发生时间。
  - 大 key 扫描（`redis-cli --bigkeys`），如单个 hash 包含百万字段。
  - 热点 key 的访问频率（`redis-cli --hotkeys`，针对 LFU 策略）。
- **关注点**：是否存在 O(N) 命令（如 `KEYS *`、`SMEMBERS` 大集合）导致阻塞。

### 场景 6：分布式锁的正确性
- **观测数据**：
  - 锁的过期时间与实际执行时间对比（是否提前释放）。
  - 同一锁被多个客户端同时持有的次数（通过 `DEBUG OBJECT` 看引用计数）。
  - Redlock 场景下，多数实例的加锁成功/失败比例。
- **关注点**：是否存在锁未释放、死锁或可重入问题。

### 场景 7：消息队列的消费积压
- **观测数据**：
  - List/Streams 中的消息长度（`LLEN`、`XLEN`）。
  - 消费者组 pending 消息数量（`XPENDING`）。
  - 消息重试次数及死信情况（需额外记录）。
- **关注点**：生产者速度远大于消费者时，是否导致内存暴涨。

### 场景 8：集群模式下的数据分布
- **观测数据**：
  - 各 slot 分布是否均衡（`CLUSTER SLOTS` 的 slot 数量差 <10%）。
  - 集群节点间网络延迟（`INFO cluster` 中的 `cluster_stats_messages_*`）。
  - 迁移中的槽位（`CLUSTER GETKEYSINSLOT` 检查是否阻塞正常请求）。
- **关注点**：扩缩容时是否出现请求失败或数据丢失。

## 三、常用观测工具与命令

| 观测目的      | 命令/工具                                        | 关键指标示例                                       |
| ------------- | ------------------------------------------------ | -------------------------------------------------- |
| 实时统计      | `INFO ALL`                                       | `keyspace_hits`, `used_memory`, `connected_slaves` |
| 监控面板      | Prometheus + Grafana + redis_exporter            | 命中率趋势、内存增长曲线、命令执行速率             |
| 慢查询        | `SLOWLOG GET 100`                                | 耗时 > 阈值的命令列表                              |
| 大 key 扫描   | `redis-cli --bigkeys`                            | 每个数据类型中最大的 key                           |
| 热点 key 检测 | `redis-cli --hotkeys`（需 maxmemory-policy lfu） | 访问频率最高的 key                                 |
| 命令执行监控  | `MONITOR`（慎用，性能开销大）                    | 实时打印所有请求                                   |
| 集群诊断      | `CLUSTER INFO`, `CLUSTER NODES`                  | 集群状态、主从对应关系                             |
| 压测工具      | `redis-benchmark`                                | 不同并发下的 QPS / 延迟（p99）                     |

## 四、总结：测试工程师的检查清单

- **功能测试**：验证缓存是否命中、锁是否生效、计数器是否准确。
- **性能测试**：观测 QPS、延迟（p99/p999）、内存增速。
- **稳定性测试**：模拟内存写满、主从断连、网络分区，检查 Redis 是否自动恢复。
- **数据一致性测试**：对比 Redis 与 DB 的数据，校验缓存更新策略（Cache Aside / Write Through）。
- **混沌测试**：随机 kill 主节点、从节点，观察故障转移时间和数据完整性。

理解 Redis 在这些场景下的“变与不变”（数据本身可变，但结构不变），是测试总工程能精准设计预案、定位瓶颈的关键。如果你有具体的 Redis 测试场景（例如秒杀、排行榜竞争），我可以给出更针对性的观测方案。
