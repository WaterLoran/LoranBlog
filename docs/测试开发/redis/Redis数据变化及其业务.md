# Redis数据变化及其业务

当 Redis 中的数据发生变化时，通常意味着**业务状态、系统边界或实时决策逻辑被触发**。作为测试工程师，理解这些变化背后的业务场景，能帮助你设计更精准的验证用例。

以下是 Redis 中数据变化最常见、最典型的业务场景，按数据变更类型分类：

---

## 一、新增数据（写入/初始化）

| 业务场景           | 触发动作             | Redis 数据结构                              | 业务含义                             |
| ------------------ | -------------------- | ------------------------------------------- | ------------------------------------ |
| **用户首次登录**   | 生成 Session Token   | String（`SET session:userId token`）        | 会话开始，设置过期时间（如 30 分钟） |
| **短信验证码发送** | 向手机发送验证码     | String（`SET phone:138**** 123456 EX 300`） | 临时凭证，5 分钟内有效               |
| **购物车添加商品** | 用户点击“加入购物车” | Hash（`HSET cart:userId skuId quantity`）   | 未登录时存 Redis，登录后合并到 DB    |
| **限流计数**       | 用户请求 API         | String（`INCR api:userId`）+ `EXPIRE`       | 1 分钟内访问次数 +1，超阈值则拒绝    |
| **分布式锁抢占**   | 任务开始执行         | String（`SET lock:orderId uuid NX EX 10`）  | 同一时刻只有一个实例能处理该订单     |
| **实时排行榜更新** | 用户获得积分/点赞    | ZSet（`ZINCRBY rank:gameId 10 userId`）     | 游戏积分 +10，排名实时变化           |

---

## 二、修改/更新数据（状态变更）

| 业务场景             | 触发动作                  | Redis 数据结构                                         | 业务含义                               |
| -------------------- | ------------------------- | ------------------------------------------------------ | -------------------------------------- |
| **订单状态流转**     | 订单从“待支付” → “已支付” | String/Hash                                            | 缓存中的订单状态同步更新，减少 DB 查询 |
| **库存扣减**         | 用户下单成功              | String（`DECR stock:skuId`）                           | 原子减 1，若返回值 <0 则回滚并提示缺货 |
| **用户在线状态**     | WebSocket 连接/断开       | Set（`SADD online:roomId userId` / `SREM`）            | 实时显示房间内在线人数/列表            |
| **协同编辑光标位置** | 多人协作时移动光标        | Pub/Sub 或 Stream                                      | 广播位置变化给其他协作用户             |
| **配置热更新**       | 运维修改限流阈值          | String（`SET config:rateLimit 1000`）                  | 无需重启服务，实时生效                 |
| **领取优惠券**       | 用户点击“领取”            | Set（`SISMEMBER coupon:123 userId` → 不存在则 `SADD`） | 防止重复领取，原子检查并添加           |

---

## 三、删除/过期数据（生命周期终结）

| 业务场景            | 触发方式             | Redis 机制                               | 业务含义                        |
| ------------------- | -------------------- | ---------------------------------------- | ------------------------------- |
| **验证码自动失效**  | 5 分钟倒计时结束     | TTL 自然过期                             | 用户未输入则需重新获取          |
| **缓存数据淘汰**    | 内存达到 `maxmemory` | 淘汰策略（LRU/LFU/TTL）                  | 热点数据被踢出，下次访问回源 DB |
| **登出/注销 Token** | 用户点击“登出”       | 主动 `DEL session:userId`                | 强制会话失效，提高安全性        |
| **限流桶清零**      | 时间窗口结束         | Key 自动过期                             | 下一秒重新开始计数              |
| **临时黑名单移除**  | 封禁时间结束         | Key 过期（`SET blacklist:ip 1 EX 3600`） | 自动解封 IP                     |
| **分布式锁释放**    | 业务执行完成         | Lua 脚本判断 uuid 后 `DEL`               | 释放锁，避免死锁                |

---

## 四、批量/原子变更（复杂事务）

| 业务场景                 | 触发动作            | Redis 命令/机制                                       | 业务含义                  |
| ------------------------ | ------------------- | ----------------------------------------------------- | ------------------------- |
| **秒杀库存扣减**         | 多个用户同时抢购    | Lua 脚本（判断库存 >0 → DECR → 记录用户）             | 保证不超卖、不重复购买    |
| **榜单周结算**           | 每周一 00:00        | `RENAME` 或 `EXPIRE` + 新建 key                       | 旧榜单调出，新榜重新开始  |
| **数据迁移/集群 rehash** | 扩缩容时            | 集群自动迁移 slot 中的 key                            | 部分 key 的存储位置变化   |
| **Watch + Multi/Exec**   | 库存预扣 + 订单创建 | 乐观锁（`WATCH stockKey` → 修改 → `EXEC` 失败则重试） | 保证多个 key 修改的原子性 |

---

## 五、被动变化（由外部系统触发）

| 外部事件            | Redis 响应动作                                         | 业务场景示例                                                 |
| ------------------- | ------------------------------------------------------ | ------------------------------------------------------------ |
| **数据库表变更**    | 通过 CDC（如 Canal）监听 binlog → 更新/删除 Redis 缓存 | 管理员在后台修改商品价格，同步刷新缓存                       |
| **消息队列消费**    | 消费者从 Kafka 拉取消息 → 更新 Redis 中的聚合数据      | 用户评论后，更新 Redis 中的“好评率”统计                      |
| **定时任务触发**    | 定时脚本（如 Cron）批量写入/删除 Redis key             | 每天凌晨 2 点重置用户签到次数                                |
| **AI 模型预测结果** | 推理服务将结果写入 Redis                               | 实时推荐系统：用户行为特征 → 模型预测 → 写入 Redis 供前端轮询 |

## 六、测试工程师的观测关注点

当 Redis 数据变化时，你需要验证：

1. **原子性**：并发场景下（如扣库存、限流计数）是否出现数据错乱
2. **过期策略**：TTL 是否按预期生效，是否存在“永远不过期的脏数据”
3. **淘汰策略**：内存写满时，被驱逐的 key 是否符合业务预设（如优先淘汰非热点数据）
4. **一致性**：Redis 与 DB 之间的数据是否最终一致（例如缓存更新后，DB 未及时同步）
5. **性能影响**：大量 key 同时过期（雪崩）或热点 key 集中失效（击穿）时，QPS 毛刺情况
6. **监控指标**：`keyspace_hits/misses`、`evicted_keys`、`expired_keys` 的变化趋势

举例：  
> 在秒杀测试中，你应模拟 500 并发同时 `DECR` 库存 key，检查最终库存是否为 0 且无超卖记录。同时观察 Redis 的 `instantaneous_ops_per_sec` 和慢日志。

---

## 总结：从测试角度分类数据变化场景

| 变化类型      | 典型业务                | 测试重点                           |
| ------------- | ----------------------- | ---------------------------------- |
| **写入**      | 验证码、Session、购物车 | TTL 准确性、并发重复写入           |
| **更新**      | 订单状态、库存、排行榜  | 原子性、CAS 乐观锁                 |
| **删除/过期** | 登出、限流重置、锁释放  | 被动过期 vs 主动删除、内存淘汰策略 |
| **批量**      | 秒杀、周榜单切换        | Lua 脚本正确性、集群 rehash 影响   |
| **被动**      | 消息队列触发、CDC 同步  | 最终一致性、延迟容忍度             |

理解这些场景后，你可以针对性地设计测试用例：比如使用 `redis-benchmark` 压测原子命令，用 `MONITOR` 捕获真实请求序列，或编写混沌实验强制主从切换验证数据丢失风险。
