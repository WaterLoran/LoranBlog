# 如何在测试过程中沉淀校验规则

从测试工程师的视角来看，Great Expectations 的校验规则并非一蹴而就，而是在软件测试生命周期的不同阶段被**发现、提炼、固化**的。下面我将结合具体场景，总结在每个阶段可以沉淀出哪些类型的校验规则，并给出实用经验。

---

## 一、需求分析与测试设计阶段

**核心任务**：理解业务规则、数据定义、字段约束、状态流转等预期行为，提前设计正向和负向的校验点。

### 可沉淀的校验规则类型

| 规则类型           | 示例（基于电商订单）                                         | 对应 GE Expectation                                          |
| ------------------ | ------------------------------------------------------------ | ------------------------------------------------------------ |
| **字段级约束**     | `order_id` 必填且唯一；`total_amount` ≥ 0；`status` 枚举值固定 | `ExpectColumnValuesToNotBeNull`<br>`ExpectColumnValuesToBeUnique`<br>`ExpectColumnValuesToBeInSet` |
| **跨字段业务规则** | `discount` ≤ `total_amount`；`order_date` ≤ `delivery_date`  | `ExpectColumnValuesToMatchOtherColumn`<br>`ExpectCompoundColumnsToBeUnique` |
| **表结构约定**     | 订单表应包含 10 个字段，且字段名、类型与设计文档一致         | `ExpectTableColumnsToMatchSet`<br>`ExpectColumnValuesToBeOfType` |
| **引用完整性**     | `orders.customer_id` 必须在 `customers` 表中存在             | 合并后校验 `ExpectColumnValuesToBeTrue`                      |
| **状态机合法路径** | `PENDING` → `PAID` → `SHIPPED` → `COMPLETED`；不允许反向     | 自定义 `ExpectValidStatusTransition`                         |

### 测试工程师经验

> **经验1：与产品/业务方共同评审“数据契约”**  
> 在需求评审阶段，不要只看功能流程，要专门拉一次**数据规格评审**。把字段类型、取值范围、必填性、唯一性、表间关系、状态流转图都落到文档里，这些就是校验规则的源头。

> **经验2：提前编写“数据质量检查点清单”**  
> 用 Excel 或思维导图列出所有可校验的维度：完整性、唯一性、有效性、一致性、准确性、及时性。每个维度下逐字段填写预期。测试设计阶段产出的这份清单，可以直接转化为 GE 的 Expectation Suite。

> **经验3：为每个规则标注“严重等级”**  
> - **Critical**：阻断流水线（如主键重复、金额为负）  
> - **High**：需告警但可继续（如外键缺失、枚举值非法）  
> - **Medium**：仅记录监控（如字段格式偏离但可容忍）  
> 这有助于后续在 Checkpoint 中配置不同的 action（失败退出 vs 仅通知）。

## 二、测试执行与缺陷发现阶段

**核心任务**：执行功能测试、集成测试、数据迁移测试时，通过实际数据触发不符合预期的场景，从而**反向提炼**出遗漏的校验规则。

### 可沉淀的校验规则类型

| 发现方式            | 典型场景                                                   | 沉淀的校验规则                                               |
| ------------------- | ---------------------------------------------------------- | ------------------------------------------------------------ |
| **缺陷引发**        | 发现某笔订单 `total_amount` 为负数，原因是上游计算逻辑 bug | `ExpectColumnValuesToBeBetween(total_amount, min=0)`         |
| **数据探索（EDA）** | 统计 `order_date` 发现 0.1% 的记录年份是 1900（默认值）    | `ExpectColumnValuesToBeBetween(order_date, min='2020-01-01')` |
| **对比测试**        | 新旧系统同一订单的金额不一致                               | `ExpectColumnValuesToMatchOtherColumn` 或跨数据源的比对      |
| **边界值测试**      | 传入极大金额 10^9 导致下游溢出                             | `ExpectColumnValuesToBeBetween(total_amount, max=1e7)`       |
| **组合场景**        | 同一客户同一秒下两单（本应被幂等拦截）                     | `ExpectCompoundColumnsToBeUnique(['customer_id','order_time'])` |

### 测试工程师经验

> **经验4：把“缺陷根因”转化为“永久校验规则”**  
> 每一个数据相关的 bug，修复后都应该追加一条 GE 期望，防止回归。例如：发现订单状态被误改为 `'COMPLETED'` 但未支付，就增加 `ExpectColumnValuesToBeInSet` 并配合 `row_condition` 检查支付状态。

> **经验5：利用数据 Profile 发现隐性规则**  
> 在测试环境执行 `ExpectationSuite` 的 `profile` 功能（或 pandas 描述性统计），观察数据的实际分布、空值率、唯一值数量。你可能会发现：`reject_reason` 字段虽然允许为空，但实际 99% 的拒绝记录都有值——这可以提炼为“非严格但建议的规则”。

> **经验6：记录“负向测试数据”作为校验用例**  
> 测试执行时构造的非法数据（如超长字符串、未来日期、负金额）不要丢弃，直接固化到 GE 的 `Evaluation Parameters` 或单独的数据集中，用于后续的回归校验。

## 三、测试右移阶段（生产监控与持续验证）

**核心任务**：将校验规则部署到生产数据流水线中，持续监控数据质量，并根据生产上的**真实异常**或**新出现的模式**反向优化规则集。

### 可沉淀的校验规则类型

| 生产现象          | 可沉淀的规则                                                 |
| ----------------- | ------------------------------------------------------------ |
| **数据延迟**      | `ExpectColumnValuesToBeBetween(order_time, max=now())`<br>`ExpectTableRowCountToBeBetween`（今日 vs 昨日） |
| **异常峰值/零值** | 某天订单量突增 10 倍 → `ExpectTableRowCountToBeBetween` 设定动态阈值（如过去 30 天均值的 ±3σ） |
| **新枚举值出现**  | 状态字段突然出现 `'REFUNDED'`，但文档未更新 → 更新 `value_set` 或改为 `ExpectColumnValuesToBeInSet(..., strict=False)` 并告警 |
| **数据漂移**      | 客户年龄字段从整数变为浮点数（类型漂移）→ `ExpectColumnValuesToBeOfType` |
| **跨系统不一致**  | 订单表与仓储表的库存扣减数量对不上 → 增加跨数据源的 `ExpectQuer圴ColumnValuesToMatchOtherColumn` |

### 测试工程师经验

> **经验7：建立“规则演进机制”**  
> 生产环境的数据模式会随时间变化。建议每两周 review 一次生产校验结果，将频繁出现的“假阳性”规则调低严重等级或修改阈值；将新发现的“真异常”固化为新规则。

> **经验8：区分“硬规则”与“软规则”**  
> - **硬规则**：违反即阻断下游（如金额为负）。用 `ExpectationSuite` 的 `catch_exceptions=False` 或 Checkpoint 中设定 `fail_on_unexpected=True`。  
> - **软规则**：仅记录到 Data Docs 或发送 Slack 提醒，不阻断流水线。通过 Checkpoint 的 `actions` 配置区分处理。

> **经验9：利用 Evaluation Parameters 实现“自适应规则”**  
> 例如：今日订单量应该与昨日相差不超过 20%。可以先用 SQL 查询昨日数量，然后作为参数传入 `ExpectTableRowCountToBeBetween`。这种动态规则比固定阈值更适应业务波动。

## 四、回归与持续集成阶段（CI/CD 中的校验）

虽然不是严格独立的阶段，但在自动化回归测试中，可以沉淀出以下规则：

| 回归场景             | 规则沉淀                                                     |
| -------------------- | ------------------------------------------------------------ |
| **代码变更影响分析** | 每次构建时运行 GE 校验，对比 baseline 分支的数据校验结果，自动识别预期外的数据变化 |
| **数据迁移脚本验证** | 迁移前 vs 迁移后的数据一致性校验（行数、总和、唯一键）→ `ExpectTableRowCountToEqual`, `ExpectColumnSumToEqual` |
| **API 返回数据校验** | 将 API 返回的 JSON 转为 DataFrame，然后应用 `ExpectColumnValuesToMatchJsonSchema` 或自定义期望 |

> **经验10：将校验规则作为“测试资产”纳入版本控制**  
> 所有 `ExpectationSuite` 的 JSON 文件应存放在代码仓库中，与功能测试代码一起评审、一起 CI。修改规则需要走 PR 流程，确保数据质量的可审计性。

---

## 总结：测试工程师的校验规则沉淀路径图

| 阶段         | 主要输入                     | 输出（校验规则）                     | 关键动作                                 |
| ------------ | ---------------------------- | ------------------------------------ | ---------------------------------------- |
| **测试设计** | 需求文档、数据字典、业务规则 | 字段级、表级、引用完整性、状态机规则 | 数据契约评审，产出检查点清单             |
| **测试执行** | 缺陷、数据探索、对比测试     | 边界值、组合唯一性、跨字段一致性规则 | 将 bug 根因固化，用 profile 发现隐性规则 |
| **测试右移** | 生产监控、数据漂移、新枚举值 | 动态阈值、跨系统比对、时效性规则     | 规则演进，软硬规则分离，自适应参数       |
| **CI/回归**  | 代码变更、迁移脚本、API 响应 | 前后对比规则、基线校验               | 规则版本化，集成到 CI 流水线             |

通过这样分阶段的沉淀，测试工程师不仅是在“校验数据”，更是在**构建企业级的数据质量知识库**，让数据校验从一次性活动变为持续改进的工程实践。
