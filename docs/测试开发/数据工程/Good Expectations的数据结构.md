# Good Expectations的数据结构

Good Expectations (GX) 通过一套清晰的目录结构来管理项目，每个文件和文件夹都扮演着特定的角色，共同构成一个“数据上下文”（Data Context）。了解这套结构，是高效使用 GX 进行数据工程的基础。

下面是默认的项目目录结构（使用 `great_expectations init` 初始化）及各文件的作用:

```
great_expectations/
├── great_expectations.yml       # 🔧 核心配置文件
├── expectations/                # 📋 期望套件目录
├── checkpoints/                 # ⚙️ 检查点配置目录
├── plugins/                     # 🧩 自定义插件目录
├── uncommitted/                 # 💾 非版本控制文件目录
│   ├── config_variables.yml     # 🔑 敏感信息（如数据库密码）
│   ├── data_docs/               # 📊 自动生成的Data Docs站点（HTML）
│   └── validations/             # ✅ 验证结果记录（JSON）
├── .gitignore
└── (其他项目文件)
```

### 🧭 核心概念与目录结构
`great_expectations/` 是 GX 项目的数据上下文，它像一个总管家，组织并管理着所有关键信息。你可以把每一个子目录理解为专门存放特定类型“信息”的“容器”，也就是GX里所说的“存储”（Store）。这些容器在核心配置文件中被定义和关联：

#### **`great_expectations.yml`** - 项目的中枢大脑
这是项目的总配置文件，它定义了所有东西在哪里以及如何连接。
*   **存储位置配置**：定义了项目元数据（如期望、检查点、验证结果等）存储在哪。默认存储在本地文件系统的相应子目录中，但也可以配置到云端（如 AWS S3, Azure Blob）或数据库，以便团队共享。
*   **数据源配置**：声明如何连接到你的数据库或文件系统（如 PostgreSQL、CSV 文件）。

#### **`expectations/`** - 📋 数据质量的规则书
此目录存储着你对数据的每一个“期望”，即数据质量校验规则，例如“`id`列值不能为空”、“`age`列值必须介于0到120之间”。
*   **物理形式**：以`JSON`文件存储，你可以像管理代码一样对它们进行版本控制。
*   **逻辑关系**：由**期望存储（Expectations Store）** 管理。

#### **`checkpoints/`** - ⚙️ 自动化验证的执行器
检查点将期望套件、数据源和执行动作打包成一个可重复运行的自动化验证流程。
*   **物理形式**：以`.yml`配置文件形式存在，定义了“用哪套规则去验证哪批数据”。
*   **逻辑关系**：由**检查点存储（Checkpoint Store）** 管理。

#### **`plugins/`** - 🧩 功能扩展的百宝箱
此目录用于存放你的自定义代码，例如个性化的数据连接器、自定义期望或新的数据渲染方式，让你可以按需扩展GX的核心功能。

#### **`uncommitted/`** - 💾 机密与成果的保管箱
此目录下的所有文件默认**不应纳入版本控制（如Git）**，因为它包含敏感信息或生成的报告。
*   **`config_variables.yml` (敏感信息)**：集中存放数据库密码、API密钥等机密信息。GX的模板功能可以在 `great_expectations.yml` 中通过占位符安全地引用这些值。
*   **`data_docs/` (📊 数据文档)**：由GX自动生成的一个静态HTML网站。它将期望套件、验证结果等数据以人类可读的方式呈现，是团队查看数据质量的“仪表盘”。
*   **`validations/` (✅ 验证结果)**：存储每次运行检查点后产生的详细验证结果，记录哪些数据通过了校验，哪些失败了。
    *   **逻辑关系**：由**验证结果存储（Validation Results Store）** 管理。

### 🔄 工作流程与文件交互
这些组件并非孤立存在，它们在一个典型的数据验证工作流中紧密协作：
1.  **配置数据源**：在 `great_expectations.yml` 文件中定义数据连接。
2.  **创建期望套件**：使用 `Validator` 定义数据校验规则，并将规则保存为 `expectations/` 目录下的 `JSON` 文件。
3.  **定义检查点**：创建 `checkpoints/` 下的 `.yml` 文件，将期望套件和数据源绑定，构成一个可执行的验证任务。
4.  **运行验证与生成报告**：执行检查点。GX会依据规则验证数据，并自动完成两件事：
    *   将验证结果（`JSON`）保存到 `uncommitted/validations/` 目录。
    *   基于验证结果，自动更新 `uncommitted/data_docs/` 下的数据文档，生成最新的数据质量报告。

### 💡 新旧版本差异与最佳实践
由于你之前提到使用的是 **Great Expectations 1.x（GX Core）**，需要注意它与传统版本在结构上的一些差异：

*   **目录根名称**：在 **GX 1.0+ (GX Core)** 中，项目默认根目录通常为 **`gx/`**，以区别于旧版本的 `great_expectations/`。
*   **未变更目录**：**旧版本（0.18.x）** 的目录结构，除了根目录名称，其他子目录及功能与本文描述基本一致。例如，在旧版本中，验证结果默认也存储在 `uncommitted/validations/` 目录下。

**最佳实践建议**：
*   **版本控制**：将 `great_expectations.yml`, `expectations/`, `checkpoints/` 和 `plugins/` 纳入Git进行版本控制。
*   **安全**：确保 `uncommitted/` 目录**不被**纳入版本控制，所有敏感信息（如数据库密码）只能通过 `uncommitted/config_variables.yml` 管理。
*   **团队协作**：为了让团队共享数据文档和验证结果，建议将 `data_docs` 和 `validations` 的存储后端配置为云存储（如AWS S3），而非本地文件系统。

### 💎 总结
Great Expectations 的文件结构清晰、职责分明：`great_expectations.yml` 是定义全局配置的“大脑”，`expectations/` 和 `checkpoints/` 共同构成了可复用的“规则库”和“执行器”，而 `uncommitted/` 则安全地存放着敏感的“机密”和宝贵的“工作成果”。这套设计理念，使得数据质量工程变得像软件工程一样可维护、可协作。
