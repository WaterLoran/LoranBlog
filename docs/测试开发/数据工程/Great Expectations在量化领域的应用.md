# Great Expectations在量化领域的应用

Great Expectations (GE) 在量化领域的应用有鲜明的特点，与其他行业既有共通之处，也有量化特有的深度要求。

---

## 一、GE 在各行业的应用概览

### 1. 金融行业：监管合规与风险控制

**应用场景**：银行、投资公司、保险机构的数据质量保障

| 应用案例             | 具体实践                                                     | 业务价值                                       |
| :------------------- | :----------------------------------------------------------- | :--------------------------------------------- |
| **银行监管报表**     | FinTrust Bank使用GE验证监管报送数据的完整性，检查字段缺失、数据类型错误、逻辑不一致（如负存款） | 错误率从5%降至0.25%，避免监管处罚              |
| **投资公司数据入湖** | 全球投资机构用GE建立数据契约，统一第三方数据供应商的格式规范 | 新数据源接入效率提升，不再需要重复定义质量规则 |
| **保险公司ML管道**   | 欺诈检测模型因数据源污染而崩溃后，引入GE做自动化质量门禁     | 防止空值、单位不一致等问题破坏生产模型         |

**金融行业的共性特点**：
- 数据质量直接关联**合规风险**和**金钱损失**
- 需要满足监管对数据审计追溯的要求
- 外部数据源多，需要建立统一的**数据契约**

### 2. 科技/互联网行业：数据产品与用户体验

**应用场景**：用户行为数据、AB测试、推荐系统

| 应用案例         | 具体实践                                                   | 业务价值                         |
| :--------------- | :--------------------------------------------------------- | :------------------------------- |
| **Calm App**     | 在Airflow DAG中嵌入GE验证，按严重级别分级处理（告警/阻断） | 在用户发现问题前主动发现数据异常 |
| **一般数据产品** | 验证用户行为埋点数据的完整性、会话时长计算的正确性         | 保障数据产品可靠性，提升决策信心 |

**科技行业的共性特点**：
- 数据量大、变更频繁，需要**自动化质量门禁**
- 多与Airflow、dbt等编排工具集成
- 强调**主动发现**而非被动响应

### 3. 数据基础设施：特征存储与数据湖

**应用场景**：Databricks、Delta Lake、数据湖仓一体架构

| 应用案例               | 具体实践                                       | 业务价值                 |
| :--------------------- | :--------------------------------------------- | :----------------------- |
| **Databricks特征存储** | 在特征刷新时用GE验证数据分布、空值率、异常值   | 防止坏特征污染模型训练   |
| **数据湖质量保障**     | 对Delta Lake表进行行数、唯一性、数据新鲜度检查 | 确保数据产品的可靠性基线 |

**基础设施层的共性特点**：
- 需要与Spark/PySpark生态深度集成
- 验证规模大，需要**高性能执行**


## 二、GE 在量化领域的特殊应用

量化交易对数据质量的要求比传统金融更苛刻——**数据错误直接导致策略亏损或系统崩溃**。以下是量化领域的独特应用场景：

### 1. 行情数据验证

**量化特有的挑战**：行情数据是时序的、高频的、多源的，任何延迟或错误都会影响策略决策。

| 验证类型       | GE 期望示例                         | 量化业务意义                 |
| :------------- | :---------------------------------- | :--------------------------- |
| **时序完整性** | 每秒必须有1条tick数据               | 防止行情断流导致策略无信号   |
| **价格合理性** | 价格变化不超过前值的±10%            | 过滤异常报价（胖手指、闪崩） |
| **多源一致性** | 交易所A与交易所B的同一品种价差<阈值 | 确保主备行情源切换时无跳变   |

```python
# 量化行情验证示例
expectation_tick_frequency = ExpectColumnValuesToBeBetween(
    column="tick_count_per_second",
    min_value=0.9,  # 至少每秒0.9条
    max_value=1.1
)

expectation_price_spread = ExpectColumnPairValuesToBeBetween(
    column_A="price_source_a",
    column_B="price_source_b",
    max_difference=0.001  # 价差不超过0.1%
)
```

### 2. 策略因子数据验证

**量化特有的挑战**：策略依赖数百个因子，因子数据错误会传导至整个投资组合。

| 验证类型           | GE 期望示例                              | 量化业务意义               |
| :----------------- | :--------------------------------------- | :------------------------- |
| **因子分布稳定性** | 因子值均值/标准差与历史30日均值偏差<2σ   | 监测因子漂移，防止策略失效 |
| **行业中性**       | 各行业暴露度之和≈0                       | 验证中性化处理正确         |
| **极值处理**       | Winsorized后的值不超过原始值的±5倍标准差 | 防止极端值扭曲信号         |

### 3. 回测数据完整性验证

**量化特有的挑战**：回测依赖历史数据的完整性，数据缺失会导致**前视偏差**和**幸存者偏差**。

| 验证类型         | GE 期望示例                                                  | 量化业务意义         |
| :--------------- | :----------------------------------------------------------- | :------------------- |
| **无未来数据**   | `expect_column_values_to_be_between` with timestamp ≤ current | 防止前视偏差         |
| **成分股完整性** | 每日股票数量与交易所公告一致                                 | 确保全市场覆盖       |
| **复权准确性**   | 后复权价格 = 前复权价格 × (1+复权因子)                       | 验证分红拆股处理正确 |

### 4. 风控数据验证

**量化特有的挑战**：风控系统依赖实时计算的持仓、希腊字母、杠杆率，错误会导致**误杀或漏杀**。

| 验证类型           | GE 期望示例                      | 量化业务意义                 |
| :----------------- | :------------------------------- | :--------------------------- |
| **持仓对账**       | 交易系统持仓 = 清算系统持仓      | 防止数据不一致导致的仓位错误 |
| **希腊字母一致性** | Delta(组合) = Σ Delta_i × 持仓_i | 验证风控计算正确性           |
| **杠杆率限制**     | 杠杆率 ≤ 3.0                     | 确保风控规则生效             |

### 5. 多阶段管道验证

**量化特有的挑战**：数据经过原始→清洗→特征→策略→风控多阶段流转，每一阶段都可能引入错误。

根据Pluralsight的实验设计，GE可以实现**分阶段递进式验证**：

```python
# 原始数据验证：宽松规则
raw_expectations = [
    ExpectColumnValuesToNotBeNull(column="price", mostly=0.95),  # 允许5%空值
    ExpectColumnValuesToBeBetween(column="volume", min_value=0)
]

# 清洗后验证：严格规则
cleaned_expectations = [
    ExpectColumnValuesToNotBeNull(column="price", mostly=1.0),  # 必须100%完整
    ExpectColumnValuesToBeBetween(column="volume", min_value=0)
]

# 特征层验证：业务规则
feature_expectations = [
    ExpectColumnValuesToBeInSet(column="factor_quartile", value_set=[1,2,3,4]),
    ExpectColumnValuesToBeBetween(column="momentum", min_value=-1, max_value=1)
]
```


## 三、量化 vs 通用领域的应用对比

| 维度           | 通用领域应用           | 量化领域特殊要求                               |
| :------------- | :--------------------- | :--------------------------------------------- |
| **时效性要求** | 分钟/小时级验证        | 毫秒/微秒级监控，盘前必须完成验证              |
| **数据复杂度** | 结构化为主             | 时序+订单簿+多源异构数据                       |
| **验证逻辑**   | 简单约束（非空、范围） | 复杂计算关系（Greeks、持仓对账、因子中性化）   |
| **失败处理**   | 告警、阻断、记录       | **熔断**：策略降级、切换到备份数据源           |
| **合规要求**   | 审计追溯               | 监管报告+**交易复盘**双重追溯                  |
| **验证频率**   | 每日批处理             | 实时验证（每笔订单、每Tick行情）               |
| **依赖工具链** | Airflow、dbt、Spark    | **低延迟系统**（C++核心）+ 回测平台 + 仿真环境 |


## 四、GE 在量化测试工程师工作中的定位

结合之前讨论的量化测试职责，GE可以应用于以下工作：

| 测试工程师职责   | GE 的应用方式                                                |
| :--------------- | :----------------------------------------------------------- |
| **数据层比对**   | 用`ExpectColumnValuesToMatchOtherColumn`验证交易系统与清算系统持仓一致 |
| **计算关系校验** | 用`ExpectColumnValuesToMatchOtherColumn`验证`总资产 = 现金 + 持仓市值` |
| **状态机校验**   | 开发`Custom Expectation`验证订单状态流转合法性               |
| **业务约束校验** | 用`ExpectColumnValuesToBeBetween`验证杠杆率≤3、单笔金额≤100万 |
| **时序因果校验** | 用`row_condition`验证`trade_time >= order_time`              |

### 量化测试工程师的GE实践建议

1. **从盘后验证开始**：先对历史数据做GE验证，建立质量基线
2. **逐步前移**：将验证集成到数据管道（Airflow DAG），在数据进入策略系统前拦截问题
3. **区分严重级别**：如Calm的做法，warning级别仅告警，critical级别阻断管道
4. **开发自定义期望**：量化特有的验证（如Greeks计算）需要`Custom Expectation`
5. **与CI/CD集成**：回测平台更新时自动触发GE验证，确保数据质量


## 五、GE 的局限性（量化场景需注意）

根据Monte Carlo的分析，GE等开源工具在规模化后存在局限：

| 局限性               | 量化场景的表现                                 | 应对策略                             |
| :------------------- | :--------------------------------------------- | :----------------------------------- |
| **只能验证已知问题** | 只能发现已写期望的数据问题，无法发现新模式异常 | 结合监控告警+人工巡检                |
| **测试创建成本高**   | 每个字段/每条规则都需要手工编写期望            | 建立期望模板库，自动化生成           |
| **无自动根因分析**   | 发现失败后需人工定位原因                       | 结合链路追踪工具（如Jaeger）         |
| **不处理实时流**     | 主要面向批处理                                 | 对实时交易，需要配合其他流式验证工具 |

对于量化机构，GE更适合**盘后验证**和**数据管道验证**；实盘交易中的实时风控验证，需要更低延迟的方案。
