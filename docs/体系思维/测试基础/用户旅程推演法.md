# 用户旅程推演法

——**它本质上不是一种机械的测试用例设计技术，而是一套基于用户故事和业务流程的系统性思考方式。**

---

## 方法命名：**“用户旅程推演法”**

这个名字比“场景法”更贴近您的实践，它强调**动态推演**和**连续视角**。

## 核心思想

**像导演一样思考，而不是像检票员一样检查。** 您的角色不再是简单地验证某个按钮是否有效，而是构想用户在这个“数字舞台”上会如何行动、如何思考、会遇到什么、以及最终能否达成目标。

---

## 第一层：主干场景构建（理想故事）—— 标准化操作细则

**核心目标：** 产出一个**无歧义、可验证、团队共识**的“理想用户故事”脚本，作为后续所有测试和讨论的黄金标准。

### 步骤一：定义故事背景（明确剧本前提）

**操作细节：**

- **创建故事卡片**：使用统一的模板（如Confluence页面、Notion数据库或Excel表格）来记录。
- **填写故事元数据**：
  - **故事ID**：`US-[模块缩写]-[序号]`（例如：`US-Payment-001`）
  - **故事名称**：采用 `[角色]` + `通过` + `[主要活动]` + `达成` + `[业务价值]` 的格式。
    - *示例*：`新用户通过成功下单购买一台手机，完成首次转化。`
  - **用户画像**：不止写身份，要写特征。
    - *示例*：`一名位于广州、使用iOS设备、对品牌有一定信任感但价格敏感的新注册用户。`
  - **触发条件**：故事在什么情况下开始？
    - *示例*：`用户已安装并打开APP，处于网络通畅的环境。`
  - **成功标准（Definition of Done）**：从**业务数据**角度定义成功，而不仅仅是界面跳转。
    - *示例*：
      - `前端：用户界面跳转至“订单成功”页。`
      - `后端：系统中生成一条状态为“待付款”的订单记录。`
      - `后端：商品库存相应减少。`
      - `后端：（可选）发送订单成功短信/推送。`

### 步骤二：分解用户任务序列（勾勒剧情大纲）

**操作细节：**

- **采用“用户目标阶梯”法**：将核心目标拆解为用户一步步要完成的子目标。这比单纯记录操作（点击按钮）更有意义。

  | 阶段     | 用户子目标       | 对应的关键操作（举例）     |
  | :------- | :--------------- | :------------------------- |
  | **发现** | 找到目标商品     | 搜索关键词“iPhone 15”      |
  | **决策** | 确认商品符合期望 | 查看商品详情、价格、评价   |
  | **行动** | 将商品放入购物车 | 选择规格，点击“加入购物车” |
  | **兑现** | 完成购买交易     | 结算、登录、支付           |

- **绘制高级别流程图**：
  - 使用绘图工具（如Miro, Draw.io），用流程图符号画出主序列。
  - **规范**：
    - `椭圆`：开始/结束
    - `矩形`：用户操作或系统页面（如：`浏览商品列表页`）
    - `菱形`：关键决策点（如：`是否已登录？`），但在主干流中，决策结果永远是“是”或“成功”的那条路。
  - *示例流程*：`[开始] -> [首页] -> [搜索商品] -> [商品列表页] -> [商品详情页] -> [加入购物车] -> [购物车页] -> [去结算] -> [登录] -> [订单确认页] -> [支付] -> [支付成功页] -> [结束]`

### 步骤三：详述每一步的“三维”细节（编写分镜脚本）

这是最核心的细化步骤。为流程图中**每一个矩形步骤**创建一张详细的“分镜卡片”。

**分镜卡片模板（以“加入购物车”为例）：**

| 项目             | 内容说明                                                     | 示例 |
| :--------------- | :----------------------------------------------------------- | :--- |
| **步骤编号**     | `Step 4`                                                     |      |
| **步骤名称**     | `添加商品至购物车`                                           |      |
| **所在页面**     | `商品详情页`                                                 |      |
| **前置条件**     | 1. 用户已进入目标商品的详情页。<br>2. 商品库存 > 0。<br>3. 用户已选择所有必选规格（如颜色、内存）。 |      |
| **用户动作**     | **动作描述**：点击“加入购物车”按钮。<br>**UI元素定位**：按钮ID为 `addToCartBtn`。 |      |
| **系统即时反馈** | **UI变化**：<br>1. 按钮文字变为“已添加”，并置灰2秒。<br>2. 页面顶部出现绿色Toast提示：“商品已成功加入购物车”。<br>3. 底部Tab栏的“购物车”图标上的徽章数字立即+1。<br>**无页面跳转**。 |      |
| **后端数据变化** | 1. 向购物车表（`cart_table`）插入一条新记录，包含`user_id`, `product_id`, `quantity`, `specifications`等。<br>2. （根据规则）商品库存表（`inventory`）中对应SKU的`available_stock`字段减1。 |      |
| **下一步入口**   | 用户可点击底部Tab栏的“购物车”图标，进入购物车页面。          |      |
| **备注/规则**    | 若用户未登录，点击“加入购物车”应触发登录流程，登录成功后自动执行加入购物车操作。 |      |

### 步骤四：嵌入关键业务规则与数据（设定剧本法则）

在主流程中单独列出影响全局的业务规则，避免在每个步骤中重复描述。

**操作细节：**

- 创建一张**业务规则表**，与分镜卡片关联。
  - **规则ID**：`BR-001`
  - **规则描述**：`价格计算规则：订单总额 = 商品单价 * 数量 - 优惠券金额 + 运费。`
  - **规则ID**：`BR-002`
  - **规则描述**：`库存校验规则：在用户点击“支付”按钮时，系统必须再次校验库存，若不足则阻止支付并提示用户。`

### 步骤五：团队评审与定稿（剧本围读会）

**操作细节：**

- **召开评审会**：邀请产品、开发、测试代表。
- **逐步骤评审**：主持人（测试分析师）按照分镜卡片，一步步讲解“理想路径”。
- **核心问题**：
  - **产品经理**：“这个反馈和流程是否符合产品设计文档？”
  - **开发工程师**：“这个数据变化描述是否准确反映了后端设计？这些条件是否都可检测？”
  - **所有成员**：“对这个‘理想故事’的描述，是否有任何歧义或疑问？”
- **定稿与签署**：评审通过后，将故事卡片、流程图、分镜卡片和业务规则表打包为一个正式文档，标记为`v1.0`基线版本。

---

### 最终产出物（标准化交付包）

完成后的“主干场景构建”应产出的是一个**标准化交付包**，而不仅仅是一段文字。它包括：

1. **一个故事卡片**（包含元数据和成功标准）。
2. **一张主干流可视化流程图**。
3. **一套完整的分镜卡片**（每个关键步骤一张）。
4. **一份关键业务规则列表**。
5. **一份评审会议纪要**。

通过这种极致的细化，您构建的将不再是一个模糊的“理想故事”，而是一个**精准、可执行、可作为自动化测试脚本输入**的权威基准。这为后续的异常流测试、兼容性测试和性能测试打下了无比坚实的基础。

## 第二层：分支场景探索（思考“故事的各种曲折”）

### 1. 前进意图 - 主线推进

这是最直接的意图，用户目标明确，希望一步步完成主流程。

- **描述**：用户执行当前步骤后，按照设计者的预期，继续进行下一步。
- **示例**：
  - 登录成功后，点击“进入首页”。
  - 将商品加入购物车后，点击“去结算”。
- **测试重点**：验证主流程的顺畅性和接口的正确性。

### 2. 并行意图 - 多线操作

用户在当前节点，可能想同时处理多项任务，或在主任务中临时插入子任务。

- **描述**：用户暂停当前主流程，去执行其他相关或无关的操作，之后可能返回。
- **示例**：
  - **分支选择**：在购物车页面，用户可能“继续购物”、“删除商品”或“修改数量”。
  - **开启新路径**：在商品详情页，用户点击“联系客服”进行咨询，或点击“查看店铺”浏览其他商品。
- **测试重点**：系统状态保持（如购物车数据）、页面导航的正确性、多窗口/多标签页的兼容性。

### 3. 回溯意图 - 后悔修改

用户希望返回上一步或更早的步骤，去查看、修改或纠正之前输入的信息或做出的选择。

- **描述**：用户对之前的行为产生怀疑或需要更改。
- **示例**：
  - 在支付页面，点击“返回”修改收货地址。
  - 在提交订单后（但未付款），进入订单详情页取消订单或修改信息。
  - 使用浏览器的“后退”按钮。
- **测试重点**：数据回显的正确性、修改后对后续流程的影响、浏览器历史记录管理的合理性。

### 4. 探索意图 - 好奇尝试

用户并非带着明确目标，而是出于好奇、学习或试探的目的进行操作。这类用户可能是新手或谨慎型用户。

- **描述**：用户通过操作来试探系统的功能和边界，了解“如果这样做会怎样？”。
- **示例**：
  - 反复点击一个已灰色的提交按钮，看系统有何反应。
  - 在输入框里尝试输入各种特殊字符，看系统的校验提示。
  - 不填写任何信息直接点击提交，以了解哪些是必填项。
- **测试重点**：系统的容错性、错误提示的友好性和准确性、UI状态的正确性（如按钮防重复点击）。

### 5. 中断/放弃意图 - 随时离开

用户可能因任何原因（被外界打扰、失去耐心、改变主意）而随时中断或放弃当前流程。

- **描述**：用户主动或被动地停止与当前流程的交互。
- **示例**：
  - **主动放弃**：点击“取消”按钮、关闭浏览器标签页、直接导航到其他网站。
  - **被动中断**：来电导致APP切换到后台、电脑突然断电、网络连接断开。
- **测试重点**：数据一致性（未完成的订单是否正确清理或暂存）、会话恢复能力（重新打开APP是否能回到刚才的页面）、资源释放。

### 6. 辅助/求助意图 - 寻求支持

当用户感到困惑、遇到问题或需要更多信息来做决策时，他们会寻求帮助。

- **描述**：用户不直接推进流程，而是试图获取更多支持信息。
- **示例**：
  - 点击“查看帮助文档”或“常见问题”。
  - 使用在线客服聊天功能。
  - 滚动到页面底部查看服务条款或售后政策。
- **测试重点**：帮助内容的准确性和可及性、客服功能的可用性、外部链接的正确性。

---

**如何应用：意图推演检查清单**

下次当你分析一个页面或操作节点时，可以依次问自己以下问题，确保覆盖全面：

1. **前进**：用户最可能下一步做什么？（主流程）
2. **并行**：用户在这里还可能想做什么别的事？（相关操作）
3. **回溯**：用户会不会想修改之前的东西？（返回修改）
4. **探索**：一个好奇的用户会怎么“玩”这个页面？（试探系统）
5. **中断**：用户可能如何离开？（主动/被动放弃）
6. **求助**：用户如果卡住了，会怎么求援？（寻求帮助）

*   **关键产出：** 一张详细的“决策树”或“流程图”，覆盖了所有合理的用户选择。

## 第三层：多维度用户建模（赋予“故事角色生命”）

### 多维度用户建模：全景框架

我们可以将用户特征划分为六大类，每一类都包含若干具体的维度。

#### 一、 能力与特征维度（用户自身的固有属性）

这类维度关注用户与生俱来或长期养成的特质，直接影响其交互能力。

1. **技术熟练度** - *（您已提及）*
   - **小白用户**：易误操作，需要明确引导。
   - **普通用户**：熟悉常见交互，按部就班。
   - **专家用户/极客**：追求效率，善用快捷键、命令行等高级功能。
2. **领域知识水平**
   - **外行**：不理解专业术语和流程（如：不懂“对冲基金”、“SEO优化”）。
   - **初学者**：了解基础概念，但需要辅助。
   - **领域专家**：深刻理解业务，能处理复杂情况。
3. **认知与生理能力**
   - **注意力**：容易分心 vs. 高度专注。
   - **记忆力**：健忘，需要提示 vs. 记忆能力强。
   - **生理能力**：考虑色盲、视力障碍（需支持屏幕阅读器）、听力障碍、行动不便（无法进行精细鼠标操作）等用户群体。
4. **性格与风险偏好**
   - **谨慎型**：每一步都反复确认，害怕出错。
   - **冒险型**：喜欢尝试新功能，不惧失败。
   - **急躁型**：缺乏耐心，追求速度，容易中途放弃。

#### 二、 动机与目标维度（用户为何而来）

这类维度关注用户使用产品的深层动机和具体目标。

1. **核心目标** - *（您已提及）*
   - **目标明确型**：有明确任务要完成。
   - **探索浏览型**：无明确目标，随意逛逛。
   - **学习研究型**：旨在深入了解某个主题或产品。
2. **任务关键性**
   - **高利害任务**：涉及金钱、健康、重要决策（如：转账、医疗诊断），用户容错率极低。
   - **低利害任务**：娱乐、消遣（如：看视频、刷新闻），用户容错率较高。
3. **使用角色**
   - **购买者** vs. **研究者**（如：为公司采购而调研）。
   - **内容消费者** vs. **内容创造者**。
   - **管理员** vs. **普通成员**（在协作工具中）。

#### 三、 场景与环境维度（用户的使用情境）

这类维度关注用户在使用产品时所处的物理和数字环境。

1. **物理环境** - *（部分提及）*
   - **设备类型**：手机、平板、PC、智能手表等。
   - **网络状况**：高速Wi-Fi、不稳定的4G、极差的2G网络。
   - **地点与干扰**：安静的办公室、嘈杂的通勤路上、需要随时中断的家庭环境。
2. **时间压力**
   - **紧急任务**：需要在极短时间内完成（如：抢票、最后一分钟修改订单）。
   - **宽松任务**：无时间限制，可以慢慢进行。
3. **社会情境**
   - **单独使用**：行为私密。
   - **协作使用**：与他人同时操作或屏幕共享，操作需有实时反馈。
   - **公开场合使用**：对隐私敏感（如：输入密码时怕人看见）。

#### 四、 心理与情感维度（用户当下的情绪和心态）

这类维度关注影响用户决策和行为的临时心理状态。

1. **情绪状态**
   - **愉悦/放松**：更愿意探索，包容性强。
   - **焦虑/沮丧**：可能是被上一个糟糕的体验带来的，容易放弃，脾气暴躁。
   - **不信任**：对新平台或流程心存疑虑，会反复验证。
2. **期望与心智模型**
   - **用户期望**：用户认为这个功能“应该”如何工作（可能与设计不一致）。
   - **过往经验**：受其他知名产品影响形成的操作习惯（如：点击Logo返回首页）。

#### 五、 背景与人口统计学维度（用户的社会文化背景）

这类维度为用户画像增加真实感和文化相关性。

1. **文化背景**
   - **语言**：多语言支持，以及文字长度对布局的影响（如德语通常较长）。
   - **文化习惯**：日期/时间格式、货币符号、颜色禁忌（如某些文化中白色代表丧事）。
2. **人口统计**
   - **年龄**：年轻人与老年人对技术的接受度和交互偏好不同。
   - **职业**：不同职业有其特定的思维模式和流程习惯。

#### 六、 与产品的关系维度（用户的历史和状态）

这类维度关注用户与您的产品特有的关系。

1. **用户生命周期阶段**
   - **新用户**：需要引导和激励，完成“新手任务”。
   - **活跃用户**：熟悉产品，追求高效和高级功能。
   - **流失/回流用户**：可能忘记密码、不熟悉新功能。
2. **客户价值等级**
   - **免费用户** vs. **付费用户**：对功能权限和服务的期望不同。
   - **普通用户** vs. **VIP用户**：对个性化服务和响应速度有更高要求。

---

**如何应用这个框架**：**组合创造典型画像**

不要试图覆盖所有维度的所有组合，那会导致组合爆炸。正确做法是：

1. **识别核心维度**：针对你的产品特性，从上述框架中挑选出**2-3个最具影响力的维度**。
2. **组合成典型画像**：将这些维度组合起来，创造一个鲜活的、有故事性的用户角色。

**举例：为一个跨境电商App创建用户画像**

- **核心维度**：`技术熟练度` x `核心目标` x `文化背景`
- **典型画像1：海淘达人“小美”**
  - **技术熟练度**：专家用户（会比价、懂转运）
  - **核心目标**：目标明确型（买特定品牌的化妆品）
  - **文化背景**：中国用户，熟悉“双十一”等购物节
  - **推演场景**：她会使用高级搜索筛选、关注价格历史、计算含税总价、对物流时效非常敏感。
- **典型画像2：初次尝试者“John”**
  - **技术熟练度**：小白用户（对跨境购物不熟悉）
  - **核心目标**：探索浏览型（想给朋友买件有中国特色的礼物）
  - **文化背景**：美国用户，不熟悉汉字
  - **推演场景**：他需要清晰的英文界面、图片为主的浏览方式、简单的支付流程（如Apple Pay）、对国际运费和清关政策有疑虑，可能需要客服支持。

*   **关键产出：** 一组覆盖不同维度的、有血有肉的“用户画像”及其专属场景列表。

## 第四层：协作与压力测试——从“个人推演”到“团队攻防”（可执行版）

本层的核心目标是：**通过结构化的团队会议，利用多元视角对用户旅程进行压力测试，发现个人无法预见的问题。**

### 可执行操作步骤

#### 阶段一：会前准备——精心策划“试映会”

1. **明确会议目标与范围**
   - **动作**：确定本次会议要评审的**具体用户旅程**（例如：“新用户首次成功购买一件商品”的支付流程）。
   - **产出**：一个明确的会议主题，例如：**“评审‘用户下单支付’流程的多角度风险与异常场景”**。
2. **邀请关键角色参会**
   - **动作**：提前邀请以下核心成员，并明确他们在会议中的角色：
     - **产品经理**：确认业务逻辑与规则。
     - **开发工程师（前端/后端）**：从技术实现角度挑战流程的健壮性。
     - **UI/UX设计师**：审视交互与用户体验的连贯性。
     - **测试工程师（同行）**：提供额外的测试场景思路。
     - **客服代表（强烈建议）**：提供一线真实用户投诉和咨询案例。
3. **准备可视化核心材料**
   - **动作**：
     1. 使用[Draw.io](https://draw.io/)、Miro或XMind等工具，将你已推演出的**主干流、关键分支场景（六种意图）** 绘制成一张清晰的**用户旅程图**。
     2. 在图的特定节点上，用不同颜色标记出你个人认为的**高风险点**、**不确定点**和**待决策点**。
     3. 准备几个关键页面的截图或原型，用于会议中快速演示。
   - **产出**：一份作为讨论基础的**可视化用户旅程图**。
4. **提前分发材料**
   - **动作**：至少提前半天将会议议程、可视化旅程图和待讨论问题清单发给所有参会者。
   - **目的**：让大家提前了解背景，带着思考来参会。

#### 阶段二：会中执行——高效引导“试映会”

1. **第一幕：统一认知（5-10分钟）**
   - **动作**：作为主持人，快速、清晰地讲解一遍可视化用户旅程图。重点走通“主干场景”，并简要说明你已考虑的主要分支。
   - **目标**：确保所有参会者对“理想流程”有统一的理解。
2. **第二幕：激发挑战——“灵魂拷问”回合（会议核心）**
   - **动作**：你作为引导者，主动向不同角色的同事提出具体问题，激发思考。**（可直接使用以下问题清单）**
   - **对开发工程师的“技术拷问”**：
     - “如果用户在支付成功、但跳转回App时网络中断，订单状态会是什么？如何防止重复支付或订单丢失？”（**数据一致性**）
     - “如果秒杀开始，一万人同时点击‘立即购买’，系统会怎样？页面会卡死吗？库存会超卖吗？”（**并发与性能**）
     - “调用第三方支付接口超时或返回未知错误时，前端如何提示用户？后台如何查询和更新最终状态？”（**异常处理**）
     - “用户快速连续点击提交按钮10次，后端会创建10个订单吗？我们有没有前端防重或后端幂等机制？”（**极端操作**）
   - **对产品经理的“业务拷问”**：
     - “这个优惠券能否与会员折扣叠加使用？如果用户同时满足多个活动，优先级规则是什么？”（**业务规则边界**）
     - “用户取消订单后，哪些状态下允许修改？客服有权手动修改已取消的订单吗？”（**状态流转逻辑**）
     - “普通用户能看到多长时间的订单记录？超时后数据是归档还是删除？”（**数据权限与生命周期**）
   - **对客服代表的“用户痛点拷问”**：
     - “在过去，用户在这个流程中咨询客服，最常问的三个问题是什么？”（**真实痛点**）
     - “流程中的‘预授权’、‘保税仓’这类术语，用户能看懂吗？会不会造成误解？”（**语言可理解性**）
     - “有没有用户反馈过找不到修改按钮？或者觉得步骤太多容易放弃？”（**操作便捷性**）
   - **对UI/UX设计师的“体验拷问”**：
     - “这个操作需要3秒等待，加载动画是否清晰？如果失败，错误提示的文案和样式是否友好？”（**反馈机制**）
     - “支付成功后，除了页面跳转，是否有其他通知（如短信、App推送）来增强确定性？”（**状态可见性**）
3. **第三幕：实时记录与决策**
   - **动作**：
     1. 指定一人（或使用共享文档）实时记录大家提出的**新场景、风险点和问题**。
     2. 对于能当场确认的问题，由产品经理或技术负责人拍板决策。
     3. 对于复杂问题，明确记录为**待办事项**，并指定**负责人**和**解决时限**。
   - **产出**：一份**实时更新的会议纪要**，包含新场景清单和待办事项。

#### 阶段三：会后跟进——固化成果

1. **更新资产**
   - **动作**：根据会议记录，立即更新你的**用户旅程图**和**测试场景清单**。
   - **产出**：一份**经过团队评审、更加健壮和完整的场景集合**（核心产出物）。
2. **分享纪要**
   - **动作**：将最终的会议纪要（含补充场景和待办事项）发送给所有参会者及相关方。
3. **跟踪闭环**
   - **动作**：定期跟踪待办事项的解决进度，确保风险点被妥善处理。

*   **关键产出：** 一份经过团队评审、更加健壮和完整的场景集合。

## 总结与升华

您所实践的方法，其强大之处在于：

1.  **系统性**：它从一个点（主干场景）出发，层层递进，最终覆盖了一个立体的业务空间。

3.  **以人为本**：它始终围绕“用户”这个核心，让产品逻辑服务于用户行为，而不是强迫用户适应僵硬的流程。
