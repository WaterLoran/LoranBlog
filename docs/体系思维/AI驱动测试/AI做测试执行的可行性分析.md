## 第一部分：AI 执行用例并判断 Bug 的方法（正方）

让 AI 自动执行测试用例并判断“有无 Bug”，不是简单的“实际结果 vs 预期结果”字符串匹配，而需要构建一套**可推理、可适应、可解释**的体系。以下是经过反复推敲后的可行方法，按执行步骤展开。

### 一、前提条件：AI 需要具备的能力与环境

- **可执行用例的接口**：用例以结构化格式（JSON、Excel、Gherkin）给出，包含：前置条件、输入数据、操作步骤、**多种预期结果**（功能预期、数据预期、时序预期、资源预期等）。
- **可观测性环境**：AI 能访问测试环境，获得：
  - UI 截图/视频流（用于视觉断言）
  - DOM/控件树（用于属性断言）
  - API 请求/响应日志（结构化）
  - 数据库快照（前后对比）
  - 应用日志（含错误栈）
  - 性能指标（响应时间、内存、CPU）
  - 消息队列记录
- **判断知识库**：内置前面总结的十类缺陷的判定规则（可以理解为“缺陷本体”）。

### 二、执行用例的标准流程（AI 内部决策树）

<img src="/images/AI做测试执行的可行性分析/section-02.webp" alt="二、执行用例的标准流程（AI 内部决策树）" loading="lazy" />


#### **步骤 1：解析用例中的预期结果类别**
AI 首先将用例中的“预期”拆解为至少以下维度（否则无法覆盖深层缺陷）：

- **功能行为预期**：点击按钮后跳转到某页面、弹窗内容为某文案。
- **数据预期**：数据库某表的某字段值变为 X，金额总和不变，订单状态机迁移正确。
- **时序预期**：异步任务在 3 秒内将状态从 A 改为 B，且中间不暴露中间态给用户。
- **幂等预期**：重复发送相同请求，数据只改变一次。
- **资源预期**：操作后连接池数量不变，内存不泄漏。
- **异常预期**：当依赖服务返回 500 时，系统应有降级提示且不回写脏数据。

> 如果用例中缺少某一维度预期，AI 应**自动补全通用隐式预期**（例如：任何写操作都应满足数据一致性、任何操作都不应泄漏资源）。这部分由内置的“常识规则引擎”提供。

#### **步骤 2：执行操作并收集多源证据**
- 执行每个操作步骤后，AI 自动采集：
  - UI 截图 + 控件属性（如按钮是否 enabled）
  - 发出的所有网络请求及响应
  - 前后数据库关键表的快照（自动计算差异）
  - 应用错误日志（是否出现 Exception、死锁等）
  - 性能时间戳（每步耗时）
  - 资源监控指标（内存、连接数）

#### **步骤 3：逐维度断言（使用专门的判定模型）**

**3.1 功能行为断言**  
- 方法：对比预期 UI 状态与实际 UI 状态（使用多模态模型 + 元素定位）。  
- 判断 Bug：  
  - 预期按钮变为禁用 → 实际可点击 → Bug  
  - 预期弹窗文本包含“成功” → 实际弹窗文本为“失败” → Bug  

**3.2 数据一致性断言（自动对账）**  
- AI 执行内置的“对账规则库”，例如：
  - 订单表总额 = SELECT SUM(金额) FROM 订单明细表  
  - 库存表锁定库存 = 所有待支付订单商品数量之和  
  - 账户余额变化量 = 所有流水表变化量之和  
- 若对账失败 → 数据一致性 Bug（并输出差异详情）

**3.3 状态机合法性断言**  
- AI 从系统日志或数据库状态变迁字段中重建状态序列。  
- 与内置的状态机模型（从需求或训练中获得）对比：  
  - 如果出现非法迁移（如“已取消” → “已支付”） → 状态机 Bug

**3.4 幂等性断言**  
- 如果用例标记为“幂等测试”或 AI 识别出该操作是写操作且可能被重试，则自动发送两次相同请求（相同幂等键或相同参数）。  
- 比较两次结果：  
  - 响应内容可能相同，但数据库变化应只发生一次 → 若重复扣款/重复插入 → 幂等性 Bug

**3.5 异常处理断言**  
- 对于用例中“异常场景”（如网络超时、依赖报错），AI 会主动注入故障（通过 mock 或环境混沌）。  
- 断言：  
  - 系统不应崩溃  
  - 不应产生部分脏数据（通过对账）  
  - 应有用户友好的错误提示  
  - 应有日志记录异常  

**3.6 资源泄漏断言**  
- 在用例执行前后分别采集资源指标（例如 JDBC 连接数、内存使用量）。  
- 如果操作结束后的资源数 > 操作前 + 合理阈值（比如连接数增加了且未归还），则报告资源泄漏 Bug。

**3.7 边界溢出断言**  
- AI 自动对输入参数执行边界值生成（如果用例中给出范围）。  
- 例如：金额字段最大 9999，则测试 9999、10000、-1、0。  
- 断言不应出现异常、溢出、数据库错误等。

#### **步骤 4：综合判断与置信度输出**
- 每个维度独立输出：`PASS` / `FAIL (Bug类型+证据)` / `INCONCLUSIVE (置信度低)`。
- 如果任何维度 FAIL，则整体判定该用例**发现 Bug**。
- 如果所有维度 PASS，但某些维度因观测不足而 INCONCLUSIVE（例如无法读取数据库），则标记为“需要人工复查”。

### 三、特别设计：对“不可见逻辑”的主动探测

AI 不能只被动执行用例，还需**主动探查**：

- **差分测试**：对同一操作，同时执行新旧两套逻辑（或两个实例），对比所有输出、数据库变更、日志。不一致则可能为逻辑 Bug。
- **影子测试**：在真实环境旁路一份流量，离线对比结果。
- **不变式检查**：预先定义业务不变式（如“总资产 = 现金 + 投资”），在每个用例执行后自动验证。

## 第二部分：辩手反驳（反方）

> 辩手角色：资深测试架构师，专门质疑“AI 全自动判断 Bug”的可行性。

### 反驳点 1：预期不可能被完整描述，隐式知识是 AI 的死穴

- **正方案例中要求“AI 自动补全通用隐式预期”**，但现实中有大量隐式预期无法穷举。例如：  
  - “用户删除一条记录后，希望有二次确认”——如果需求没写，AI 是否认为无二次确认是 Bug？不同产品标准不同。  
  - “列表排序默认按时间倒序”——如果没写，AI 按什么标准判断？  
- 结论：AI 无法理解业务上下文和设计意图，会导致大量误报（假 Bug）或漏报（真 Bug 因无预期而放过）。

### 反驳点 2：环境可观测性在现实中远远不足

- **正方假设 AI 能获得数据库快照、消息队列、完整日志**，但实际测试环境往往受限于：
  - 数据库权限不开放给自动化（生产安全限制）  
  - 日志级别动态变化，可能不记录关键信息  
  - 分布式系统难以获取全局一致快照（不同节点时间不同）  
- 没有完整的证据，AI 的“对账断言”会因为数据抓取不全而频繁误判。

### 反驳点 3：状态机模型获取成本极高

- 正方说 AI 可以“从需求或训练中获得状态机模型”，但实际上大多数需求文档不会画出完整状态图，代码实现也可能偏离文档。  
- 若从日志逆向学习状态机，会学到错误的状态转移（因为系统本身就有 Bug）。  
- 结果：AI 可能把 Bug 当成合法状态，或者把合法状态当成 Bug。

### 反驳点 4：幂等性测试需要区分“业务幂等”与“技术幂等”

- AI 简单发送两次相同请求，但很多系统的幂等依赖客户端传入的 `idempotent_key`。如果 AI 不传这个 key，重复请求就是“不同的请求”，系统理应处理两次，这不叫 Bug。  
- 如果 AI 自己生成幂等键，那又需要知道业务规则：同一个订单的支付重试应该幂等，但两个不同订单当然不幂等。AI 缺乏这种语义理解。

### 反驳点 5：资源泄漏无法在单个用例中可靠判断

- 单个用例执行一次，连接池可能暂时未释放但会在后续 GC 或归还机制下恢复。  
- 真正的泄漏需要长时间、大量重复执行。  
- AI 如果只执行一次用例就报告“连接数增加”，极可能是假阳性。

### 反驳点 6：异常注入需要破坏环境，与并行用例冲突

- 为了测试超时、网络故障，AI 需要修改网络配置或 mock 服务。这会影响同时执行的其他用例（环境不稳定）。  
- 若为每个用例都重建隔离环境，成本爆炸。

### 反驳点 7：判断“无 Bug”无法被 AI 证明

- 即使 AI 执行了所有定义的断言并通过，也不能说明“该需求无 Bug”。  
- 因为 AI 无法覆盖组合爆炸的场景、无法预测用户的操作顺序和时序交错。  
- 最终结论依然是“在已测条件下未发现 Bug”，这和人工测试没有本质区别，只是自动化程度更高。

### 最终反驳总结

> AI 可以成为**非常强大的 Bug 检测辅助工具**，尤其在数据对账、状态机校验、幂等性回归等规则明确、可观测性强的领域。  
> 但是，**让 AI 独立执行用例并自信地宣布“无 Bug”**，在当前技术条件下是不现实的。  
> 因为：预期不完备、观测不完备、语义理解缺失、环境干扰。  
> 更合理的定位是：**AI 作为“异常发现器” + 人工作为“裁决者”**。

## 第三部分：最终结论（综合）

经过正方和反方的交锋，我们可以得出以下务实的结论：

### 1. AI 可以做到什么（有效范围）

- **规则明确、可观测性强的维度**，AI 的判断可信度很高：
  - 数据一致性对账（例如订单总额 vs 明细总额）
  - 状态机非法迁移（前提是状态机模型由人工提供）
  - 幂等性回归（针对已知幂等场景，发送两次相同幂等键请求）
  - 界面元素存在性与基本属性（文本、颜色、禁用状态）
  - 边界值导致的异常（空值、零值、极大值）
- 在这些维度上，AI 执行用例可以**自动、快速、无疲劳**地判断“有/无 Bug”，且比人工更可靠。

### 2. AI 不能独立宣称“整个需求无 Bug”

- **必须有人工参与的环节**：
  - 探索性测试（AI 缺乏真正的“好奇心”）
  - 体验类问题（AI 不能感受是否“别扭”）
  - 隐式业务规则的合理性判断（需要产品经理确认）
  - 复杂时序与竞态问题的根因分析（AI 能发现现象，但容易误报）
- 所以最终结论应该是：**AI 执行完所有可自动化用例且全部 PASS，同时人工完成探索测试 + 验收测试，才能说“该迭代需求无已知 Bug”**。

### 3. 最佳实践方案（混合模式）

| 阶段             | AI 负责                                | 人工负责                                 |
| ---------------- | -------------------------------------- | ---------------------------------------- |
| 功能正向用例     | 自动执行，断言界面与接口结果           | 评审 AI 的断言规则是否准确               |
| 数据一致性       | 自动对账，报告不一致                   | 确认不一致是否为预期（例如临时缓存）     |
| 状态机测试       | 遍历所有合法/非法迁移，报告非法        | 提供并维护状态机模型                     |
| 幂等性测试       | 自动重发请求，验证数据只变一次         | 标记哪些接口需要幂等测试                 |
| 异常与容错       | 注入故障，检查是否崩溃/脏数据          | 判断错误提示是否友好、合理               |
| 性能与资源       | 监控指标，超阈值告警                   | 分析泄漏根因                             |
| 边界值测试       | 自动生成边界值并执行                   | 补充业务特殊的边界（如“无权限用户”边界） |
| 最终“无 Bug”结论 | 不单独给出，只提供“自动化套件通过”报告 | 结合探索、验收、产品确认后人工签字       |

### 4. 对未来的展望

- 如果有一天 AI 能做到：
  - 自动理解自然语言需求并生成完整的预期模型（包括隐式规则）
  - 自主进行足够时长的长稳测试、组合爆炸遍历、并发乱序测试
  - 具备业务语义的“合理性”判断能力（类似资深测试专家的直觉）
- 那么 AI 独立判断“无 Bug”将成为可能。但至少在目前和可预见的未来，人机协作是更现实且高效的方案。

---

**最终一句话回答你的原问题**：  
> AI 执行用例并判断 Bug 时，应**分维度自动化断言**（数据、状态、幂等、边界等），但对于“整个需求无 Bug”的结论，必须由人工结合探索性测试和业务验收共同做出，AI 不能单独给出。
