# 测试工作流拆分场景升级为协同闭环

![测试工作流拆分场景升级为协同闭环](/images/测试工作流拆分场景升级为协同闭环/banner.webp)

你原先的 `do`、`review`、`merge`、`debug` 四动作思路，本质上是在测试的每个核心环节（业务分析、测试设计、用例编写）内部建立“执行—检查—整合—回溯”的小闭环。  
结合我之前提出的不足与补充建议，我们可以通过 **多 Agent 协同** 的方式，将这些环节从“独立小闭环”升级为“全流程协同闭环”，同时解决割裂、准入准出、根因分析、度量等问题。

下面我将给出一个详细的设计方案，涵盖：
1. **设计思路调整**
2. **数据交流与传输模型**
3. **Agent 体系设计与职责**
4. **在 Cursor 中的落地方式**
5. **实施步骤与关键要点**

---

## 一、设计思路调整：从“工序内闭环”到“协同闭环”

原有思路是**环节内闭环**，每个环节独立做 do/review/merge/debug，但缺少跨环节联动。  
调整为 **“协同闭环”**：每个环节仍然是这四个动作，但增加了：

- **准入条件**：本环节开始前必须满足上一环节的准出标准（由质量门禁 Agent 判断）
- **准出条件**：本环节完成后必须达到质量标准才能进入下一环节
- **跨环节反馈**：任何环节发现的问题（包括 review 和 debug 中发现的）都能自动触发对上游或下游的提醒，甚至自动创建改进任务
- **全局根因分析**：所有环节的 debug 数据汇集到根因分析 Agent，定期生成改进建议并推动落地
- **端到端缺陷溯源**：缺陷回归阶段发现的漏测会自动追溯到具体环节，并更新该环节的 debug 数据库

整体架构从“串行工序”变为 **“环环相扣的智能协作网络”**。

## 二、数据交流与传输模型

为了实现多 Agent 协同，需要定义统一的数据结构和通信协议。所有 Agent 通过一个 **事件总线（Event Bus）** 或 **共享数据库** 进行异步通信。

### 2.1 核心数据对象

```json
// 业务分析对象 (BusinessAnalysis)
{
  "id": "BA-001",
  "version": 1,
  "status": "draft|reviewing|approved|rejected",
  "content": { ... },
  "created_by": "agent_ba_do",
  "review_comments": [...],
  "merge_source_ids": [...],
  "quality_gate_status": "pass|fail",
  "debug_records": [
    { "timestamp": "...", "source": "test_design", "issue": "...", "root_cause": "..." }
  ]
}

// 测试设计对象 (TestDesign)
{
  "id": "TD-001",
  "business_analysis_id": "BA-001",
  "status": "...",
  "content": { ... },
  "quality_gate_status": "...",
  "debug_records": [...]
}

// 用例对象 (TestCase)
{
  "id": "TC-001",
  "test_design_id": "TD-001",
  "status": "...",
  "content": { ... },
  "execution_results": [...],
  "defects": [...],
  "quality_gate_status": "...",
  "debug_records": [...]
}
```

### 2.2 通信方式

- **事件总线**：使用 Redis Pub/Sub 或 Kafka 类消息队列，Agent 订阅感兴趣的事件（如 `ba.approved`、`td.merged`、`tc.debug.found`）。
- **共享存储**：所有产出物保存在统一的知识库（如向量数据库 + 关系数据库），Agent 通过 API 读写。
- **Agent 间直接调用**：仅在需要强同步的场景（如准入检查）使用 REST/gRPC。

<img src="/images/测试工作流拆分场景升级为协同闭环/section-02.webp" alt="2.2 通信方式" loading="lazy" />


### 2.3 数据流转示意

```
[业务分析 Agent] → (发布 ba.approved 事件)
        ↓
[质量门禁 Agent] → (检查准出条件，发布 gate.passed)
        ↓
[测试设计 Agent] → (订阅 ba.approved，启动 do/review/merge/debug)
        ↓ (发布 td.approved)
[用例编写 Agent] → ...
        ↓
[缺陷回归 Agent] → 发现漏测 → 发布 defect.trace 事件
        ↓
[根因分析 Agent] → 汇总 debug_records → 生成改进报告
```

## 三、Agent 体系设计与职责

我们设计 8 类 Agent，分工协作。所有 Agent 均可部署为独立的服务，通过统一的消息总线通信。

### 3.1 环节执行 Agent（do_agent）

对应你原先的 `xx_do`。  
**职责**：执行具体工作（分析需求、设计测试、编写用例），生成初稿。  
**能力**：可调用 LLM（如通过 Cursor 的 AI 能力）辅助生成内容；可根据用户指令或模板自动生成初稿。  
**输入**：上游产出物（如业务分析稿）、用户需求描述。  
**输出**：产出物（初稿）并存入共享存储，发布 `draft.created` 事件。

### 3.2 评审 Agent（review_agent）

对应 `xx_review`。  
**职责**：对产出物进行自动化评审，生成评审意见。可结合规则（如检查表）和 LLM 判断。  
**能力**：可调用静态分析、规范检查、一致性校验（如业务分析与测试设计的一致性）。  
**输入**：产出物 ID。  
**输出**：评审报告（通过/驳回/建议），发布 `review.completed` 事件。

### 3.3 合并 Agent（merge_agent）

对应 `xx_merge`，但功能增强。  
**职责**：将多个同类产出物合并为一个统一版本，并做一致性校验。  
**能力**：  
- 冲突检测（如业务规则重复、矛盾）  
- 术语一致性检查  
- 合并后生成基线版本  
**输入**：多个产出物 ID。  
**输出**：合并后的产出物，发布 `merge.completed` 事件。

### 3.4 根因追溯 Agent（debug_agent）

对应 `xx_debug`，但范围扩展。  
**职责**：针对本环节发现的问题，追溯上游环节的根因，并记录到 `debug_records`。  
**能力**：  
- 结合问题描述，查询上游产出物的变更历史、评审记录  
- 调用 LLM 分析可能的根因（如需求歧义、设计遗漏）  
- 将分析结果写入该环节的 debug 记录，并触发上游环节的 debug 记录更新（如果根因在上游）  
**输入**：问题描述、本环节产出物 ID、上游产出物 ID。  
**输出**：更新 debug_records，发布 `debug.recorded` 事件。

### 3.5 质量门禁 Agent（gate_agent）

**新增**。  
**职责**：定义并执行每个环节的准入/准出条件。  
**能力**：  
- 维护每个环节的准出标准（如评审通过率、缺陷密度阈值）  
- 监听环节完成事件，自动检查准出条件，若通过则标记 `quality_gate_status=pass`，否则标记 fail 并通知相关人员  
- 监听下一环节启动请求，检查上游准出状态，若未通过则阻止  
**输入**：产出物 ID、环节类型。  
**输出**：更新质量门禁状态，发布 `gate.passed` 或 `gate.failed` 事件。

### 3.6 端到端缺陷溯源 Agent（trace_agent）

**新增**。  
**职责**：在缺陷回归阶段，将发现的缺陷反向追溯至源头环节，并自动更新该环节的 debug 记录。  
**能力**：  
- 接收缺陷回归 Agent 报告的缺陷  
- 分析缺陷与用例、测试设计、业务分析之间的关联（通过内容相似度、变更历史等）  
- 确定最可能遗漏的环节，在相应产出物的 `debug_records` 中添加记录，并标注“漏测”  
- 触发根因分析 Agent 进行深度分析  
**输入**：缺陷描述、相关用例/设计/分析 ID。  
**输出**：更新 debug_records，发布 `trace.completed` 事件。

### 3.7 根因分析与改进 Agent（rca_agent）

**新增**。  
**职责**：定期汇总所有 debug_records，进行统计分析和根因分类，生成改进建议。  
**能力**：  
- 按环节、根因类型、问题模式进行聚类  
- 识别高频根因（如“需求不明确”占 40%）  
- 生成改进报告（如“建议在业务分析环节增加需求澄清会模板”）  
- 可将改进建议转化为任务，分配给相关人员或自动更新模板/规则  
**输入**：所有 debug_records（定期批量）。  
**输出**：改进报告，发布 `improvement.proposed` 事件。

### 3.8 度量与仪表盘 Agent（metrics_agent）

**新增**。  
**职责**：实时收集各环节、各 Agent 的关键指标，提供可视化看板。  
**能力**：  
- 收集效率指标：do 耗时、review 周期、merge 冲突率  
- 质量指标：评审缺陷密度、各环节逃逸率  
- 根因分布、改进闭环率  
- 通过 API 提供数据给前端展示  
**输入**：所有 Agent 的事件数据。  
**输出**：指标数据，发布 `metrics.updated` 事件。

## 四、Agent 之间的交互流程（关键场景）

### 场景1：业务分析环节的正常流转

1. 用户通过 Cursor 发送指令：`@ba_do 分析用户登录需求`
2. `ba_do_agent` 生成分析初稿，存储，发布 `ba.draft.created`
3. `ba_review_agent` 订阅该事件，自动进行评审，发现无问题，发布 `ba.review.passed`
4. `ba_merge_agent` 无合并需求（因为是单份），但触发 `ba_merge_agent` 进行一致性自检，通过后发布 `ba.merge.completed`
5. `gate_agent` 订阅 `ba.merge.completed`，检查准出条件（如评审通过、无严重问题），通过后标记状态，发布 `ba.approved`
6. 测试设计环节的 `td_do_agent` 订阅 `ba.approved`，自动启动工作。

### 场景2：用例编写时发现设计遗漏，触发 debug

1. 用户执行 `tc_do` 编写用例时发现测试设计遗漏了一个边界场景。
2. 用户通过 Cursor 发送 `@tc_debug 设计未覆盖边界场景`。
3. `tc_debug_agent` 获取该用例关联的测试设计 ID，分析问题，生成 debug 记录写入用例的 `debug_records`，同时发送 `debug.recorded` 事件。
4. `trace_agent` 订阅事件，进一步分析：该问题是否应归属于测试设计环节？如果是，则在对应测试设计对象的 `debug_records` 中添加一条“下游反馈：设计遗漏边界场景”。
5. `rca_agent` 定期汇总，发现“测试设计遗漏”出现频率高，生成改进建议：在测试设计环节增加“边界场景检查表”。
6. `metrics_agent` 记录该逃逸事件，更新仪表盘。

### 场景3：缺陷回归发现的漏测被追溯

1. 缺陷回归 Agent（可独立于前三个环节）发现一个缺陷，该缺陷与用例 TC-123 相关。
2. 用户或 Agent 触发 `trace_agent`，传入缺陷信息和用例 ID。
3. `trace_agent` 分析：该用例设计时，其上游测试设计是否覆盖了该缺陷对应的场景？如果未覆盖，则在测试设计的 debug_records 中增加漏测记录。
4. 同时检查业务分析是否覆盖该场景，若也未覆盖，则在业务分析中增加记录。
5. 最终生成一个完整的漏测路径报告，并发布 `defect.traced` 事件。

## 五、在 Cursor 中的落地方式

Cursor 是一款 AI 驱动的代码编辑器，支持自定义指令、集成外部 API。我们可以利用 Cursor 的 **自定义命令（Custom Commands）** 和 **AI 上下文** 来嵌入这些 Agent。

### 5.1 技术选型建议

- **Agent 框架**：使用 **LangChain** 或 **AutoGen** 搭建 Agent 网络，每个 Agent 作为独立进程或函数，通过消息队列通信。
- **消息队列**：Redis（轻量级）或 RabbitMQ。
- **存储**：PostgreSQL（结构化数据）+ **Chroma/Qdrant**（向量存储，用于内容相似度匹配）。
- **Cursor 集成**：通过 Cursor 的 **自定义命令** 调用外部 API（如 Flask/FastAPI 服务），将 Agent 能力暴露给用户。

### 5.2 Cursor 自定义命令示例

在 Cursor 的 `settings.json` 中配置自定义命令：

```json
{
  "customCommands": [
    {
      "name": "ba_do",
      "command": "curl -X POST http://localhost:8000/agents/ba_do -d '{\"prompt\": \"{{input}}\"}'"
    },
    {
      "name": "ba_review",
      "command": "curl -X POST http://localhost:8000/agents/ba_review -d '{\"doc_id\": \"{{input}}\"}'"
    },
    ...
  ]
}
```

用户在 Cursor 中通过 `@ba_do 分析用户登录需求` 即可触发。

### 5.3 Agent 服务设计

使用 FastAPI 编写 Agent 服务，每个 Agent 暴露 REST 接口，内部通过 Redis 发布事件。

例如 `ba_do_agent` 的 API：

```python
@app.post("/agents/ba_do")
async def ba_do(prompt: str, user_id: str):
    # 1. 调用 LLM（可复用 Cursor 的 AI 或自建）生成分析初稿
    content = await llm.generate(prompt)
    # 2. 存储到数据库
    doc_id = save_business_analysis(content, status="draft")
    # 3. 发布事件
    redis.publish("events", json.dumps({"type": "ba.draft.created", "doc_id": doc_id}))
    return {"doc_id": doc_id}
```

其他 Agent 通过订阅 Redis 频道来触发。

### 5.4 利用 Cursor 的 AI 上下文

Cursor 的 AI 可以读取当前打开的文件内容，我们可以利用这一点让用户直接在编辑器中完成工作：

- 用户新建一个 `business_analysis.md` 文件，输入一些要点。
- 然后使用自定义命令 `@ba_review`，Cursor 会将当前文件内容作为输入传给 Agent，Agent 返回评审意见，插入到文件末尾或生成新文件。

这样用户无需离开编辑器即可完成所有环节。

## 六、实施步骤与关键要点

### 6.1 实施步骤

1. **搭建基础设施**：部署 PostgreSQL、Redis、向量数据库，建立 Agent 框架基础。
2. **实现核心 Agent（do/review/merge/debug）**：先实现业务分析环节的四个 Agent，跑通一个环节的完整流程。
3. **增加质量门禁 Agent**：为业务分析环节定义准出条件，实现自动检查。
4. **扩展到测试设计和用例编写**：复制模式，但注意调整准出条件和 debug 关联。
5. **实现 trace_agent 和 rca_agent**：建立端到端追溯和根因分析能力。
6. **集成到 Cursor**：编写自定义命令，将 Agent API 暴露给用户。
7. **建立度量仪表盘**：开发简单 Web 页面展示 metrics_agent 收集的数据。
8. **迭代优化**：根据实际使用反馈，调整准出标准、根因分类、AI 提示词。

### 6.2 关键要点

- **数据一致性**：所有产出物必须关联上下游 ID，以便追溯。使用数据库外键或图数据库存储关系。
- **事件幂等性**：Agent 可能重复收到事件，需要设计去重机制（如记录已处理事件 ID）。
- **人机协作**：Agent 自动完成大部分工作，但关键决策（如评审驳回）仍需人工确认。Agent 应生成清晰理由。
- **逐步增强**：初期可以只实现 do 和 review，merge 和 debug 先用人工方式，逐步自动化。
- **安全与权限**：确保只有授权用户可调用 Agent 修改产出物。

## 七、总结

通过将你原有的“环节内闭环”扩展为 **多 Agent 协同闭环**，我们不仅保留了 `do/review/merge/debug` 的清晰结构，还补足了跨环节协同、准入准出、端到端追溯、根因分析和度量等关键能力。在 Cursor 中，借助自定义命令和 AI 上下文，用户可以在熟悉的编辑器中无缝使用这些 Agent，实现测试工作的工程化、智能化。

这个方案是模块化、可逐步实施的，你可以先从业务分析环节的四个 Agent 开始，验证效果后再逐步扩展，最终形成一个完整的测试工程化平台。
