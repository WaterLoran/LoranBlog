# 规格驱动开发简介

规格驱动开发（Specification-Driven Development，简称 SDD）是一种**先定义规格、再编写实现**的软件开发方法。它的核心思想是：把“要做什么”（规格）和“怎么做”（实现）彻底分离，并将规格作为贯穿设计、编码、测试、文档的唯一事实来源。

### 1. 核心理念
在 SDD 中，任何功能在动手编码前，都必须产出一份**精确、可验证的规格说明书**。这份规格不是模糊的需求文档，而是用形式化或半形式化语言描述出来的技术约定，例如接口签名、数据模型、前置/后置条件、状态转换、异常行为等。规格一旦通过评审，所有后续工作——前后端开发、测试用例编写、文档生成——都必须严格对齐这份规格。

### 2. 典型的 SDD 流程
1. **需求分析**：理清业务目标与用户场景。
2. **编写规格**：产出高精度的规格说明书，这一步经常借助特定语言/工具（如 OpenAPI、GraphQL Schema、Protobuf、AsyncAPI 甚至形式化语言如 TLA+）。
3. **评审规格**：各方（开发、测试、产品）对规格达成共识并锁定。
4. **基于规格生成框架**：自动生成接口桩代码、Mock Server、测试套件骨架、API 文档等。
5. **实现与验证**：按规格编写业务逻辑，并通过基于规格的自动化测试验证是否符合约定。
6. **持续同步**：当需求变更时，**先改规格，再改实现**，始终保持规格与代码一致。

### 3. SDD 的主要表现形态
在实际项目中，SDD 并不是某个单一工具的代名词，它更多是一种范式，最常见的实践包括：
- **API-First / Design-First**：用 OpenAPI (Swagger) 先定义 REST 接口，再生成服务端/客户端代码和文档。
- **Contract-First 服务开发**：在微服务中先通过 Protobuf 或 GraphQL SDL 定义通信契约，各团队据此并行开发。
- **声明式基础设施**：如 Kubernetes YAML、Terraform 脚本，其实就是期望状态的规格，工具负责驱动实际资源向规格靠拢。
- **形式化规格**：在安全攸关系统（航空航天、医疗、金融）中，用数学语言精确描述系统行为，再通过定理证明或模型检验来确保实现完全吻合。

### 4. 优点
- **减少歧义和返工**：规格在早期将模糊的期望变得可验证，问题发现越早修复成本越低。
- **促成并行开发**：前后端、不同服务团队拿到同一份规格后，可以同时启动工作，用 Mock 和契约测试来联调。
- **自动化程度高**：文档、测试用例、甚至部分代码都可以从规格自动生成，降低手动同步出错的可能。
- **提升质量与合规性**：在强监管行业，具备完整、可审计的规格与实现一一对应，是合规的必要条件。

### 5. 挑战与局限
- **编写规格有成本**：写一份精确无误的规格，本身就需要专业的设计能力和领域知识，相当于“把难题提前了”。
- **需求变化会触动规格**：如果频繁变更，维护规格本身也会带来开销，需要团队有很强的纪律性。
- **易出现“规格僵化”**：过分追求完美规格可能造成前期分析瘫痪，或者后面发现规格不合理时受限于已生成的周边产物难以灵活调整。
- **不适合纯探索性开发**：在需求极不确定的原型或试错阶段，SDD 的重文档特质可能会拖慢速度。

### 6. SDD 与 TDD、BDD 的区别
很多开发者会混淆这几个概念，可以这样理解它们的关系：
- **TDD（测试驱动开发）**：先用测试用例约束代码的行为，测试是微观层面的“规格”，由开发者编写，侧重内部实现正确性。
- **BDD（行为驱动开发）**：用自然语言（如 Gherkin）描述业务场景，是面向业务人员、可读性更强的规格，侧重端到端行为验证。
- **SDD（规格驱动开发）**：规格的抽象层次可高可低，但通常更偏向架构、接口、数据契约的技术描述，并强调通过工具链从规格中衍生出其他制品（代码、测试、文档），本质上是一种 **“契约优先”** 的工程实践。BDD 和 API-First 都可以看作是 SDD 在不同层面的具体实现。

### 7. 适用场景
SDD 尤其适合以下项目：
- **跨团队协作**（如微服务、前后端分离），需要一份稳定的接口契约；
- **对外公开 API 的产品**，文档质量直接影响集成体验；
- **合规性要求高**的系统，需要可追溯、可审计的设计与实现对应关系；
- **长周期维护**的大型系统，完善的规格能降低人员变动带来的理解成本。

一句话总结：**SDD 让“写代码之前先写清楚合同”成为一种可执行、可自动化的工程纪律，它通过规格这一中枢，把设计、编码、测试、文档串联成一条无缝的流水线。**
