# 对外交付API的要求

对外交付的 API，和内部系统间调用的 API 有本质区别：你的用户不再是可控的内部团队，而是外部开发者、合作伙伴甚至未知的调用方。因此，很多对内“可容忍”的做法，对外会变成灾难。

以下是面向对外交付的 API 的优秀实践，重点关注那些**对外接口独有或要求更严苛**的地方。

---

### 1. 契约优先与设计先行

对内接口有时是“先写代码再补文档”，但对外交付必须反过来。

- **设计即承诺**：API 一旦发布，就是你和用户之间的契约。任何改动都相当于“毁约”。
- **优先定义 OpenAPI / Swagger 文件**：先产出标准的 API 描述文件，再据此进行前后端开发和 Mock。这能保证文档与实现永远一致。
- **从用户视角设计**：接口的路径、参数、响应字段都要符合调用方的直觉，而不是直接暴露底层数据库模型或服务内部结构。对外交付的 API 需要一个精心设计的“外观层”，屏蔽内部实现的变更。

### 2. 坚如磐石的版本管理与兼容性策略

对内可以用 `v1`、`v2` 共存短暂过渡，然后强制升级。对外却行不通：你无法控制所有用户的升级节奏。

- **必须要有版本策略**：常见方式是将版本号放在 URL 中（如 `/v1/`）或通过请求头指定。URL 版本化更直观，被广泛采用。
- **铁律：只增不减，不改含义**  
  在一个已发布的版本内，**绝不能**出现破坏性变更（Breaking Change）。这意味着：
  - 不能删除或重命名字段。
  - 不能把字段类型从整数改成字符串。
  - 不能缩小取值范围（如原来返回 1-100，现在只返回 1-10）。
  - 不能为已有字段强加新的必填约束。
- **新旧版本长期共存**：你需要同时维护多个活跃版本，并提供清晰的弃用时间表（如提前 6-12 个月邮件/公告通知），到期后才能关闭旧版本。

### 3. 身份认证、授权与安全（对外要求指数级提升）

内部 API 可能在可信网络内使用简单的密钥，对外则完全不同。

- **放弃 Basic Auth 和简单 API Key**：对外主流的标准是 **OAuth 2.0**（特别是 Authorization Code 流程给第三方应用，Client Credentials 给服务器间调用）。搭配短期有效的 Access Token 和长期 Refresh Token。
- **坚持 HTTPS 且开启 HSTS**：这是底线，无例外。
- **最小权限原则**：严格区分 API 的访问范围。提供不同的 `scopes` 供调用方申请，避免一个令牌通吃所有数据。
- **面向外部威胁的防护**：
  - **速率限制**（Rate Limiting）：按用户、应用、IP 等多维度限流，防止滥用和攻击。
  - **输入校验**：对外接口是公共攻击面，必须假设所有输入都是恶意的，严格校验大小、格式、范围，防范注入攻击。
  - **敏感数据遮蔽**：即使出错，也不能在日志或错误信息中泄露密码、Token、用户隐私数据。
- **避免暴露内部细节**：HTTP 响应头中，去除 `Server: ...`、`X-Powered-By: ...` 等指纹信息。错误响应中不暴露堆栈轨迹和数据库表名。

### 4. 精细化的流量控制与商业化计量

这是对外 API 独有的商业属性。

- **按需设定配额（Quota）**：除了保护性的速率限制，还需要商业配额，如“每月免费 1 万次调用，超出后付费或不可用”。配额用完时，返回清晰的状态码 `429 Too Many Requests`。
- **提供用量仪表盘**：让用户能实时看到自己的调用量、剩余配额，减少客服工单。
- **标准化的速率限制头**：在响应中返回 `X-RateLimit-Limit`、`X-RateLimit-Remaining`、`X-RateLimit-Reset`，让调用方可以优雅地自控速率。

### 5. 错误处理：像对待文档一样重视

内部接口的错误信息可能很随意，对外必须标准化、可操作。

- **充分利用 HTTP 状态码**：`200`、`201`、`400`、`401`、`403`、`404`、`409`、`429`、`500` 要语义准确地使用。即使是业务错误，也应在 `4xx` 状态下返回详细信息。
- **统一错误体结构**：推荐遵循 **RFC 7807 (Problem Details)**，返回 `type`、`title`、`status`、`detail` 等字段。你的错误响应应该包含：
  - **人类可读的描述**。
  - **唯一的错误码**（如 `INVALID_PHONE_NUMBER`），方便调用方程序化处理。
  - **哪个参数出问题了**（如 `field: "user.phone"`）。
  - **指向文档的链接**，帮助用户自己解决问题。
- **错误是开发者体验的一部分**：一个好的错误信息能显著降低对接成本，减少对你的打扰。

### 6. 文档与开发者体验是第一门面

“交付一个接口”对外意味着要交付一整套可以独立上手的产品。

- **交互式文档门户**：仅有一份静态 Specification 不够，你需要提供像 Swagger UI、Redocly 或自定义门户，让用户可以直接在文档里填入 Token 并点击“Try it”来调用测试。
- **从入门到精通的指南**：必须包含：
  - 5 分钟快速开始（获取密钥、发出第一个请求）。
  - 认证方式详解。
  - 每个端点的完整请求/响应示例。
  - 错误码列表和处理建议。
  - 常见使用场景的端到端教程。
- **多语言 SDK 与示例代码**：至少提供几种主流语言（如 Python, JavaScript, Java）的 SDK 或代码片段，降低集成门槛。
- **变更日志与公告渠道**：任何变更都必须记录在公开的 Changelog 中，并建立邮件列表或 RSS 通知用户。

### 7. 沙箱环境与可测试性

对内你可能在测试环境联调，对外则需要一个专属的、隔离的游乐场。

- **独立的沙箱（Sandbox）环境**：URL 与生产环境明确区分（如 `sandbox.api.example.com`）。沙箱不产生真实影响，不产生费用。
- **数据隔离与重置**：沙箱内的数据可以随时清理或重置，保证每个新用户都能在干净环境下体验。
- **预置的 Mock 与样例**：提供一些固定的请求能返回可预期的结果，方便用户测试错误场景和边界情况，无需他们自己去构造复杂的前置条件。

### 8. 可观测性与主动监控（向 SLA 负责）

对外 API 往往附带服务等级协议（SLA），这要求你比监控内部系统更主动。

- **从调用方视角监控**：建立主动拨测，模拟用户的关键业务流程，而不只是监控服务器 CPU。
- **关键指标与仪表盘**：实时追踪整体可用性、平均/ P95/ P99 延迟、错误率、限流拒绝数，并分用户、分接口查看。
- **设定并公开 SLA/SLO**：如“月可用性 99.9%”。你需要弄清楚达不到标准时如何补偿（通常是赠送调用额度）。
- **状态页公开透明**：出现故障时，第一时间在外部状态页（status.example.com）更新进展，而不是让用户疯狂@你。

### 9. 生命周期管理与下线流程

你无法随意关掉一个对外 API。

- **弃用计划（Deprecation）**：
  - 在响应头中加入 `Sunset` 字段（RFC 8594），或在响应体里包含 `Deprecation: true` 并注明建议替代版本。
  - 提前足够长时间（如 9-12 个月）通过邮件、站内信、文档公告等多渠道通知。
- **渐进式强制下线**：到期前可能先降低速率限制，再返回警告头，最后再硬关闭，逼迫存量的用户迁移。

### 10. 法律与商业合规

对外交付意味着正式的商业关系。

- **服务条款与隐私政策**：API 门户必须有清晰的法律条款，明确允许和禁止的用途。
- **数据驻留与合规**：若面向全球或特定行业，需考虑 GDPR、CCPA 等要求，并提供数据删除、导出接口。
- **合作伙伴与自注册分离**：不同等级的调用方可能有不同的接口集合、限频和价格，需要在认证体系中能区分。

---

### 总结：对外接口独有的视角转换

对内接口，你是“为自己和同事写代码”；对外接口，你是“**为开发者用户做产品**”。因此，所有实践都围绕：

- **信任**：通过稳定的契约、审慎的变更、透明的状态来建立。
- **自服务**：让用户不问你就能通过文档、沙箱、清晰的错误信息自己完成集成。
- **防御性**：假设调用方会犯错，假设有恶意的调用，假设自己的服务随时会出故障。

把每一个对外 API 都当作一个独立的产品来打磨，这是最根本的转变。
