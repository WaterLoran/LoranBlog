# 根据API文档生成测试用例及脚本的踩坑思考



**问题背景**:感觉拿一份API文档给AI去生成用例的时候, 感觉效果不好, 就看不到明确的测试点, 他似乎, 就值聚焦于用什么数据组合去测试, 然后期望会得出具体的哪一些数据. 就看不到具体的测试点和目的



从第一性原理出发，我们先把问题拆回到最不可再分的基本事实，再逐步推演，这样能看清问题的根源。

---

### 1. 三个基本对象的本质是什么？

**① API 文档的本质**
API 文档是一份**结构化的规格说明书**。它描述的是系统“是什么”——有哪些接口、接受什么参数、参数是什么类型、是否必填、会返回哪些状态码和字段。但它**天然不包含**以下信息：
- 这个接口在真实业务中承担什么角色（业务风险点）
- 参数之间隐含的约束和因果关系（如 `type=A` 时 `value` 必须为正，`type=B` 时可为负）
- 哪些地方最容易出错、最需要重点测试（经验性风险）

一句话：**文档给出了“语法”，但几乎没给“语义”和“风险”。**

**② 测试用例的本质**
一个完整的测试用例，最核心的不可再分单元不是“输入数据 + 预期数据”，而是：  
**在特定上下文下，为了验证某个明确的风险/需求，构造一个可控的断言。**
它必须包含三个层次：
- **测试点 / 测试目的**：我要验证什么假设？（例如：验证当金额参数传入负数时，系统能拒绝并给出明确错误码）
- **测试设计思路**：为什么选这些数据？用的是什么方法？（等价类、边界值、状态机、错误推测……）
- **具体数据和预期**：输入什么组合，期望得到什么输出。

如果把测试点/目的抽掉，只剩下数据组合，那就退化成一个**不包含验证意图的数据堆砌**，它无法回答：“这个用例失败了，到底是缺陷还是我预期写错了？” 也无法指导覆盖的完整度。

**③ 大语言模型（AI）生成文本的本质**
大模型本质是一个**基于统计的序列预测器**。它并不“理解”测试，只是根据训练语料中见过的模式，计算最可能跟随在提示词后面的 token 序列。
当它收到一份 API 文档并要求“生成测试用例”时，它所见过的相关语料大多是：
- 自动化测试脚本（Postman 的 collection、参数化测试的 JSON/CSV）
- 教程中“接口测试100例”这类表格
- 大量只罗列输入输出的简单用例模板

这些语料中，**数据组合占绝对比重，测试目的往往被弱化甚至缺失**（很多实战用例只把目的写在用例标题，甚至标题也只是“正常用例/异常用例”）。模型学到的模式就是：  
`看到 API 描述 → 枚举参数取值 → 列出请求体和预期响应体`  
这正是你观察到的“只聚焦于用什么数据组合，然后期望得出具体数据”。

---

### 2. 为什么会出现“看不到测试点”的现象？（根因推导）

从第一性原理推出的矛盾点：

**① 信息不对称：文档不包含测试目的，AI 也不主动创造目的**
文档只有参数列表和格式约束。测试点是要从业务风险、设计经验、隐式约束中提取的。人类测试人员看到 `price` 字段，会联想到“负价格、超大金额、0元、精度溢出、并发减库存”等，这是基于领域知识和风险意识。AI 没有真实的业务经历，没有“损失金钱”的概念，它只能从参数类型推算形式化的边界值（如 int 类型给出 max/min），**它无法内生“测试目的”，只能模仿数据变体**。

**② 训练数据的“有数据无目的”模式被复现**
互联网上大量测试用例生成示例，特别是面向初学者的内容，常以“参数组合覆盖”作为最佳实践（正交表、Pairwise 等），强调的是数据而非测试点。模型最高概率的输出模式就是：**把参数当因子，把取值当水平，排列组合后给预期**。结果就是你看到的“为组合而组合”，缺乏“为什么要选这一组”的解释。

**③ 生成过程缺乏“断言设计”环节**
测试用例的核心是**断言**——明确“预期是什么，以及为什么是它”。而模型在生成时，多数情况是直接拼接预期 JSON，没有显式地要求它先说出验证的假设。这就像一个学生只抄了练习册后面的答案，却没写解题思路。

**④ 看不到测试目的，其实是缺失了测试策略层**
测试用例存在一个层级关系：
- 测试策略 → 测试点 → 测试用例（数据+步骤）
API 文档只提供最底层的信息，AI 被直接要求生成最底层产物，中间关键的“测试点识别”环节被跳过了，自然就看不到。

---

### 3. 如何从根源上改善？（回归第一性原理的解决思路）

既然本质矛盾在于“文档只有语法，而用例需要风险/目的”，且 AI 不会自发补全这一层，那解决方向只有两个：**要么在输入中补全信息，要么在生成流程中强制插入推理环节。**

#### 思路一：在输入侧补全“测试动机”
不要让 AI 只面对裸 API 文档。把下列内容前置给它：
- 接口的业务用途简述（例如“这是用户下单时扣减库存的接口”）
- 风险点清单（“库存不能为负；并发可能导致超卖；金额精度为两位小数”）
- 必须覆盖的测试维度清单（功能正确、参数必填/选填校验、边界值、异常码、幂等性、安全等）
当你把“测试动机”注入后，生成的用例自然就会带上测试点的描述。

#### 思路二：改变生成流程，显式要求“先输出测试点”
利用提示词工程，强制分阶段生成：
```
步骤1：请基于以下 API 文档，列出所有你识别到的测试点。每个测试点需包含：
- 测试目的（要验证什么风险/需求）
- 测试设计方法（等价类/边界值/异常场景等）
步骤2：根据上述测试点，为每个测试点生成具体的请求数据和预期结果。
```
这样就把隐含的推理链条显性化了，你就能看到明确的测试点和目的，数据只是作为附属物出现。

#### 思路三：提供 few-shot 示例，校准输出形态
给 AI 看你心目中“好用例”的样子（包含测试点字段的模板），比如：
```
测试点ID: TC_01
测试目的：验证库存扣减成功时返回正确的剩余库存，且状态码为200
前置条件：商品库存=10
测试数据：{ "skuId": "A001", "quantity": 3 }
预期结果：HTTP 200, body: { "remainingStock": 7 }
```
模型会紧贴示例模式，把测试目的作为必填字段生成。

---

### 最终结论
从第一性原理看，**API 文档是形式化的语法描述，不携带测试目的；大模型是统计模仿者，倾向于复现训练语料中“重数据、轻目的”的用例模式；而测试用例的本质是以目的为核心的风险验证断言。** 当这三个本质直接碰撞，必然产出“只有数据组合却看不清测试点”的结果。

解法不是责备模型，而是**将缺失的“测试意图”作为额外信息注入，或通过流程设计强迫模型先将隐含的测试点显式推理出来**。这样，你才能得到有灵魂的、能直接看出验证目标的测试用例。
