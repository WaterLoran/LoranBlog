# 棋牌游戏和传统web系统的接口自动化差异

这是一个非常专业且切入要害的问题。棋牌游戏本质上也是一种软件，其接口（特别是HTTP短连接部分，如登录、充值、创建房间）与传统的Web软件（如电商、OA系统）的自动化方案**底层工具链是通用的**（如Postman/Newman、JMeter、Rest-Assured、Pytest等）。

但核心差异在于**业务特性、通信协议、状态机复杂度和数据一致性的要求**。以下是具体的五大核心差别：

### 1. 通信协议的多样性（最根本的差异）
-   **传统Web软件**：几乎**纯HTTP/HTTPS**（RESTful或GraphQL）。自动化测试只需处理请求-响应模式，工具成熟（如Requests库）。
-   **棋牌游戏**：**混合协议**。为了实时性，核心玩法（发牌、出牌、结算）通常采用**WebSocket、TCP长连接**或**UDP**（极少）。HTTP仅用于非对战类接口。
    -   **自动化难点**：测试脚本必须同时处理HTTP（短连接）和WebSocket（长连接）的交互。例如：HTTP发起“加入房间”后，需要维持WebSocket监听“发牌”事件，并断言收到的二进制/JSON数据是否正确。工具链更复杂（需引入WebSocket客户端库）。

### 2. 状态机与业务时序的复杂性
-   **传统Web软件**：大多是**无状态**或**弱状态**（如用户登录→下单→支付），状态迁移路径线性，超时机制宽松（如购物车30分钟失效）。
-   **棋牌游戏**：**强状态机**。一局牌有明确的生命周期：`等待` → `下注` → `发牌` → `叫牌/弃牌` → `比牌` → `结算`。
    -   **自动化难点**：
        -   **时序依赖**：必须在“下注”阶段断言“发牌”接口不可调用。状态跳转错误（如跳过弃牌直接结算）必须被自动化捕获。
        -   **超时处理**：每个状态有严格倒计时（如15秒内必须出牌）。自动化脚本需要模拟“等待”和“超时触发”，并校验超时后的托管或自动弃牌逻辑。
        -   **回合制协调**：自动化需要同时控制多个客户端（玩家A、玩家B），严格按照“A动作 → 等待B动作 → 校验B不能动 → 校验状态更新”的顺序执行。

### 3. 随机性与可重复性的矛盾
-   **传统Web软件**：结果**确定**。输入`商品A+数量2`，输出永远是`总价200`。自动化用例可以硬编码断言。
-   **棋牌游戏**：核心逻辑依赖**随机洗牌**和**概率**（如老虎机、麻将摸牌）。
    -   **自动化难点**：
        -   **断言不可硬编码**：不能写死“玩家A第一张牌是红桃5”。需要使用**算法式断言**，例如：
            -   总牌数正确（共54张）。
            -   各家牌型符合组合逻辑（顺子、刻子数量≥1）。
            -   牌值范围合法（1-10，JQKA）。
        -   **概率测试**：需要大量重复运行（如10000次），通过统计学分析验证抽奖/发牌概率是否偏离设计值（如“豹子”出现概率为1/221），这对自动化框架的批量运行和数据采集能力要求更高。

### 4. 并发与数据一致性的极端要求
-   **传统Web软件**：并发场景相对简单（如秒杀、抢购）。常用锁或事务保证数据一致。
-   **棋牌游戏**：**极高并发下的精确结算**。例如100张桌同时进行德州扑克，每张桌有6名玩家同时All-in，需要计算复杂的底池分配。
    -   **自动化难点**：
        -   **断线重连与状态恢复**：需要模拟玩家中途断开WebSocket，重新连接后断言客户端收到的“历史动作重放”或“当前牌局状态快照”与服务器记录完全一致。
        -   **资金安全**：自动化必须覆盖“同时结算”场景，校验筹码/金币的转入转出在数据库事务中绝对原子。例如：A赢B输，检查A增加100币的同时，B是否精确扣除100币（无浮点精度丢失）。
        -   **防作弊校验**：需要构造并发请求（如同一张牌桌，两个玩家同时抢庄或同时出牌），验证服务器是否通过分布式锁或队列拒绝后一个非法请求，而不会出现状态错乱。

### 5. 安全性测试的侧重点不同
-   **传统Web软件**：关注SQL注入、XSS、CSRF、越权、敏感数据泄露。
-   **棋牌游戏**：额外关注**外挂与协议攻击**：
    -   **重放攻击**：捕获一个“出牌”的WebSocket包，自动化脚本重放100次，校验服务器是否拒绝（因为状态已变）。
    -   **篡改请求**：修改包中的“牌值”字段（如将`card_id=3`改为`card_id=King`），校验服务器是否忽略客户端上传的牌值（正确的设计是服务器端计算牌值，客户端只传动作）。
    -   **速度攻击**：自动化脚本在0.1秒内发送20次“摸牌”请求，检查服务器是否只响应第一次有效请求。

### 技术方案总结对比表

| 维度           | 传统Web软件            | 棋牌游戏                                   |
| :------------- | :--------------------- | :----------------------------------------- |
| **协议栈**     | HTTP/HTTPS (同步)      | HTTP + WebSocket / TCP (异步)              |
| **断言方式**   | 预期值对比 (确定性)    | 状态合法性检查 + 概率统计                  |
| **状态管理**   | 线性、宽松超时         | 严格状态机、回合制、倒计时                 |
| **并发复杂度** | 用户级 (秒杀、下单)    | 牌桌级 (多角色、原子结算)                  |
| **自动化工具** | Postman, JMeter (HTTP) | Locust + WebSocket插件, 自研多客户端模拟器 |
| **典型用例**   | 登录、搜索、下单流程   | 完整牌局流程、断线重连、概率分布、防重放   |

### 实践建议
如果你的团队需要实施棋牌游戏接口自动化：

1.  **分层测试**：将HTTP管理接口（登录、充值）与WebSocket玩法接口分离测试。后者建议使用**长连接压力测试框架**（如基于Netty自研模拟器）。
2.  **引入确定性随机种子**：在测试环境，使用固定的随机数种子（如`Random(42)`）控制洗牌算法，使“随机”变得可预测，方便编写确定性断言。生产环境则使用真随机。
3.  **优先覆盖“异常场景”**：对于棋牌游戏，**断线重连、超时托管、并发抢庄**的优先级远高于正常流程（因为正常流程QA手动测试容易覆盖，但并发时序Bug极难手工测出）。
4.  **使用事件驱动模型**：编写自动化脚本时，不要使用线性`sleep`，而应基于状态变化事件（如WebSocket收到`action_timeout`事件）来驱动下一步操作，以应对网络延迟波动。
