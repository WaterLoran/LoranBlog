# AIPOM设计范式

AIPom”指的是结合AI能力与经典Page Object Model（POM）设计模式，生成的页面对象模型。这种协同模式并非取代POM，而是让AI与POM各自发挥所长：**AI负责高效生成，POM负责长期维护，两者结合是目前AI驱动UI自动化测试中的最佳实践之一**。

结合业内工具和落地方案，一个高质量的AIPom格式设计主要从**元素、操作、导航**三个核心模块展开：

### 🏛️ 核心一：元素（PageElement）—— 页面的"身份证"
这是AIPom的基石，关键在于**稳定且可维护**。

*   **唯一标识符**：为每个UI元素分配一个清晰的逻辑ID，最好与设计稿的命名规范保持一致。
*   **定位策略**：不仅限于CSS、XPath等选择器，还可扩展到AI动态识别，**支持“多策略回退”机制**，即当首选定位器失效时，能自动尝试备用定位方式。
*   **交互事件**：建议根据元素类型标记其支持的交互行为，如`clickable`、`input`，帮助AI理解其意图。

### 🎮 核心二：操作（Action）—— 测试的"台词本"
这部分定义页面允许执行的交互，要求**语义清晰且执行健壮**。

*   **语义化API**：方法名应直接反映其业务操作，如`LoginPage.loginAsAdmin()`，而不是底层的`click()`。
*   **执行前自检**：在操作前，页面对象应主动校验所依赖的元素是否可见或可用，使用智能等待确保DOM已就绪。
*   **智能重试**：对于“弹窗消失”、“动画结束”等常见状态，AI或框架应具备自动等待和重试的能力。
*   **返回结果**：操作成功后，应返回后续的页面对象或状态码，用于在测试用例中流式地构建测试流程。

### 🗺️ 核心三：导航（Navigation）—— 场景的"剧本"
这部分负责管理页面间的跳转逻辑，目标是**让AI能理解用户场景**。

*   **状态流转路径**：为AI提供一个描述页面跳转关系的有序列表，例如 `[登录页 -> 商品详情页 -> 加购页]`，这实际上是场景的“剧本”。
*   **上下文感知**：导航过程应能感知当前页面，并智能决定是跳转还是通过页面内操作完成任务。
*   **参数化跳转**：支持通过URL参数等方式动态生成目标链接，处理带查询参数或动态ID的页面。

---

### 💡 附加设计：让AI更懂你的"潜规则"
*   **关键元数据**：在AIPom模型中包含页面路径（`url`）、功能描述、所覆盖业务场景等描述性数据。
*   **Page Object的层级结构**：应支持嵌套，以清晰表达页面内组件（如卡片、对话框）的复杂层级关系。

### 🤝 协作落地：“AI生成+POM封装”模式
结合AI的强大生成能力和POM的稳定架构，能实现“效率与质量双赢”：

1. **AI生成初稿**：AI基于需求文档或页面截图，快速生成基础的元素定位和操作代码。
2. **人工封装优化**：测试工程师将AI生成的代码，封装为遵循**单一职责**（一个PO只负责一个页面）和**抽象性**（屏蔽内部细节）原则的POM类，构建稳定的对象库。
3. **智能维护更新**：当UI变更时，可借助AI的动态元素识别能力，半自动地更新POM中的定位器，而非手动重写。

### 🧪 数据格式示例：以JSON/YAML为例
一个AIPom可以用JSON或YAML格式清晰结构化，下面是登录页的示例：
```json
{
  "pageName": "LoginPage",
  "description": "登录页面，包含用户名和密码输入框以及登录按钮",
  "url": "/login",
  "elements": [
    { "logicalName": "username_input", "locators": ["id=user_login", "css=#username"] },
    { "logicalName": "password_input", "locators": ["id=user_pass", "css=#password"] },
    { "logicalName": "login_button", "locators": ["id=wp-submit", "xpath=//button[@type='submit']"] }
  ],
  "actions": [
    { "name": "loginAsAdmin", "steps": ["username_input.fill('admin')", "password_input.fill('admin123')", "login_button.click()"], "expectedResult": "跳转至欢迎页或仪表盘" }
  ],
  "navigation": [
    { "toPage": "DashboardPage", "triggerAction": "login_button.click()" }
  ]
}
```
> 💡 你也可以参考如 `page-object-mcp` 项目的数据模型，或在应用初期采用更简单的键值对Map。

### ✍️ 实操：用Prompt驱动AIPom生成
为了更规范地生成AIPom，你可以使用类似下面的Prompt：

> "你是一名资深测试开发工程师。请为`[你的被测页面名称]`页面生成基于AI的页面对象模型（AIPom）。
>
> **要求**：
> 1.  **分离关注点**：将页面元素定位器（`locators`）与业务操作（`actions`）分开定义。
> 2.  **业务语义化**：为关键业务流程创建一个语义清晰的操作，如`doLogin(...)`、`addItemToCart(...)`。
> 3.  **结构输出**：以JSON格式输出，包含 `pageName`、`elements`、`actions`、`navigation` 等字段。
> 4.  **为AI优化**：为`actions`字段添加`description`属性，简短描述该方法的目的，以便AI在后期编排复杂测试场景时能理解并调用。"

如果需要更具体的指导，可以参考一些**结构化Prompt的模板**，也可以尝试类似`page-object-mcp`的MCP服务器，它能为AI提供标准化的对象管理接口。

### ⚠️ 避坑指南：避免常见“反模式”
在设计时，注意避开以下“雷区”：
*   **不要混入断言**：PO的职责是封装操作，不应该将`assert`语句放在页面对象的方法中，验证工作应交给测试用例。
*   **不要使用隐式等待**：建议在PO层封装显式等待逻辑，以提高脚本健壮性。
*   **不要过度设计**：对于一次性或临时的测试脚本，直接用AI生成代码即可，封装POM反而会牺牲效率。
