# 群组协作的智能机协作方式

如果说“图工作流”是严格按照乐谱演奏的交响乐团，那 **“群组协作”（Swarm）** 就是一个**自我管理、即兴配合的爵士乐队**[reference:0]。每个乐手都有自己的专长，他们无需指挥，通过彼此倾听和配合，共同完成一首作品。

### 🧠 核心理念：从“指挥”到“自我组织”

*   **无中心控制**：没有中央调度器，智能体自主决定下一步行动[reference:1]。
*   **自主协作**：通过内置工具，智能体可以在最合适的时候将任务移交给最合适的队友[reference:2]。
*   **共享上下文**：所有智能体共享一个“工作记忆”，能看到完整任务和所有历史讨论[reference:3]。
*   **动态任务分配**：任务分配不是预先计划的，而是由智能体根据实时情况动态决定[reference:4]。
*   **群体智能涌现**：通过协作，团队能解决单个复杂智能体难以处理的难题[reference:5]。

### 🏗️ 架构基石

*   **`Swarm`类**：群组协作的核心，负责协调内部所有智能体[reference:6]。
*   **`SwarmNode`**：封装`Agent`实例，为群组管理提供节点ID、状态等特性[reference:7]。
*   **`SharedContext`（共享上下文）**：提供一个JSON可序列化的共享内存，是所有智能体的“公共笔记本”[reference:8]。
*   **`Handoff Tool`**：内置的交接工具，智能体用它来控制权移交给另一个智能体[reference:9]。

### ⚙️ 安全参数与执行控制

为防止无限循环，`Swarm`类提供了一系列安全参数：

| 参数                                   | 描述                                | 默认值 |
| :------------------------------------- | :---------------------------------- | :----- |
| `max_handoffs`                         | 最大交接次数                        | 20     |
| `max_iterations`                       | 最大迭代次数                        | 20     |
| `execution_timeout`                    | 总执行超时时间（秒）                | 900.0  |
| `node_timeout`                         | 单个节点执行超时时间（秒）          | 300.0  |
| `repetitive_handoff_detection_window`  | 检测“乒乓效应”的窗口大小（0为禁用） | 0      |
| `repetitive_handoff_min_unique_agents` | 触发检测的最小不同节点数            | 0      |

### 💻 从0到1：构建一个智能体团队

这是一个完整的示例，展示了如何构建一个能进行“头脑风暴”的群组：

```python
# 1. 导入必要的模块
from strands import Agent
from strands.multiagent import Swarm

# 2. 创建具有不同专业角色的智能体
researcher = Agent(
    name="researcher",
    system_prompt="你是一名研究员。你的职责是收集事实、数据和关键信息。完成后，请将你的发现传递给策略师进行下一步规划。"
)

strategist = Agent(
    name="strategist",
    system_prompt="你是一名策略师。你的职责是基于研究员提供的信息，分析并提出核心策略或行动方案。完成后，将你的计划传递给撰稿人。"
)

writer = Agent(
    name="writer",
    system_prompt="你是一名撰稿人。你的职责是基于策略师的计划，撰写一份清晰、有说服力的报告。"
)

# 3. 组建团队（Swarm）
# 智能体列表的顺序决定了执行顺序，但每个智能体也可自主决定是否以及何时移交
development_swarm = Swarm([researcher, strategist, writer])

# 4. 下达一个复杂的任务
task = "我们计划进入智能家居市场，请研究市场现状并提出初步的三年市场进入策略，最后撰写一份执行摘要。"

# 5. 执行任务，见证团队的自主协作！
result = development_swarm.run(task)

# 6. 输出最终结果
print(result)
```

### 🛡️ 在关键环节引入“人工确认”

群组协作支持**人在回路**机制，能在关键环节暂停并等待人工确认，避免危险操作[reference:10]。

```python
from strands import Agent
from strands.multiagent import Swarm
from strands.hooks import HookProvider
from strands.experimental.hooks.multiagent import BeforeNodeCallEvent

# 1. 定义一个“批准”钩子
class ApprovalHook(HookProvider):
    def register_hooks(self, registry):
        registry.add_callback(BeforeNodeCallEvent, self.approve)

    def approve(self, event):
        # 当特定节点（例如 "deployer" 部署者）执行前，触发中断并请求人工批准
        if event.node_id == "deployer":
            response = event.interrupt("approval", reason="部署操作需要人工批准，是否继续？")
            if response != "APPROVE":
                event.cancel_node = True  # 取消节点执行

# 2. 将钩子注入群组
deployer_agent = Agent(name="deployer", system_prompt="...") # 这是一个负责部署的智能体
swarm = Swarm([researcher, strategist, deployer_agent], hooks=[ApprovalHook()])

# 3. 执行任务并处理中断
result = swarm.run("请研究并执行生产环境部署。")
while result.status == "INTERRUPTED":
    for interrupt in result.interrupts:
        user_input = input(f"{interrupt.reason}: ")
        # 将用户的批准结果作为响应返回给群组，使其继续执行
        result = swarm.resume([{"interruptResponse": {"interruptId": interrupt.id, "response": user_input}}])
```

### 📊 模式对比：Graph vs Swarm vs Workflow

| 特性         | Graph                                             | Swarm                                              | Workflow                                                 |
| :----------- | :------------------------------------------------ | :------------------------------------------------- | :------------------------------------------------------- |
| **执行流**   | 受控动态：遵循预定边，但LLM决定路径[reference:11] | **自主顺序**：智能体自主决定执行路径[reference:12] | **确定性并行**：流程固定，独立任务并行执行[reference:13] |
| **结构**     | 开发者定义所有节点和边[reference:14]              | 开发者提供智能体池，路径由它们决定[reference:15]   | 开发者定义任务及其依赖[reference:16]                     |
| **状态共享** | 共享状态对象，所有智能体可读写[reference:17]      | 共享上下文，包含原始请求、任务历史等[reference:18] | 自动传递任务输出作为后续任务的输入[reference:19]         |
| **历史记录** | 完整对话记录[reference:20]                        | 共享交接记录和知识贡献[reference:21]               | 仅任务特定输入输出[reference:22]                         |

### 📌 适用场景与注意事项

**何时使用**
*   需要多角度分析的复杂研究[reference:23]。
*   需要不同领域专家协作，如软件开发或内容创作[reference:24]。
*   需集体智慧的应用，如创意构思、战略规划等。

**注意事项与局限**
*   **会话持久化不支持**：Swarm目前**不支持**会话持久化，状态会在执行结束后丢失[reference:25]。
*   **代理回调不支持**：Swarm内部**不支持**为每个Agent单独设置回调，只能在Swarm级别设置钩子[reference:26]。
*   **智能体数量**：建议智能体数量保持在**3-7个**，过多会导致协调成本上升[reference:27]。
*   **避免重复实例**：不要将同一个Agent实例重复放入Swarm，会导致状态管理冲突[reference:28]。
*   **任务描述清晰**：任务描述应**明确具体**，有助于智能体更好地理解和分工[reference:29]。

### 💎 总结

总的来说，如果问题需要**明确的步骤**（如月度报告自动化），Graph模式是更好的选择。但如果问题开放性很强，需要不同领域的专家一起“碰撞”出解决方案（如制定市场策略），Swarm模式会更适合。你可以在一个更大的系统中组合使用它们，例如让一个图工作流的某个节点，就是一个处理复杂子任务的Swarm[reference:30]。
