# 不同可测试性程度Agent的测试方法

你的判断大体对：**线上很多 Agent 交付确实是「模型 + 编排 + 业务系统」糊在一起**，不一定给你一份可重置的 JSON 假库。测试不一定要像本仓库那样「深入到每一个环节」，而是 **在你能拿到的接口与风险之间选策略**；能拆出可测性最好，不能拆也有办法，只是 **信号强弱和成本** 不同。

下面按 **「你对系统可见到什么程度」** 总结常见测法，并回答「是否总要建设可测试性」。

---

## 1. 只有对外 API（黑盒 / 灰盒）

**特征**：只暴露 HTTP/gRPC，例如「发一段 user message，拿回 assistant message + 可能 structured fields」；你看不到 DB、看不到工具列表。

**可以怎么做**

- **端到端场景测试**：用固定 **fixture 用户/订单**（在对方 staging 里造好），通过 API 跑脚本化多轮对话，断言 **最终业务结果**（再调对方只读查询 API、或人工抽检、或异步 job 完成后 webhook）。
- **契约 / 回归**：对 **响应 schema、错误码、幂等、超时** 做自动化；对「业务结果」用 **允许模糊** 的断言（子串、结构化 JSON 字段存在）。
- **LLM-as-Judge**：在拿不到 ground-truth DB 时，用 **rubric + Judge** 评「是否完成用户目标、是否合规」；成本高、要校准偏差。
- **影子 / 回放**：若对方提供 **日志 ID** 或事后 **trace**，用生产脱敏对话 **回放** 到测试环境做 diff（仍是黑盒，但比纯 API 多信息）。

**局限**：很难做你们项目这种 **确定性状态 hash**；**无法证明**「内部一定没写错表」，只能证明 **对外可观测行为** 合理。

---

## 2. 能拿到 trace / 工具日志，但没有独立数据层（灰盒）

**特征**：有云厂商 trace、Langfuse、OpenTelemetry、或「每次调用记录了 tool name + args」。

**可以怎么做**

- **轨迹测试**：比对 **工具名序列**、参数 JSON（可做规范化后比）、与 **golden 轨迹** 的 subset / unordered 匹配（你们 `eval_langsmith` 那类思路）。
- **关键副作用抽查**：例如每次 run 后调用 **内部只读 API**「查订单状态」；仍依赖对方是否暴露。

这里 **不必** 把 DB 文件拆出来，但 **需要可观测性**（至少日志）。

---

## 3. 能注入 / 重置状态，或能在测试侧 mock 依赖（浅白盒）

**特征**：不能在源码里拆模块，但可以在 **集成测试环境** 里：测试专用 DB、容器每次清空、或 mock 支付/物流。

**可以怎么做**

- **与生产同构、数据隔离**：每个用例 **seed 数据 → 调 Agent API → 查 DB/API 断言**；等价于你们现在的 `load_data()`，只是状态在对方服务里而不是 JSON 文件。
- **状态一致性**：若最终状态可 **通过 API 拉全量或 hash**，仍可做到 **确定性判分**；否则退回 **关键字段断言**。

---

## 4. 白盒：源码/配置可改，或交付时就分层（强可测性）

**特征**：像本仓库：**工具读写明确 state**、**任务带 golden actions**、**可重放**。

**可以怎么做**

- **Golden replay + hash**（你们 `state_eval`）、**轨迹 + Judge**、**单元测工具函数** 全开。
- 这是 **可测试性最好** 的形态，适合 **基准 / 回归 / CI**。

---

## 5. 「是否总要建设可测试性？」

- **不必须** 都做到本仓库这种深度才能测：**黑盒 E2E + 契约 +（可选）Judge** 在业界很常见**，尤其对外只提供 API 时**。
- **但若你要**：高置信 **回归**、**防数据写错**、**低成本海量跑批**、**可复现 bug**，就需要在交付或架构上 **逐步买可测性**：
  - **最低成本**：结构化日志 + trace id + 测试环境数据隔离。  
  - **中等**：只读查询 API、关键写操作的 **idempotency key**、staging 与 fixture。  
  - **最高**：领域层与 LLM 编排分离、工具副作用集中、**可重置 world**（或事件溯源重放）。

所以：**测试方法随「可见性 + 可控性」变化**；**「将就黑盒 API」是常态**；**「深入各环节」是理想增量**，不是二选一，而是 **从外向内演进**。

---

## 6. 一张对照表（便于你选型）

| 可见性               | 典型手段                   | 优点                     | 代价/风险                 |
| -------------------- | -------------------------- | ------------------------ | ------------------------- |
| 仅 API               | E2E 脚本、契约、Judge      | 贴近真实、易对接交付形态 | 脆弱、难确定性、flake     |
| + Trace/工具日志     | 轨迹匹配、违规检测         | 比纯文本强、可部分自动化 | 依赖埋点质量、schema 稳定 |
| + 测试环境可重置状态 | 状态/API 断言、部分 replay | 接近确定性               | 需要环境与数据治理        |
| 白盒分层 + mock DB   | hash/replay/单测工具       | 强回归、可解释           | 交付/改造成本             |

**结论句**：**只提供 API 时，就以 E2E + 契约 +（必要时）Judge 为主**；**要工程级确定性，就要逐步加可观测性与可重置状态**——不是「理解错误」，而是 **测试深度与系统可测性做交易**；本仓库代表的是 **可测性拉满** 的一种参考实现，不是唯一合法形态。
