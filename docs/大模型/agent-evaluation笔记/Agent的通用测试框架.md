# Agent的通用测试框架

下面把你们这类 **「售后 / 客服智能体 + 可复现评测」** 抽象成**通用框架应包含什么**、**怎么组织**，既对应你们当前仓库，也便于以后换业务时照结构拆模块。

---

## 1. 这种测试框架一般要包含哪些东西

可以想成 **五层 + 一条数据流**。

### （1）世界模型（Mock Backend）

- **结构化假数据**：用户、订单、商品、支付等（JSON / SQLite 均可）。
- **清晰 ID 与状态机**：如 `pending` / `delivered`、**`product_id` vs `item_id`**。
- **可重置**：每次任务从 **干净初始状态** 开始，便于 hash 或快照对比。

没有这一层，工具调用和「是否办对」都无法客观判。

### （2）工具层（Agent API / 业务能力）

- 每个售后动作一个 **原子工具**：查单、改地址、取消、退换货等。
- **统一签名**（你们这里是 Strands 的 `tool_use + agent`），且通过 **`agent.state` 或等价上下文** 读写世界，避免全局变量污染并行评测。

这是「智能体能干什么」的可执行契约。

### （3）智能体运行时（Agent Runtime）

- **系统提示（政策）**：身份核验、写库前要确认、能/不能做什么（你们的 `wiki.md`）。
- **模型路由**：不同厂商 API、温度、重试（你们的 `run.py` + `llm_providers`）。
- **对话 + 工具循环**：可由框架库实现（Strands）或自研 ReAct。

这是「谁在做决策、怎么调工具」。

### （4）任务与基准（Benchmark / Tasks）

- **任务定义**：顾客目标（只给用户模拟器看）、**golden 工具序列**（定义标准终态）、可选 **必须出现在回复里的片段**（`outputs`）。
- **任务集划分**：train / dev / test，便于防泄漏和回归。

这是「考什么题、标准答案是什么粒度」。

### （5）环境与判分（Simulator + Judge）

- **用户模拟**：规则或 LLM 扮演顾客，按剧本多轮对话（你们的 `env_litellm`）。
- **终止条件**：如 `###STOP###`、转人工等。
- **判分**：
  - **状态一致性**（终态 DB / hash，允许多条路径）；
  - 可选 **输出约束**（关键词/子串）；
  - 可选 **轨迹 / LLM Judge**（放在离线层也可以）。

这是「怎么交互、怎么算过」。

### （6）离线评估与实验（可选但工程上很有价值）

- **结果落盘**：JSON（trajectory、reward、metadata）。
- **公共抽取层**：把原始日志变成 **`EvalDataPoint`** 一类统一结构（你们的 `eval_common/extract_results`）。
- **多框架 / 多指标**：MLflow、LangSmith、DeepEval 等只做 **「阅卷方式」**，不替代运行时。

这是「同一批跑批结果，多种分析视角与可追溯」。

## 2. 如何组织这样一个框架（推荐目录/职责划分）

用「依赖方向」组织：**外层依赖内层，内层不知道外层**。

```text
data/              # 世界 + schema 说明
tools/             # 对世界只读/写的原子操作（与 policy 一致）
wiki.md 或 policies/   # 智能体系统提示（与合规一致）

tasks/ 或 引用外部 benchmark 包   # Task 定义（instruction / golden / outputs）

runtime/
  run_*.py         # 组装 model + agent + load_data + 循环入口
  env_*.py         # 用户模拟、与 agent 的 IO、何时结束、第一层判分

eval_common/       # 从 results 抽标准结构 + 状态 replay/hash（与框架无关的「数学」）
eval_<vendor>/     # 各产品线的 adapter（只依赖 eval_common + results）
results/           # 产物
```

**组织原则（便于维护和换模型/换阅卷）**：

1. **数据与工具放一起演进**：改 schema 就改 `data/` + `tools/`，别让 prompt 里写死和 JSON 不一致的字段。
2. **政策（wiki）与工具能力对齐**：工具 `TOOL_SPEC` 里要求的确认、枚举值，应在 policy 里再写一遍，减少模型「以为可以」但工具拒绝。
3. **任务与运行时解耦**：`Task` 只描述「考什么」；`Env` 只负责「怎么演对话 + 何时算分」；不要在 `tasks` 里写死 API Key。
4. **运行时判分 vs 离线判分分工**：运行时给 **便宜、确定** 的主信号（如状态 hash）；LLM Judge、轨迹匹配放 **离线**，避免每次跑批都贵且难复现。
5. **统一 `EvalDataPoint`**：所有下游评估只认一种结构，换阅卷框架不改主流程。

## 3. 和你们当前仓库的对应关系（方便你对照记忆）

| 通用块                 | 你们仓库里大致在哪                                  |
| ---------------------- | --------------------------------------------------- |
| 世界                   | `data/` + `load_data()`                             |
| 工具                   | `tools/`                                            |
| 政策                   | 根目录 `wiki.md`                                    |
| 任务                   | `tau_bench/.../tasks_*.py` + `types.py`             |
| 运行时 + 环境判分      | `run.py`、`env_litellm.py`                          |
| 统一抽取 + 状态 replay | `eval_common/`                                      |
| 多框架阅卷             | `eval_mlflow/`、`eval_langsmith/`、`eval_deepeval/` |
| 产物                   | `results/*.json`                                    |

---

## 4. 一句话总结

要对 **售后类智能体** 做可扩展测试，框架一般要包含：**假后端 + 工具 API + Agent 运行时与政策 + 任务基准 + 对话环境与判分 +（可选）结果落盘与多框架离线评估**；组织上按 **数据/工具 → 政策 → 任务 → 环境 → 评估** 分层，让 **「世界怎么变」** 和 **「对话怎么转」** 和 **「分怎么算」** 可独立替换、独立版本化。
