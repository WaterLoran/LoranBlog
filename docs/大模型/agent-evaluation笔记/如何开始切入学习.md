# 如何开始切入学习

## 这套测试在测什么（原理）

可以把它想成：在一个假的电商客服后台里，让一个 LLM 客服通过工具帮「模拟顾客」办事，最后看世界有没有被改对。

每条 Task（见 `tau_bench/types.py`）大致有三块：

1. `instruction`：只给 用户模拟器 看的剧本（顾客是谁、要什么、脾气怎样）。客服智能体看不到这段（和真实场景一致：顾客不会一次性把需求文档念完）。
2. `actions`：标注员认为的标准答案——一串「工具名 + 参数」。不强制智能体按同样顺序调用，而是用来 重放 到一份干净的数据库上，得到 golden 最终状态。
3. `outputs`（可选）：要求客服在 自然语言回复 里必须出现某些信息（例如答案 `"10"`），用子串匹配检查。

**判分（reward）**在 `env_litellm.py` 的 `calculate_reward` 里：

- 把智能体跑完后 `agent.state["datas"]`（JSON 模拟库）算一个 hash。
- 用 `eval_common/state_eval.py` 的 `replay_actions`：在全新数据副本上按 `task.actions` 顺序执行同一套工具（跳过 `transfer_to_human_agents` 等终止类工具），再算 golden hash。
- 两个 hash 一致 → 认为「世界状态」对了，这是 tau-bench 风格里很核心的 状态一致性 指标；若 `outputs` 非空，还要检查智能体历史回复里是否包含规定片段。

所以：测试任务的本质 = 隐藏目标（instruction）+ 可验证的终态（actions 重放）+ 可选的口头交付物（outputs）。

------

## 一次 `main.py` 跑起来时发生了什么（过程）

建议你在心里按时间顺序跟这条链：

1. `main.py`：解析参数 → `RunConfig` → 调 `run.py` 的 `run(config)`。

2. `run.py`：读 `wiki.md` 作为客服系统提示词；选模型（如 Moonshot）；为每个 task id 建 `strands.Agent` + `tools/`；`agent.state["datas"] = load_data()`。

3. `env_litellm.Env`：`reset` 选中 `tasks[task_id]`；用 `instruction` 拼用户系统提示，用户侧用 LiteLLM（如 Kimi）生成第一句顾客话。

4. `loop()`

   （多轮）：

   - 用户说一句话 → `agent(user_input)`（Strands 内部会模型 + 工具循环）→ 得到客服回复（可能已改库）；
   - 再把客服回复塞回用户对话历史 → LLM 生成下一句用户话；
   - 直到用户输出 `###STOP###` 或触发转人工等结束条件。

5. 结束时 `calculate_reward`：hash 对比 + `outputs` 检查 → reward 0 或 1（及 `info`）。

6. 结果写入 `results/*.json`，供 MLflow / LangSmith / DeepEval 等再做轨迹评估。

你要学会的「测试过程」，就是上面这条 任务定义 → 双 LLM 对话 → 工具改状态 → 与 golden 重放对比 的闭环。

## 应该从哪里开始学（推荐顺序）

下面按「读代码量小 → 建立全局 → 深入机制」排，都在本仓库内即可完成。

1. `README.md` + `EVALUATION_GUIDE.md`
   建立词汇表：tau-bench、retail、Strands、三框架评估各自干什么。
2. `tau_bench/types.py` 里的 `Task` / `Action`
   一眼看懂一条任务由哪些字段组成（上面三块）。
3. 打开 `tau_bench/envs/retail/tasks_test.py` 里前 1～2 条 `Task(...)`
   对照 `instruction` 和 `actions`，想：顾客想要什么、标准答案工具链在改什么数据。
4. `data/readme.md` + `data/__init__.py`（或 `load_data`）
   明白 `datas` 是什么结构（订单、用户、商品），后面看工具才有落点。
5. 选一个简单工具，例如 `tools/get_order_details.py`
   看 `ToolUse` / `Agent` / `agent.state` 怎么读写，这是「智能体怎么改变世界」的最小例子。
6. `env_litellm.py`：重点 `loop` 和 `calculate_reward`
   这是整条测试管道的「心脏」：对话怎么转、何时算分。
7. `eval_common/state_eval.py`（`replay_actions`、`MockAgent`）
   理解 为什么不用轨迹逐格比对，而是用「重放 golden actions」得到标准终态。
8. 最后再回到 `run.py`
   把 Agent 创建、`wiki.md`、结果路径串起来，你就从入口到出口都通了。

若你还想学 跑完 JSON 之后 三个评估框架怎么用同一批结果，再读 `eval_common/extract_results.py` 和各自的 `eval_*/run_eval.py`。

------

## 小结一句

学这套测试，核心不是背命令，而是理解：`Task` 如何把「顾客意图」和「可验证的终态」拆开，以及 `Env.loop` 如何用双 LLM 对话 + 工具执行把前者变成后者，最后用状态 hash（和可选 `outputs`）做客观判分。
从 `types.py` 的 `Task` → `tasks_test.py` 一条样例 → `env_litellm.py` 的 `loop` + `calculate_reward` 这条线读下去，效率最高。
