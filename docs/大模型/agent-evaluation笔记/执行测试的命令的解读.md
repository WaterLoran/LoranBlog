

# agent-evaluation中执行测试的命令的解读

```bash
# 单条任务测试（Kimi）
uv run python main.py \
  --agent-strategy tool-calling \
  --env retail \
  --model kimi-k2-0905-preview \
  --model-provider moonshot \
  --user-model kimi-k2-0905-preview \
  --user-model-provider moonshot \
  --user-strategy llm \
  --task-ids 0 \
  --max-concurrency 1

```



这条命令是在 用 uv 跑一条零售客服基准任务：启动 `main.py`，在 tau-bench 的 retail 任务集里只跑 task id = 0，用 Kimi（Moonshot） 同时驱动 客服智能体 和 模拟用户，对话结束后按 数据库状态是否与 golden 一致（以及可选的 output 匹配）打出 reward，并把轨迹与结果写到 `results/` 下的 JSON。

逐项说明参数含义和实际发生的事：

## `uv run python main.py`

在项目依赖环境里执行 `main.py`：解析命令行得到 `RunConfig`，再调用项目根目录的 `run.py` 里的 `run(config)`（不是 tau-bench 原版里那套 `ToolCallingAgent` 工厂）。

## `--env retail`

限定为零售场景；`run.py` 会从 `tau_bench.envs.retail.tasks_*` 加载任务（默认 `--task-split` 是 `test`，所以一般是 `tasks_test`）。

## `--model kimi-k2-0905-preview` 与 `--model-provider moonshot`

给 Strands `Agent` 用的后端模型：走 Moonshot 的 OpenAI 兼容接口（需环境变量里的 `MOONSHOT_API_KEY` / `KIMI_API_KEY` 等，见 `eval_common/llm_providers.py`）。`run.py` 里会构造 `LiteLLMModel` 接到 Kimi。

## `--user-model` / `--user-model-provider moonshot`

用户模拟器（在 `env_litellm.py` 里用 LiteLLM 调 LLM）也用同一套 Kimi，根据任务说明生成「顾客」的一行行回复，和客服智能体多轮对话。

## `--user-strategy llm`

在 原版 tau-bench 里会区分用户是规则模拟还是 LLM 模拟。在当前仓库的 `run.py` / `env_litellm.py` 里，用户侧 始终是 LiteLLM 调模型；该参数会进入 `RunConfig`，并出现在 结果文件名 里，但 不会 在 `env_litellm.py` 里再切换成另一套用户逻辑。

## `--agent-strategy tool-calling`

在 原版 tau-bench 里表示「原生 tool calling」类智能体。本仓库里被测体固定是 `strands.Agent` + `tools/` 工具；该参数同样主要反映在 输出 JSON 的文件名 上（`run.py` 里 `ckpt_path` 含 `agent_strategy`），而不是再去选 `tau_bench/agents/tool_calling_agent.py`。

## `--task-ids 0`

只跑 第 0 号 测试任务（`idxs = [0]`），不做整段 `start_index`～`end_index` 区间。

## `--max-concurrency 1`

含义是「最多并行多少任务」；`main.py` 会把该值写进 `RunConfig`，但 `run.py` 当前是用 `for idx in idxs` 顺序执行，没有按 `max_concurrency` 做进程池并行。因此这里写 `1` 与默认行为一致，属于 预留/与文档对齐 的写法，对当前实现几乎无影响。

------

整体流程简述：读 `wiki.md` 作为客服系统提示词 → 为任务 0 建 `Env` → 用户模型先开口 → 循环里客服 `Agent` 回复并可能调工具改 `agent.state["datas"]` → 用户模型再回复，直到 `###STOP###` 或转人工等结束条件 → `calculate_reward` 里对比数据 hash（及 `outputs`）→ 打印是否成功并把结果写入 `results/` 下的 JSON。
