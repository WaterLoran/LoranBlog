# 具体的task解读

下面用 **`TASKS_TEST` 里第 1 条（task id 0）** 做主例子，**第 2 条（task id 1）** 用一句话对比「同一顾客同一单，标准答案为何不同」。

---

## 例子一：`TASKS_TEST[0]`（task id 0）

### `instruction`：顾客想要什么（用户模拟器看的剧本）

原文核心是：

- 你是 **Yusuf Rossi**，邮编 **19122**。
- 已收到货的单 **#W2378156**。
- 想 **换货**（exchange）：
  - **机械键盘** → 要类似款，但开关要 **clicky**；
  - **智能温控器** → 要 **兼容 Google Home**，不要只支持 Apple HomeKit 那种。
- 若找不到「clicky + RGB 背光 + 全尺寸」的键盘，则退而求其次：**可以接受不要背光**。
- 性格：**一次把事情办利索**，细节要对。

注意：这里全是 **自然语言需求**，没有直接告诉客服「请调用 `exchange_delivered_order_items`，参数写这些 ID」。智能体要靠对话 + 查库 + 查商品 + 推理，最后自己调工具。

### `actions`：标准答案在「工具世界」里干了什么

这是一条 **有顺序的参考工具链**，判分时会在干净数据库上 **重放** 得到 golden 状态。逐步对应顾客意图：

| 顺序 | 工具                             | `kwargs` 在干什么              | 和顾客意图的关系                                             |
| ---- | -------------------------------- | ------------------------------ | ------------------------------------------------------------ |
| 1    | `find_user_id_by_name_zip`       | 名 Yusuf、姓 Rossi、邮编 19122 | 先 **确认身份**，拿到系统里的 `user_id`（剧本里是姓名+邮编，不是直接背 user_id）。 |
| 2    | `get_order_details`              | `order_id`: `#W2378156`        | 打开这单，看 **行项目、商品、状态**（是否已送达、当前 SKU、line item id 等），换货前必查。 |
| 3    | `get_product_details`            | `product_id`: `1656367028`     | 查 **某一侧商品** 的规格（多半对应当前键盘或候选款），用来核对 clicky / 背光 / 尺寸等。 |
| 4    | `get_product_details`            | `product_id`: `4896585277`     | 查 **另一商品**（多半是温控器或另一候选），核对 Google Home 等。 |
| 5    | `exchange_delivered_order_items` | 见下表                         | **真正改数据库**：在已送达订单上把指定行换成新 SKU，并指定付款方式。 |

`exchange_delivered_order_items` 这一笔在标准答案里是：

- **`order_id`**：`#W2378156`（就是顾客说的那单）。
- **`item_ids`**：`1151293680`、`4983901480` —— 订单里 **要被换掉的两个行项目**（对应键盘 + 温控器两条线）。
- **`new_item_ids`**：`7706410293`、`7747408585` —— 换成的 **两个新商品 SKU**（标注员认为满足「clicky 键盘 + Google Home 温控器」的配对）。
- **`payment_method_id`**：`credit_card_9513926` —— 换货可能涉及差价，用该用户的这张卡处理。

`outputs=[]`：这道题 **不要求** 客服在自然语言里必须出现某个固定子串（例如某个数字）；通过与否主要看 **最终 `datas` 的 hash** 是否与 golden 一致。

**一句话总结这条 Task**：顾客要用自然语言完成「一单里两件货的换规格」；标准答案工具链是 **先身份 → 再订单 → 再两件商品详情 → 最后一次性 exchange 改订单行与商品引用**。

## 例子二：`TASKS_TEST[1]`（task id 1）——和例子一同场不同卷

### `instruction` 和 task 0 差在哪？

前面几乎一样，但 **键盘缺货时的策略**不同：

- Task 0：**没有理想键盘**时 → 可以接受 **不要背光** 的折中，仍尽量换键盘 + 温控器。
- Task 1：**没有理想键盘**时 → **只换温控器**，键盘就不换了。

所以 **顾客口头目标** 在「缺货时的分支」上不一致。

### `actions` 差在哪？（为何标准答案不同）

Task 1 的 `exchange_delivered_order_items` 只有 **一行旧货、一行新货**：

- `item_ids`: `["4983901480"]` —— 只动 **一件**（从标注看是温控器那条线，不动键盘那条 `1151293680`）。
- `new_item_ids`: `["7747408585"]` —— 只换成 **一个新 SKU**。

前面 `find_user` / `get_order` / 两个 `get_product_details` 和 task 0 **相同**：说明标注员认为 **探查过程** 仍要同样查清楚；但最终 **写库** 的 exchange 只反映「只换温控器」这一分支。

这正好帮你理解 **`instruction` 差几个字 → `actions` 里最后一步改库范围可以完全不同**；评估时重放的是 **这一条 Task 自带的 golden**，不是「所有合理做法」的并集。

## 读题时你可以在心里问的三个问题

1. **`instruction` 里顾客的最终业务结果是什么？**（本题：换货；分支：两件都换 vs 只换一件。）
2. **`actions` 前几步是不是在「定位人、单、货」？**（`find_*` / `get_order` / `get_product` 典型是读库 + 推理依据。）
3. **最后一步 `exchange_*` / `return_*` / `modify_*` 真正改了哪些 id？**（对应 `orders` / `users` 里哪些行，和 hash 判分直接相关。）

若你想把数字和真实商品名对上，下一步可在 `data/products.json` / `data/orders.json` 里搜这些 `product_id`、`order_id` 或行项目 id，那是「数据层」对照，上面已是「任务层」对照解读。
