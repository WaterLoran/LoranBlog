# 知识库使用场景

### 角色一：新入职员工 / 实习生（目标：快速上手，少问蠢问题）

- **场景1：入职前3天的“名词扫盲”**
  - **痛点**：开会时大家狂飙“SPU”、“SKU”、“锁库”、“正向单”，完全听不懂。
  - **他怎么用**：直接打开 **第一章《术语与词典》** ，Ctrl+F 搜索听不懂的词。不看代码，不看流程，只看定义和举例。
- **场景2：理解“一整套业务全貌”**
  - **痛点**：Leader只扔给你一个接口文档，你完全不知道这接口在整个系统里处于什么位置。
  - **他怎么用**：看 **第三章《核心业务流程》** 的时序图/状态机图，先搞懂“从下单到签收”到底分几步，再去看细节。

---

### 角色二：产品经理 / 业务架构师（目标：设计新需求，避免逻辑冲突）

- **场景3：设计新促销活动时，校验“规则冲突”**
  - **痛点**：运营说要搞“全场9折”且“可与优惠券叠加”，你忘了之前系统有限制。
  - **他怎么用**：查阅 **第四章《业务规则》** 中的 `R-ORDER-001`（优惠券与满减互斥）。发现互斥规则后，他会找运营确认：“新活动要打破旧规则吗？”并更新规则文档，然后提需求给开发。
- **场景4：评估“修改发货逻辑”的影响面**
  - **痛点**：想修改“拆单规则”（从按仓库拆改为按店铺拆），不知道会影响哪些地方。
  - **他怎么用**：查看 **第七章《关系导航》** 的反向索引。他看到“拆单规则”关联了“数据字典”中的 `parent_order_id`，关联了“流程”中的支付回调，还关联了“权限”中的客服改地址权限。他会拉上所有关联方开会评估。

---

### 角色三：后端/前端开发工程师（目标：写代码不踩坑，接口对接不出错）

- **场景5：编写“库存扣减”代码前的技术选型**
  - **痛点**：不知道该用数据库乐观锁还是Redis原子操作。
  - **他怎么用**：直接翻看 **第四章 `R-SKU-001`（超卖防御锁库）** ，里面写了“使用Redis原子递减”。再看 **第六章《非功能约束》** 中要求“TP99 < 150ms”，于是他果断放弃数据库悲观锁，采用Redis+Lua脚本。
- **场景6：对接“订单状态”枚举值**
  - **痛点**：前端问“已支付”的状态码是多少？支付成功后要跳转到哪个页面？
  - **他怎么用**：打开 **第二章《数据字典》** 的订单状态枚举，直接复制 `20-已支付`。不需要去翻几万行的老代码，知识库就是唯一的真相源（Single Source of Truth）。
- **场景7：排查线上“手机号显示乱码”问题**
  - **痛点**：测试报Bug说手机号没脱敏。
  - **他怎么用**：查阅 **第六章《非功能约束》** 中的安全合规条款，发现明确写着“存储加密，日志脱敏”。他会检查自己的日志切面，发现没加脱敏注解，立即修复。

---

### 角色四：测试 / QA 工程师（目标：覆盖全场景，不出生产事故）

- **场景8：撰写“下单流程”的测试用例**
  - **痛点**：怕漏测边界情况。
  - **他怎么用**：把 **第三章《流程》** + **第四章《规则》** + **第二章《状态机》** 拼在一起。
  - 他会设计出如下用例矩阵：
    1. 黑名单用户下单（测 R-USER-001）→ 预期阻断。
    2. 普通用户买库存为1的商品，并发下2单（测 R-SKU-001 超卖防御）→ 预期只有1单成功。
    3. 支付超时（测流程节点1的超时机制）→ 预期状态变 `11`，且锁库释放。
- **场景9：回归测试时，确认“权限改动”范围**
  - **痛点**：开发改了订单查询接口，不知道要测哪些角色。
  - **他怎么用**：看 **第五章《角色与权限矩阵》** 。发现客服有“代客修改地址”权限，运营没有，于是测试用例中会覆盖“客服登录修改”和“运营登录修改（预期403）”两条线。

---

### 角色五：客服 / 运营人员（目标：解决客户投诉，配置活动）

- **场景10：客户来电质问“为什么我不能用优惠券？”**
  - **痛点**：客户骂骂咧咧，客服不知如何解释底层逻辑。
  - **他怎么用**：客服在知识库搜索“优惠券”，命中 **`R-ORDER-001`** 规则。客服温柔地回复：“亲，系统自动为您选取了最大优惠方案，满减金额高于优惠券，所以为您自动使用了满减哦。”
- **场景11：运营配置“VIP免邮”活动**
  - **痛点**：运营想改免邮门槛，但不知道要不要写代码。
  - **他怎么用**：看 **第四章 `R-USER-002`（VIP免邮门槛）** 。发现规则逻辑是 `金牌 OR 总价>=99`，且写在知识库里。运营拿着这个规则去找产品经理：“改规则需要发版吗？还是后台配置？”——知识库帮他们识别了“硬编码规则”与“可配置规则”。

---

### 角色六：系统架构师 / 技术负责人（目标：技术选型与容量规划）

- **场景12：评估“大促秒杀”时系统会不会挂**
  - **痛点**：老板问服务器要不要扩容。
  - **他怎么用**：查阅 **第六章《非功能约束》** 中的性能指标（QPS 1w+）。结合 **第二章《数据字典》** 中订单表的字段长度和索引，估算单条写入耗时，再结合 **流程** 中的Redis锁库存步骤，推算出整体链路瓶颈在数据库写入，从而决定引入消息队列异步落库。
- **场景13：做“数据迁移/分库分表”方案**
  - **痛点**：订单表太大，要按年分表。
  - **他怎么用**：看 **第二章** 订单表结构，确认 `order_id` 生成规则包含“年月日”，且 **第六章** 规定“在线库仅留6个月”。他据此制定按 `order_id` 前缀进行分表迁移的策略。

### 附加高阶场景：所有人都会用的“变更影响面分析”（黄金场景）

- **场景14：当“支付回调逻辑”要改动时**
  - 架构师发出变更通知。所有人不是靠开会记忆，而是：
    - 开发查 **流程节点2**，确认改动点。
    - 测试查 **关联规则**（R-SKU-001库存扣减），补充并发测试。
    - 产品查 **权限矩阵**，确认支付回调不涉及权限。
    - 客服提前获知变更，准备话术（如支付成功通知文案变化）。
- **场景15：离职/转岗交接**
  - 老员工离职不用口口相传，直接把知识库链接扔给新人：“把第一章到第三章看完，我们下周开始接需求。”

---

### 总结：用户使用知识库的三种模式（深度分层）

| 使用深度     | 用户角色           | 典型动作                                                     |
| :----------- | :----------------- | :----------------------------------------------------------- |
| **浅层查阅** | 客服、新员工、运营 | 关键词搜索（术语/规则），只看文字定义。                      |
| **中层参照** | 产品、开发、测试   | 复制字段名/状态码，依据规则写代码/用例，依据流程画时序图。   |
| **深层联动** | 架构师、技术负责人 | 做变更影响分析，做技术选型，做容量评估，反向推导业务合理性。 |

**最后给你一个真诚的建议**：想让知识库被“用”起来，光有内容不够。你需要在知识库首页做一个 **“角色快速入口”** ：

- “我是新员工，我该看什么？”
- “我是开发，我要查字段/状态码。”
- “我是运营，我要查活动规则。”

并且，**一定要打通“业务术语”到“代码仓库/接口文档”的超链接**——当开发能直接从知识库跳转到Swagger接口定义时，他这辈子就离不开这个知识库了。
