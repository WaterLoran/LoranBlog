# 交付件示例：《电商交易域业务知识库（订单/用户/商品篇）》

## 第一章：术语与词典（统一语言）

> **说明**：此表用于对齐业务、产品、研发三方认知，禁止在文档中使用非表内缩写。

| 术语           | 英文缩写              | 定义                                                         | 关联实体    | 备注                     |
| :------------- | :-------------------- | :----------------------------------------------------------- | :---------- | :----------------------- |
| **SPU**        | Standard Product Unit | 标准化产品单元，商品信息聚合的最小单位（如：iPhone 15）      | 商品        | 不包含价格/颜色          |
| **SKU**        | Stock Keeping Unit    | 库存量单位，具体可售卖的最小单元（如：iPhone 15 黑色 128GB） | 商品 + 库存 | 价格、库存挂在此层级     |
| **C端用户**    | C-End User            | 在APP/小程序注册的普通买家                                   | 用户        | -                        |
| **黑名单用户** | Blacklist User        | 被风控标记的异常用户，下单受限                               | 用户        | 关联风控规则             |
| **正向订单**   | Forward Order         | 买家创建并支付成功的常规购买订单                             | 订单        | -                        |
| **逆向订单**   | Reverse Order         | 由正向订单触发的退款/退货单                                  | 订单 + 售后 | 必须关联父订单ID         |
| **锁库**       | Stock Locking         | 用户下单成功时，暂时冻结对应SKU库存的行为                    | 订单 + 商品 | 分"下单锁库"与"支付锁库" |
| **订单状态机** | Order State Machine   | 订单从创建到终态（完成/关闭）的流转路径定义                  | 订单        | -                        |

## 第二章：数据字典（核心实体定义）

> **说明**：此处仅展示核心字段，实际交付件需包含完整字段清单。

### 1. 实体关系总览 (ER图逻辑)
- `User` (1) ---- (n) `Order`
- `Order` (1) ---- (n) `Order_Item`
- `Order_Item` (1) ---- (1) `SKU`
- `SKU` (n) ---- (1) `SPU`

### 2. 核心表字段明细

**表：`user` (用户表)**

| 字段名       | 类型    | 必填 | 业务含义                          | 来源/规则                       |
| :----------- | :------ | :--- | :-------------------------------- | :------------------------------ |
| `user_id`    | bigint  | 是   | 用户唯一ID                        | 雪花算法生成                    |
| `user_level` | tinyint | 是   | 用户等级 (1-普通, 2-银牌, 3-金牌) | 根据年消费金额由T+1离线任务计算 |
| `phone`      | varchar | 是   | 手机号                            | **存储须加密（AES-256）**       |
| `is_black`   | tinyint | 否   | 是否黑名单                        | 默认0，风控系统回调标记为1      |

**表：`sku` (商品库存表)**

| 字段名            | 类型          | 必填 | 业务含义                   | 来源/规则                        |
| :---------------- | :------------ | :--- | :------------------------- | :------------------------------- |
| `sku_id`          | bigint        | 是   | 单品ID                     | -                                |
| `price`           | decimal(10,2) | 是   | 当前销售单价               | 单位：元；变更需运营审批         |
| `available_stock` | int           | 是   | **可用库存**（可售卖数量） | `总库存 - 订单锁库存 - 预占库存` |
| `lock_stock`      | int           | 是   | 已锁库存（下单未支付）     | 支付成功/超时取消时释放或扣减    |

**表：`order` (订单主表)**

| 字段名            | 类型          | 必填 | 业务含义     | 来源/规则                        |
| :---------------- | :------------ | :--- | :----------- | :------------------------------- |
| `order_id`        | bigint        | 是   | 订单号       | 规则：`年月日 + 机房ID + 序列号` |
| `parent_order_id` | bigint        | 否   | 父订单ID     | 用于拆单场景（多店铺/多仓库）    |
| `user_id`         | bigint        | 是   | 下单用户     | 外键关联 `user`                  |
| `order_status`    | tinyint       | 是   | **订单状态** | 见下方 **状态机枚举**            |
| `total_amount`    | decimal(10,2) | 是   | 商品总金额   | `Σ(购买数量 * 单价)`             |
| `discount_amount` | decimal(10,2) | 是   | 优惠总金额   | 含优惠券、满减、积分抵扣总和     |
| `pay_amount`      | decimal(10,2) | 是   | **实付金额** | `total_amount - discount_amount` |
| `pay_time`        | datetime      | 否   | 支付完成时间 | 触发库存扣减的时机标记           |

**订单状态枚举 (order_status)**:
`10-待支付` -> `20-已支付(待发货)` -> `30-已发货(待收货)` -> `40-已完成` (终态) <br>
`10-待支付` -> `11-已超时取消` (终态) <br>
`20-已支付` -> `21-用户申请退款` -> `22-退款中` -> `23-退款完成` (终态)

## 第三章：核心业务流程（状态机与节点）

**流程名称：用户下单支付主链路**

1. **节点1：提交订单（待支付）**
   - **输入**：用户ID、SKU ID、购买数量、收货地址
   - **系统动作**：
     - 校验SKU `available_stock` >= 购买数量。
     - **（触发业务规则）** 执行促销优惠计算。
     - **执行锁库**：将 `sku.lock_stock` += 购买数量。
     - 生成 `order` 记录，状态置为 `10-待支付`。
   - **超时机制**：若30分钟内未支付，定时任务将状态改为 `11-已超时取消`，并 **释放锁库**。

2. **节点2：支付回调（已支付）**
   - **输入**：支付平台回调的 `order_id` 和 `transaction_id`。
   - **系统动作**：
     - 更新 `pay_time` = now()，状态置为 `20-已支付`。
     - **永久扣减库存**：`sku.available_stock -= 购买数量`；`sku.lock_stock -= 购买数量`。
     - **（触发业务规则）** 计算用户积分，异步发放。

3. **节点3：发货履约（已发货）**
   - **操作角色**：运营/仓库系统。
   - **系统动作**：记录物流单号，状态置为 `30-已发货`。

## 第四章：业务规则引擎（决策核心）

> **写法规范**：每条规则需带上唯一编码，以便代码溯源（如 `R-ORDER-001`）。

| 规则编码        | 规则名称         | 所属实体  | 触发节点   | 核心逻辑（伪代码/自然语言）                                  | 异常处理                         |
| :-------------- | :--------------- | :-------- | :--------- | :----------------------------------------------------------- | :------------------------------- |
| **R-USER-001**  | 黑名单下单拦截   | 用户      | 提交订单前 | `IF user.is_black == 1 THEN 阻断流程`                        | 前端弹窗："账户异常，请联系客服" |
| **R-SKU-001**   | 超卖防御锁库     | 商品      | 提交订单中 | 使用Redis原子递减：<br>`if (redis.decr(available) < 0) { rollback; return 库存不足; }` | 回滚订单，提示"库存不足"         |
| **R-ORDER-001** | 优惠券与满减互斥 | 订单      | 金额计算时 | 同一订单下，**不可同时使用**店铺优惠券和跨店满减，系统自动选取优惠金额较大的方案。 | 计算完成自动应用                 |
| **R-USER-002**  | VIP免邮门槛      | 用户+订单 | 运费计算时 | `IF user.user_level >= 3 (金牌) OR order.total_amount >= 99 THEN 运费=0 ELSE 运费=6` | -                                |
| **R-ORDER-002** | 拆单规则         | 订单      | 提交订单后 | 购物车商品若属于**不同仓库**或**不同店铺**，系统自动将`order`拆分为多个子订单（`parent_order_id`指向原单）。 | 子订单独立支付                   |

## 第六章：非功能约束与合规（边界护栏）

| 类别           | 具体要求                                                     | 涉及对象            | 违反后果     |
| :------------- | :----------------------------------------------------------- | :------------------ | :----------- |
| **性能 (SLA)** | 提交订单接口 TP99 < 150ms；秒杀场景 QPS 支撑 1w+。           | 订单业务流程        | P0级故障     |
| **数据一致性** | 支付回调必须采用**分布式事务（TCC模式）**，确保支付成功则库存必扣，支付失败则锁库必释放。 | 支付节点 + 库存扣减 | 资损或超卖   |
| **安全合规**   | 用户手机号、身份证在日志中**脱敏打印**；传输全链路HTTPS/TLS 1.3。 | 用户数据字典        | 安全合规红线 |
| **数据留存**   | 已完成的订单数据，**仅保留在线库6个月**，超过6个月自动归档至冷存储（OSS）。 | 订单数据字典        | 数据库膨胀   |

## 第七章：交付件之间的关系联动（本库导航索引）

为了让使用者不迷路，我在文档末尾增加了**“反向索引”**。例如：

- **当你看到规则 `R-ORDER-001`（优惠互斥）**：
  - 去查 **数据字典**：看 `order.discount_amount` 是如何汇总的。
  - 去查 **流程**：该规则在“提交订单-金额计算”节点生效。
  - 去查 **权限**：只有运营经理能修改互斥配置。

- **当你看到字段 `sku.available_stock`（可用库存）**：
  - 它被 **规则** `R-SKU-001`（超卖防御）使用。
  - 它在 **流程** 的“提交订单”节点被修改。
  - 它的计算依赖 **非功能约束** 中的Redis缓存一致性。
