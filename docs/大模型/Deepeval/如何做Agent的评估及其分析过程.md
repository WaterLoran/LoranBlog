# 如何做Agent的评估及其分析过程

这是一个非常好的问题。选择哪些评估指标，本质上是将**业务目标**和**风险点**翻译成**可量化的测试项**。下面我为你提供一个系统性的分析框架，帮助你一步步确定需要评估什么。

---

## 智能体评估的决策框架（五步法）

### 第一步：明确智能体的类型与核心职责

不同智能体的“成败”定义完全不同。先回答三个问题：

| 问题                     | 示例回答                                                     | 决定了哪些评估维度             |
| :----------------------- | :----------------------------------------------------------- | :----------------------------- |
| **它做什么？**           | 客服机器人 / 数据分析师 / 代码助手 / 操作执行器（如发邮件、订票） | 工具使用、任务完成度、安全边界 |
| **它需要多轮对话吗？**   | 是，用户可能追问、修改意图                                   | 知识保留、角色遵循、对话完整性 |
| **它拥有哪些工具/API？** | 数据库查询、计算器、第三方API                                | 工具调用正确性、参数准确性     |

**输出**：初步圈定候选指标范围。例如：
- 客服机器人 → `RoleAdherence`, `ConversationRelevancy`, `TaskCompletion`
- 数据分析Agent → `ToolCorrectness`, `PlanAdherence`, `StepEfficiency`

---

### 第二步：识别关键失败模式（风险分析）

针对你的智能体，想象它最让人崩溃的几种失败方式。这是最重要的一步。

| 失败模式                                                 | 对应的评估指标                      |
| :------------------------------------------------------- | :---------------------------------- |
| 明明有工具却不用，硬编一个错误答案                       | `TaskCompletion`, `ToolCorrectness` |
| 用了工具，但参数传错了（如查询“2023年”写成“2022年”）     | `ToolCorrectness`（细粒度检查）     |
| 多轮对话中忘记了用户刚才说的关键信息                     | `KnowledgeRetention`                |
| 计划步骤混乱，做了很多无用功才完成                       | `PlanAdherence`, `StepEfficiency`   |
| 最后结果看起来对了，但过程有安全隐患（如执行了危险命令） | `Misuse`, `Safety`（自定义）        |
| 用户明确要求A，它做成了B                                 | `GoalAccuracy`                      |
| 回复冗长、重复、无礼                                     | `Coherence`, `Politeness`           |

**输出**：列出你最担心的 3-5 种失败模式，并为每种匹配至少一个候选指标。

---

### 第三步：对齐业务指标（非功能性需求）

即使功能正确，业务可能还关心成本、速度、用户感受等。

| 业务关切       | 可选的评估方式                                           |
| :------------- | :------------------------------------------------------- |
| **响应时间**   | 不是 DeepEval 直接指标，但可在测试中记录耗时，设置阈值   |
| **成本**       | 统计调用 LLM 的 token 数、工具调用次数                   |
| **用户满意度** | 使用 `UserSatisfaction` 指标（需要标注或代理模型评分）   |
| **可解释性**   | 评估智能体是否输出推理过程（自定义指标：`HasReasoning`） |
| **鲁棒性**     | 对输入扰动、工具返回异常值是否仍能正常工作（压力测试）   |

**输出**：确定是否需要加入**效率类**或**体验类**指标。

---

### 第四步：评估资源与可行性

不是所有指标都能“开箱即用”。你需要考虑：

| 资源限制                  | 影响                                                         |
| :------------------------ | :----------------------------------------------------------- |
| **有没有 ground truth？** | 如果没有期望输出，`TaskCompletion` 需要人工标注或使用更强的模型作为评判员 |
| **评估成本**              | 每跑一次测试都要调用 LLM 打分，如果测试用例很多，费用会上涨  |
| **可自动化程度**          | `ToolCorrectness` 可以自动验证参数；`UserSatisfaction` 通常需要人工或代理模型 |
| **开发时间**              | 内置指标 5 分钟就能跑起来；自定义指标可能需要半天到一天      |

**输出**：圈定出 **“必做且可做”** 的指标集合，暂时搁置资源不足的指标。

---

### 第五步：设计分层评估策略（从小到大的测试集）

不要试图一次性评估所有指标。采用金字塔策略：

```
     /\
    /  \  少量：端到端任务完成（最接近真实用户）
   /____\
  /      \ 中等量：关键子能力（工具调用、记忆）
 /________\
/          \ 大量：基础安全、格式、单步正确性（快速回归）
```

**示例分层**：
- **L1（快速冒烟测试）**：`JSONCorrectness`、`Misuse` – 每次代码提交都跑
- **L2（核心能力回归）**：`ToolCorrectness`、`KnowledgeRetention` – 每日构建跑
- **L3（完整任务评估）**：`TaskCompletion`、`GoalAccuracy` – 每周或发版前跑

## 实际案例分析：一个“邮件助手”智能体

**场景**：用户可以要求智能体“给张三发一封邮件，主题是会议延期，附件上传这个PDF”。智能体需要调用 `send_email(to, subject, body, attachment)` 工具。

### 应用五步法：

1. **类型**：操作执行型，单轮为主，涉及工具。
2. **风险分析**：
   - 最怕：发错人、漏附件、邮件内容错误
   - 次要：参数格式错误、调用失败不重试
3. **业务指标**：用户满意度、成功发送率、平均耗时
4. **可行性**：有明确的期望输出（to, subject, body），可以用 `ToolCorrectness` 自动比对参数；满意度需要人工或代理模型
5. **分层策略**：
   - L1：检查输出是否包含 `send_email` 调用（`ToolCorrectness` 基本版）
   - L2：验证参数完全匹配期望（`ToolCorrectness` 细粒度）
   - L3：完整场景测试（如先查询联系人再发邮件，测试 `PlanAdherence`）

**最终选择的指标**：
- 必选：`ToolCorrectness`、`TaskCompletion`（发邮件动作是否执行）
- 可选（如有资源）：`StepEfficiency`（是否一步到位，没有多余操作）
- 监控（非测试）：记录实际 API 调用成功率、平均延迟

## 总结：决策流程图

```
开始
 │
 ▼
【智能体类型】──► 候选指标池
 │
 ▼
【失败模式脑暴】──► 匹配指标，标记优先级(高/中/低)
 │
 ▼
【业务指标对齐】──► 加入效率/体验类指标
 │
 ▼
【可行性评估】──► 筛除当前无法实现的
 │
 ▼
【分层策略】──► L1(快速) / L2(核心) / L3(完整)
 │
 ▼
输出：一组可执行的指标 + 测试频率
```

**关键原则**：从“用户最在意什么”和“最常出什么错”出发，而不是从“DeepEval 提供了什么指标”出发。先用最简单的一两个指标跑通流程，再逐步丰富。
