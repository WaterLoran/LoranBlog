# 如何做安全与合规的评估及其分析过程

对于 LLM 应用中的**安全与合规评估**，决策过程与功能评估有本质不同：安全不是“越准越好”，而是**底线问题**。你需要根据**法规要求、业务场景、用户群体、潜在危害程度**来决定评估哪些方面。

下面提供一个**安全与合规评估的六步决策框架**，帮助你系统性地识别和选择需要检测的风险类型。

---

## 安全与合规评估决策框架（六步法）

### 第一步：识别适用的法律法规与行业标准

安全评估的首要驱动因素是**合规义务**。不同行业、地区有不同要求。

| 法规/标准                                  | 核心要求                                           | 影响的评估指标                    |
| :----------------------------------------- | :------------------------------------------------- | :-------------------------------- |
| **GDPR（欧盟通用数据保护条例）**           | 不得处理未经同意的个人数据，发生泄露需72小时内报告 | `PIILeakage`（必须）              |
| **CCPA（加州消费者隐私法案）**             | 用户有权知道、删除其个人信息                       | `PIILeakage` + 数据删除验证       |
| **HIPAA（美国健康保险流通与责任法案）**    | 保护医疗健康信息                                   | `PIILeakage`（医疗ID、诊断信息）  |
| **金融行业（PCI-DSS、FFIEC）**             | 不得输出信用卡号、账户信息                         | `PIILeakage` + 自定义财务信息检测 |
| **中国《生成式人工智能服务管理暂行办法》** | 不得生成违法、有害、歧视性内容                     | `Toxicity`, `Bias`, `Misuse`      |
| **欧盟《人工智能法案》**                   | 高风险系统需进行基本权利影响评估                   | 全套安全指标 + 红队测试           |

**分析问题**：你的应用会在哪个地区上线？属于哪个行业（医疗、金融、教育、公开对话）？是否有明确禁止输出的内容类型？

**输出**：列出必须合规的指标（通常是 `PIILeakage` 和 `Toxicity` 的基础版本）。

---

### 第二步：分析用户群体与使用场景

同样的内容，对成年人可能无害，对儿童就是有害的。场景决定了风险的敏感度。

| 用户群体/场景              | 风险敏感度 | 需要额外关注的指标                                           |
| :------------------------- | :--------- | :----------------------------------------------------------- |
| **面向儿童（<13岁）**      | 极高       | `Toxicity`（脏话、暴力）、`Misuse`（诱导危险行为）、`SexualContent`（自定义） |
| **面向普通公众（如客服）** | 中高       | `Bias`（种族、性别歧视）、`PIILeakage`（邮箱、电话）         |
| **企业内部（员工助手）**   | 中         | `PIILeakage`（员工信息、商业机密）、`Misuse`（滥用权限）     |
| **医疗咨询**               | 极高       | `NonAdvice`（不得提供医疗诊断）、`PIILeakage`（病历号）      |
| **金融顾问**               | 极高       | `NonAdvice`（不得提供投资建议）、`Bias`（信贷决策歧视）      |

**分析问题**：你的用户是否包含未成年人或弱势群体？是否涉及专业建议领域？是否有任何可能的危害（身体、心理、财产）？

**输出**：根据用户敏感度，决定是否需要 `Toxicity`、`NonAdvice`、`Bias` 等指标。

---

### 第三步：识别最可能发生的滥用模式

想象恶意用户或无意中可能触发的危险输出。这需要结合你的应用功能。

| 滥用模式                 | 示例                             | 对应评估指标                            |
| :----------------------- | :------------------------------- | :-------------------------------------- |
| **生成仇恨/歧视言论**    | “为什么XX种族更愚蠢”             | `Toxicity`, `Bias`                      |
| **泄露其他用户信息**     | 模型训练数据中混入他人隐私       | `PIILeakage`                            |
| **提供危险指导**         | “如何制作炸弹”“如何自杀”         | `Misuse`                                |
| **绕过内容过滤（越狱）** | 通过角色扮演诱导模型输出违规内容 | 红队测试（DeepTeam）                    |
| **自动执行恶意操作**     | 调用API删除文件、发送垃圾邮件    | `Misuse` + `ToolCorrectness`            |
| **生成虚假/误导性信息**  | “某药能治愈新冠”                 | `Hallucination`（但安全视角需单独检测） |

**分析问题**：如果有人故意想破坏你的系统，他们最可能做什么？你的模型是否有可能无意中输出危险内容？

**输出**：选择 2-3 个最可能发生的滥用模式，匹配对应的安全指标。

---

### 第四步：评估风险等级与容忍度

不是所有风险都需要同等投入。进行简单的**风险矩阵分析**：

| 风险等级 | 发生可能性 | 危害程度                   | 建议动作                                        |
| :------- | :--------- | :------------------------- | :---------------------------------------------- |
| **极高** | 高         | 严重（人身伤害、巨额罚款） | 必须评估，设置严格阈值（如0.9），并加入红队测试 |
| **高**   | 中         | 中等（隐私泄露、品牌损害） | 必须评估，阈值0.7-0.8，定期人工抽查             |
| **中**   | 低         | 轻微（用户不适、轻微偏见） | 可选评估，阈值0.5-0.6，可仅监控                 |
| **低**   | 极低       | 可忽略                     | 暂不评估，依赖基础模型能力                      |

**示例**：
- 医疗咨询应用 → 输出危险建议（高危害）→ 必须评估 `NonAdvice` + `Misuse`，阈值 0.95
- 客服聊天机器人 → 偶尔出现不礼貌（低危害）→ 可选评估 `Politeness`，阈值 0.5

**输出**：为每个选定的指标设定通过阈值（0-1之间，越高越严格）。

---

### 第五步：评估技术可行性

安全指标并非都能“开箱即用”。有些需要定制或结合人工审核。

| 指标         | 开箱可用性 | 注意事项                                                   |
| :----------- | :--------- | :--------------------------------------------------------- |
| `PIILeakage` | ✅ 高       | 可检测常见模式（邮箱、电话、身份证号）；但商业机密需自定义 |
| `Toxicity`   | ✅ 高       | 基于开源模型（如Detoxify），但中文支持需验证               |
| `Bias`       | ⚠️ 中       | 需要定义敏感属性（种族、性别等），且评估成本较高           |
| `Misuse`     | ⚠️ 中       | 需要预设危险类别（武器、毒品、自杀等），可定制关键词       |
| `NonAdvice`  | ❌ 低       | 需要根据业务定义“专业建议”边界，通常需自定义               |
| **红队测试** | ⚠️ 中       | DeepEval 的 DeepTeam 提供自动化攻击生成，但需人工审核结果  |

**输出**：区分“可直接使用”、“需简单配置”、“需深度定制”三类指标，合理分配开发资源。

---

### 第六步：设计安全评估的分层策略

安全评估不应该只在发版前做，而应**融入开发、测试、部署全流程**。

```
        /\
       /  \  定期：全面红队测试 + 人工审计（季度/半年）
      /____\
     /      \ 发版前：完整安全指标套件（所有高风险指标）
    /________\
   /          \ 每日：核心安全指标（PII泄露、毒性、滥用）
  /____________\
 /              \ 每次提交：快速安全检查（仅硬编码规则）
```

**示例分层**（面向公众的对话系统）：

| 层级            | 内容                    | 指标/方法                                      | 运行频率     |
| :-------------- | :---------------------- | :--------------------------------------------- | :----------- |
| **L0 提交门禁** | 禁止明显有害词          | 自定义关键词黑名单                             | 每次代码提交 |
| **L1 每日回归** | PII泄露、毒性、基础滥用 | `PIILeakage`, `Toxicity`, `Misuse`（预设词表） | 每日构建     |
| **L2 发版前**   | 偏见、专业建议检测      | `Bias`, `NonAdvice`（自定义） + 人工抽样       | 每次发版     |
| **L3 季度审计** | 越狱、对抗性攻击        | DeepTeam 红队测试 + 外部审计                   | 每季度       |

## 实际案例：金融客服聊天机器人

**场景**：银行提供的在线客服，用户可以询问信用卡、贷款、理财等。用户包含普通成年人。

### 应用六步法：

1. **法规**：适用中国《生成式AI管理办法》+ 金融行业对投资建议的监管 → 必须检测 `NonAdvice`（不得提供具体投资建议）
2. **用户群体**：普通成年人，但可能包含金融知识薄弱者 → 风险中等
3. **滥用模式**：最常见的是用户诱导模型给出“哪只股票会涨” → `Misuse`；其次是模型无意中输出其他客户的账户信息 → `PIILeakage`
4. **风险等级**：输出虚假投资建议可能导致财产损失 → 高危害，必须拦截；PII泄露可能导致罚款 → 高危害
5. **可行性**：`PIILeakage` 可直接使用；`NonAdvice` 需要自定义一套金融领域的关键词和拒绝话术模板；`Bias`（如信贷歧视）可暂缓，因为数据量不足
6. **分层策略**：
   - L0：关键词黑名单（“推荐买入”“预测涨停”）
   - L1：每日跑 `PIILeakage` + 自定义 `NonAdvice`
   - L2：发版前人工抽查 100 条高风险对话
   - L3：每季度使用 DeepTeam 模拟攻击（越狱尝试）

**最终选择的指标**：
- **必须**：`PIILeakage`（阈值 0.99，任何泄露都失败），`Misuse`（自定义金融违规词，阈值 0.95）
- **强烈推荐**：`NonAdvice`（自定义，阈值 0.90）
- **可选**：`Toxicity`（金融客服通常不需要高敏感度，阈值 0.5 仅作监控）
- **暂缓**：`Bias`（需要大量标注数据，成本高）

## 总结：决策流程图

```
开始
 │
 ▼
【法规识别】GDPR/HIPAA/金融/儿童保护等 ──► 强制指标
 │
 ▼
【用户/场景分析】是否弱势群体？是否专业建议？ ──► 补充指标
 │
 ▼
【滥用模式脑暴】最可能的恶意/意外输出 ──► 匹配指标
 │
 ▼
【风险矩阵】发生可能性 × 危害程度 ──► 设定阈值
 │
 ▼
【可行性评估】开箱可用？需定制？ ──► 分配开发资源
 │
 ▼
【分层策略】提交门禁 → 每日 → 发版 → 季度审计
 │
 ▼
输出：指标清单 + 阈值 + 运行频率 + 红队测试计划
```

**关键原则**：安全与合规评估是**防御性**的。先从**必须合规**的指标（如 PII 泄露、毒性）开始，确保基础底线；然后根据业务风险逐步增加定制指标；最后通过定期的红队测试发现未知漏洞。**宁可过度评估，也不要遗漏高风险点**。
