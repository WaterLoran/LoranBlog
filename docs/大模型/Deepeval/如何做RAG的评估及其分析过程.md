# 如何做RAG的评估及其分析过程

这是一个非常经典的问题。RAG（检索增强生成）系统涉及检索和生成两个环节，每个环节都有不同的失败模式。决定评估哪些指标，本质上是**根据你的业务场景、数据特点、用户痛点，定位系统最薄弱的环节**。

下面我提供一个 **RAG 评估决策的五步分析框架**，帮助你科学地选择指标。

---

## RAG 评估决策框架（五步法）

### 第一步：分解 RAG 流水线，定位关键节点

RAG 系统的典型流程是：**用户问题 → 检索（召回相关文档块）→ 生成（基于问题+上下文输出答案）**。每个节点有独立的评估维度。

| 节点                  | 核心职责                                     | 失败的表现                                   |
| :-------------------- | :------------------------------------------- | :------------------------------------------- |
| **检索器**            | 从知识库中返回最相关的 k 个文档块            | 召回不全、召回结果不相关、相关文档排位靠后   |
| **生成器（+上下文）** | 基于检索到的上下文生成正确、忠实、有用的回答 | 编造事实（幻觉）、遗漏关键信息、回答偏离问题 |

**分析问题**：你的系统目前最大的瓶颈是“搜不到”还是“答不对”？
- 如果用户经常反馈“明明有答案，但系统说没有” → 重点评估**检索质量**。
- 如果用户反馈“答案看起来合理，但其实是错的” → 重点评估**生成质量**。

---

### 第二步：分析你的知识库和数据特点

不同数据源会突出不同的风险：

| 数据特点                             | 风险                                 | 优先关注的指标                                          |
| :----------------------------------- | :----------------------------------- | :------------------------------------------------------ |
| **长文档、多主题**                   | 检索器可能只召回一小段，遗漏核心信息 | `ContextualRecall`（是否包含所有必要信息）              |
| **有明确的正确答案**（如 FAQ、手册） | 可以精准对比                         | `AnswerSimilarity`、`Correctness`                       |
| **答案需要综合多个片段**             | 生成器可能忽略部分片段               | `ContextualRelevancy`（上下文片段是否都相关且被使用）   |
| **用户问题表述多样**（同义问法多）   | 检索器可能对某些表述不敏感           | `AnswerRelevancy`（答案与问题相关性，间接反映检索质量） |
| **知识更新频繁**                     | 模型可能依赖旧知识                   | `Faithfulness` + 检测是否利用最新上下文                 |

**分析问题**：你的知识库是结构化的 FAQ 还是非结构化的长文档？用户提问方式是否多样？答案是否需要多源融合？

---

### 第三步：收集用户的真实失败案例

最直接的方法是**分析线上日志或用户反馈**，找到高频失败模式。常见的有：

| 用户抱怨                             | 对应的评估指标                         | 说明                     |
| :----------------------------------- | :------------------------------------- | :----------------------- |
| “我问的明明是A，你回答的是B”         | `AnswerRelevancy`                      | 答案偏离问题             |
| “你们系统瞎编，文档里根本没这句话”   | `Faithfulness`                         | 幻觉检测                 |
| “答案不完整，漏了关键步骤”           | `ContextualRecall`                     | 检索没把关键信息找回来   |
| “把不相关的内容也列出来了，看着很乱” | `ContextualPrecision`                  | 检索结果中无关文档太多   |
| “答案里有前后矛盾的信息”             | `ContextualRelevancy` + `Faithfulness` | 检索了冲突片段或生成混乱 |

**方法**：抽取 50-100 条真实失败案例，人工分类，统计各类问题占比。占比最高的 1-2 类就是你的首要评估目标。

---

### 第四步：评估资源的可行性

不是所有指标都能直接套用。你需要确认是否具备评估所需的条件：

| 指标                  | 需要的“参考答案”         | 是否需要人工标注？         |
| :-------------------- | :----------------------- | :------------------------- |
| `AnswerRelevancy`     | 只需要用户问题           | 否（自动）                 |
| `Faithfulness`        | 只需要检索到的上下文     | 否（自动）                 |
| `ContextualRecall`    | 需要标注“理想上下文片段” | 是（或使用更强的模型生成） |
| `ContextualPrecision` | 需要标注“相关文档”的排序 | 是（或代理模型）           |
| `Correctness` (GEval) | 需要一个标准答案         | 是（或合成数据）           |

**决策**：
- 如果没有标注数据，优先选择 **`AnswerRelevancy` + `Faithfulness`**（仅需问题和上下文）。
- 如果能够花费少量人力标注 100-200 个测试用例，可以加入 `ContextualRecall` 和 `ContextualPrecision`。
- 如果完全没有人力，可以使用 `Synthesizer`（DeepEval 内置）自动从文档生成问答对和期望上下文。

---

### 第五步：设计分层评估策略

采用 **金字塔模型**，从快速回归到全面评估：

```
     /\
    /  \  少量：端到端答案正确性（模拟真实用户）
   /____\
  /      \ 中等量：检索质量（精确率、召回率）
 /________\
/          \ 大量：基础防幻觉、答案相关性（快速回归）
```

**示例分层**（针对一个典型客服 RAG）：

| 层级        | 评估内容                   | 指标                              | 运行频率     |
| :---------- | :------------------------- | :-------------------------------- | :----------- |
| **L1 冒烟** | 答案是否编造、是否跑题     | `Faithfulness`, `AnswerRelevancy` | 每次代码提交 |
| **L2 核心** | 检索是否带回关键信息       | `ContextualRecall`（抽样 100 条） | 每日构建     |
| **L3 完整** | 综合质量（与标准答案对比） | `GEval`（自定义 correctness）     | 每周或发版前 |

## 实际案例：一个内部知识库问答 RAG

**场景**：公司员工通过 RAG 查询内部规章制度（如年假政策）。知识库为 PDF 文档，用户提问非常多样（“我能休几天假”“年假有多少天”等）。

### 应用五步法：

1. **流水线分析**：检索器基于向量相似度；生成器使用 GPT-4。
2. **数据特点**：长文档，答案通常散落在不同章节；有明确正确答案（政策原文）。
3. **用户抱怨**：最常见的是“答案漏掉了关键条件（比如转正后才能休假）” → **召回不全**；其次是“偶尔编造数字” → **幻觉**。
4. **可行性**：我们有政策原文，可以手动构建 50 个高难度问题并标注期望答案和关键上下文。
5. **分层策略**：
   - L1：每次提交跑 `Faithfulness`（防止幻觉）
   - L2：每日跑 `ContextualRecall`（确保关键点被召回）
   - L3：每周跑 `GEval`（与标准答案比对整体正确性）

**最终选择的指标**：
- **必选**：`Faithfulness`, `ContextualRecall`, `AnswerRelevancy`
- **可选**：`ContextualPrecision`（如果检索结果经常混入无关文档）
- **暂缓**：`Correctness`（因为标准答案标注成本高，先用 GEval 替代）

## 总结：决策流程图

```
开始
 │
 ▼
【定位薄弱环节】检索差 vs 生成差？
 │
 ▼
【分析数据特点】长文档/FAQ/多源？ ──► 锁定候选指标
 │
 ▼
【收集真实失败案例】人工分类 ──► 优先解决高频问题
 │
 ▼
【评估资源】有无标注数据？ ──► 筛选可落地的指标
 │
 ▼
【分层设计】L1快速 / L2核心 / L3完整
 │
 ▼
输出：一组指标 + 测试集规模 + 运行频率
```

**关键原则**：不要试图“全部评估”。从 **`Faithfulness` + `AnswerRelevancy`** 这对最轻量、无需标注的指标开始，快速建立基线。然后根据暴露的问题逐步增加 `ContextualRecall`、`ContextualPrecision` 等检索质量指标。如果资源允许，再加入端到端的 `Correctness` 评估。
