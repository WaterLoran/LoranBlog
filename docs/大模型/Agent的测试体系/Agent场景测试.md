# Agent场景测试

针对你列出的6类B端Agent场景测试，每类的核心风险与测试方法如下。目标是**在生产前模拟真实复杂场景，发现概率性、状态性、并发性缺陷**。

---

## 一、多轮对话测试

### 风险点
- 上下文截断/遗忘（超过窗口长度后早期信息丢失）
- 跨轮指代消解错误（“它”、“那个订单”指代错）
- 状态污染（上一轮的错误状态影响本轮）
- 用户中途修改意图（先问A，后改问B，再回A）

### 测试方法
| 测试类型         | 具体做法                                                     | 验证指标                           |
| ---------------- | ------------------------------------------------------------ | ---------------------------------- |
| **黄金路径多轮** | 预设3～8轮标准剧本（如：查订单→改地址→确认→取消），脚本化回放 | 最终状态正确，每轮回复与标注一致   |
| **随机多轮组合** | 从操作库随机采样组成N轮对话，自动检测最终业务状态一致性      | 无状态漂移，无未完成的工具调用     |
| **长上下文压测** | 轮数逐步增加至模型上限+20%，插入大量无关闲聊                 | 关键信息（订单号、日期）不丢失     |
| **跨轮负向测试** | 第3轮说“算了”，第4轮说“还是帮我做第2轮的事”                  | Agent能正确重置/回溯意图           |
| **用户中断恢复** | 多轮中用户突然说“停”、“换话题”，再切回原任务                 | 上下文不混乱，能自然衔接或明确询问 |

**工具**：对话编排框架（Rasa Trace、LangSmith）、自定义模拟器（按状态机驱动）

---

## 二、工作流分支测试

### 风险点
- 条件判断错误（if-else逻辑与业务规则不符）
- 分支遗漏（某些条件组合无对应处理）
- 分支间状态共享污染（变量作用域问题）
- 循环分支死循环或无限递归

### 测试方法
| 测试类型          | 具体做法                                                | 验证指标                                     |
| ----------------- | ------------------------------------------------------- | -------------------------------------------- |
| **分支覆盖矩阵**  | 列出工作流中所有条件变量的笛卡尔积，每个组合至少跑一次  | 所有组合都有明确输出，无“未定义行为”         |
| **边界值分支**    | 针对数值条件测试临界点（如“库存>0”测试0和1）            | 分支逻辑符合预期                             |
| **默认分支测试**  | 故意输入未定义的条件值（如枚举外字符串）                | 触发fallback逻辑，而非崩溃或幻觉             |
| **分支嵌套深度**  | 构造4层以上嵌套条件，验证执行顺序                       | 各层变量作用域隔离，外层变量不被内层意外修改 |
| **分支+多轮混合** | 第一轮走分支A，第二轮走分支B，第三轮要求回溯分支A的结果 | 工作流状态机正确保留分支上下文               |

**工具**：工作流引擎（LangGraph、Dify）的单元测试框架、决策表测试工具

---

## 三、工具链路（ToolChain）测试

### 风险点
- 链路依赖错误（B工具需要A工具的输出格式，但格式不匹配）
- 中间失败未传递（A失败后B仍被调用，浪费资源）
- 输出截断/超额（工具返回1万条数据，Agent只取了前10条导致误判）
- 并行工具调用时的竞态条件

### 测试方法
| 测试类型         | 具体做法                                                     | 验证指标                                                     |
| ---------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| **依赖图遍历**   | 显式定义工具间的数据依赖（有向无环图），测试所有路径         | 每个路径的输入输出schema匹配                                 |
| **错误传播测试** | 让链路中某个工具返回错误（如超时、403），验证后续工具是否被跳过，且Agent能给出友好提示 | 错误不扩散，链路提前终止且返回明确原因                       |
| **数据放大测试** | 工具A返回1000条记录，要求Agent用工具B逐条处理                | Agent不会一次性发送1000次调用（应有分页/聚合），且内存不溢出 |
| **并行工具链**   | 同时调用多个独立工具链，验证结果合并是否正确                 | 结果不交错，最终回答包含所有信息                             |
| **循环依赖检测** | 工具A调用B，B又调用A（设计上应禁止）                         | Agent能检测并中断，或给出循环告警                            |

**工具**：OpenTelemetry埋点 + 链路追踪（Jaeger）、工具Mock服务器（可注入延迟/错误）

## 四、异步/长任务测试

### 风险点
- 任务状态丢失（Agent在任务完成后忘记告知用户）
- 轮询机制缺陷（频率过高/过低，或永不终止）
- 任务超时未处理
- 用户中途查询长任务进度时，Agent返回过时状态

### 测试方法
| 测试类型         | 具体做法                                                     | 验证指标                                              |
| ---------------- | ------------------------------------------------------------ | ----------------------------------------------------- |
| **任务生命周期** | 创建异步任务 → 轮询状态 → 任务完成 → 获取结果 → 通知用户     | 每个阶段状态正确，最终通知送达                        |
| **超时模拟**     | 设置任务预期时长5秒，Mock后端故意耗时10秒                    | Agent应在超时后明确告知用户“任务可能失败，请稍后重试” |
| **进度查询并发** | 用户在一个会话中发起长任务，同时开启另一个会话查询同一任务ID | 两次查询返回一致的状态，无脏读                        |
| **中断恢复**     | 长任务执行过程中，用户关闭浏览器再打开，重新连接             | Agent能恢复之前的任务上下文，继续报告进度             |
| **取消任务**     | 用户发送“取消任务”时，Agent调用取消接口，且后续轮询停止      | 任务被标记为已取消，不再浪费资源                      |

**工具**：消息队列模拟器（Kafka/RabbitMQ Mock）、任务状态模拟器（可控延时）

## 五、并发测试

### 风险点
- 资源竞争（两个会话同时修改同一订单状态）
- 限流失效（超出API配额未降级）
- 全局状态污染（会话A的变量被会话B覆盖）
- 数据库死锁或连接池耗尽

### 测试方法
| 测试类型         | 具体做法                                                     | 验证指标                                          |
| ---------------- | ------------------------------------------------------------ | ------------------------------------------------- |
| **相同用户并发** | 同一个user_id同时开启5个会话，每个会话操作同一资源（如修改收货地址） | 最后一次修改生效，无中间状态泄露，无数据错乱      |
| **不同用户并发** | 100个虚拟用户同时调用Agent，每个执行不同工具                 | 工具调用成功率≥99.9%，无认证串号                  |
| **峰值冲击**     | 从0到1000 QPS瞬时上升，持续1分钟                             | Agent应限流返回429，而非崩溃；限流后能自动恢复    |
| **资源死锁检测** | 构造两个会话：A锁订单1、等待订单2；B锁订单2、等待订单1       | Agent不应同时持有两个锁；应超时回滚或主动死锁检测 |
| **共享缓存并发** | 多个会话命中相同语义缓存，同时写入新缓存                     | 缓存无脏数据，最终一致                            |

**工具**：Locust / JMeter（模拟并发用户）、Toxiproxy（注入网络延迟和丢包）

## 六、异常恢复测试

### 风险点
- 部分失败后Agent进入不可恢复状态
- 重试策略导致雪崩
- 异常后上下文不完整，用户需重头开始

### 测试方法
| 测试类型         | 具体做法                                                 | 验证指标                                                     |
| ---------------- | -------------------------------------------------------- | ------------------------------------------------------------ |
| **工具随机失败** | 按5%概率让任意工具返回5xx错误，观察Agent行为             | Agent应重试最多3次，若仍失败则明确告知用户，不崩溃           |
| **网络分区**     | 切断Agent与工具服务的连接5秒，再恢复                     | Agent应检测到连接断开，进入降级模式（如“系统繁忙，请稍后”），恢复后能继续 |
| **依赖服务重启** | 在对话中间重启数据库或Redis                              | Agent应优雅处理连接断开，重连后会话状态不丢失                |
| **模型服务超时** | LLM API延迟从1秒突变到30秒                               | Agent应有超时熔断，返回“AI响应超时，请重试”，而非hang住      |
| **状态恢复**     | Agent在执行第3步时崩溃重启，恢复后能读取持久化的对话历史 | 用户无需重新输入前2步信息，Agent能从断点继续                 |

**工具**：Chaos Mesh / Gremlin（注入故障）、State Persistence层（Redis/DB）的恢复测试脚本

## 七、幂等与重试风暴测试

### 风险点
- 同一请求因网络超时被客户端重试，导致业务重复执行（如重复转账）
- 重试风暴：故障恢复后所有积压请求同时重试，打垮下游
- 无指数退避导致定时同步重试，形成共振

### 测试方法
| 测试类型         | 具体做法                                                     | 验证指标                                                     |
| ---------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| **幂等性验证**   | 使用相同幂等键（idempotency_key）连续调用3次写操作（如“创建工单”） | 只创建一条记录，后续两次返回第一次的结果，无副作用           |
| **重复请求风暴** | 同时发送100个相同幂等键的请求                                | 后端只处理一次，其余返回“已处理”，无锁竞争或死锁             |
| **重试风暴模拟** | 让Agent某个工具超时，观察客户端重试行为                      | 重试间隔应指数退避（1s, 2s, 4s...），且总重试次数≤5          |
| **雪崩测试**     | 先让下游服务慢响应（P99=10秒），触发大量重试；然后恢复服务，看是否瞬间产生10倍流量 | 重试应带抖动（jitter），恢复后流量平滑上升，不超过正常值的2倍 |
| **幂等键过期**   | 同一个幂等键在24小时后再次调用                               | 应视为新请求（如果业务允许），否则返回“密钥过期”             |

**工具**：自定义重试客户端模拟器、压力测试时注入延迟并观察重试模式

## 落地建议：测试自动化矩阵

将以上场景测试集成到CI流水线中：

| 测试阶段                        | 触发条件 | 覆盖的场景                            | 运行时间要求 |
| ------------------------------- | -------- | ------------------------------------- | ------------ |
| **单元级（Tool/Workflow分支）** | 每次PR   | 分支覆盖、工具链路依赖                | < 1分钟      |
| **集成级（多轮+异常）**         | 每日定时 | 黄金多轮剧本、故障注入、幂等          | < 10分钟     |
| **系统级（并发+长任务）**       | 发布前   | 并发100用户、长任务生命周期、重试风暴 | < 30分钟     |
| **混沌级**                      | 每周     | 网络分区、服务崩溃、随机失败          | 1小时        |

建议使用**测试编排语言**（如HCL + Cucumber）将上述场景写成可执行的Given-When-Then剧本，与代码一同维护。
