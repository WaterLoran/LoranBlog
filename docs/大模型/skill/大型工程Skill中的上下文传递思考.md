# 大型工程Skill中的上下文传递思考

**当多个小 Skill 组合成大 Skill 时，它们之间的上下文（如中间结果、状态、数据）是如何传递的？** 这直接决定了组合的可行性、稳定性和效率。

在 Cursor / Claude Code 这类基于提示词和工具的 Skill 系统中，**没有传统编程语言中的共享内存或全局变量**。上下文传递必须**显式、有结构、可追踪**。下面先分析影响，再给出处理策略。

---

## 一、上下文传递的常见方式（3种）

### 1. **通过大 Skill 的提示词“记忆”传递（最脆弱）**
大 Skill 在提示词中要求自己“记住”每个小 Skill 的输出，并作为后续调用的输入。例如：
```
步骤1: 调用小Skill A，得到结果X。
步骤2: 将结果X作为参数，调用小Skill B。
```
**实际执行**：AI 在同一段对话中生成所有步骤，它确实可以“记住”X，因为所有文字都在上下文中。  
**问题**：如果对话很长或中间有用户打断，AI 可能“忘记”或混淆；而且无法持久化，每次执行都要重新生成。

### 2. **通过工具调用参数传递（推荐）**
如果使用 MCP 工具（如 `call_skill`），可以将前一个 Skill 的输出作为 JSON 参数传给下一个 Skill：
```json
call_skill(skill_name="skill_b", input={"previous_result": {"status": "ok", "data": {...}}})
```
工具内部可以维护一个上下文对象，每次调用都携带必要的状态。

### 3. **通过临时文件/外部存储传递（工程化最强）**
小 Skill 将输出写入约定好的临时文件（如 `/tmp/skill_ctx.json`），后续 Skill 读取该文件。  
**优点**：不受对话 token 限制，可被任意 Skill 复用，方便调试。  
**缺点**：需要管理文件生命周期（清理、并发冲突）。

---

## 二、上下文传递带来的影响

| 影响           | 具体表现                                                     | 严重程度 |
| -------------- | ------------------------------------------------------------ | -------- |
| **Token 爆炸** | 大 Skill 将所有中间结果都塞进提示词，超出上下文长度          | ⚠️ 高     |
| **状态不一致** | 某个小 Skill 修改了外部状态（如文件、数据库），但大 Skill 仍然使用旧缓存 | ⚠️ 中     |
| **错误难定位** | 链式调用中一个 Skill 输出异常格式，导致后续全部失败，难以溯源 | ⚠️ 高     |
| **并发冲突**   | 多个大 Skill 同时执行，写入同一个临时文件，数据混乱          | ⚠️ 中     |
| **可重复性差** | 依赖 AI “记忆”的结果在不同会话中无法复现                     | ⚠️ 高     |
| **调试困难**   | 难以单独测试某个小 Skill 在特定上下文中的行为                | ⚠️ 中     |

---

## 三、优秀处理策略（工程经验）

### 策略1：**小 Skill 设计为“纯函数”风格**
- 每个小 Skill 的**输入完全由参数决定**，不依赖外部隐式状态（如当前打开的文件、之前会话的内容）。
- **输出只依赖输入**，无副作用（或副作用明确声明）。
- 这样上下文传递就简化为参数的拷贝。

**示例**：  
❌ 坏设计：`/analyze` 默认分析当前光标所在的函数。  
✅ 好设计：`/analyze --code "function add(a,b){return a+b}"` 显式传入代码。

### 策略2：**统一使用 JSON 作为上下文交换格式**
- 所有小 Skill 的输入输出都遵循一个基础 Schema：
```json
{
  "ok": true,
  "result": { ... },   // 实际业务数据
  "error": null,
  "context_id": "uuid" // 可选，用于关联日志
}
```
- 大 Skill 负责维护一个**上下文对象**，每次调用小 Skill 时，将必要的字段从该对象中提取出来作为参数。

### 策略3：**使用临时文件 + 锁管理上下文（适合重度组合）**
- 定义一个临时目录（如 `.skill_context/`），每个大 Skill 执行时生成一个唯一的 `run_id`。
- 步骤：
  1. 大 Skill 创建 `run_id`，并写入初始上下文到 `context_{run_id}.json`。
  2. 每调用一个小 Skill，读取当前上下文文件，将其中的部分作为输入。
  3. 小 Skill 执行完毕，将输出合并回上下文文件（可使用 `jq` 或工具）。
  4. 所有步骤完成后，删除上下文文件。

**优点**：完全解耦，不占用对话 token，可复现，方便调试。  
**缺点**：需要额外工具支持（文件读写、合并 JSON）。

### 策略4：**大 Skill 作为“状态机”显式管理上下文**
在提示词中定义大 Skill 的**状态变量**，并要求自己每一步都显式输出当前状态（类似调试打印）。  
例如：
```
[状态] step=1, context={"files": ["a.py"], "results": []}
[动作] 调用 /read-file --path a.py
[结果] 得到 content = "def foo():..."
[新状态] step=2, context={"files": ["a.py"], "results": [{"file":"a.py","content":"..."}]}
```
这种虽然消耗 token，但可读性极强，易于调试。适合开发阶段。

### 策略5：**避免深层嵌套，优先使用“扁平化”组合**
如果一个大 Skill 需要调用 10 个小 Skill，考虑是否可以**并行**而不是串行，或者将部分组合提前沉淀为新的中等级别 Skill。  
例如：`/full-check` 可以同时调用 `/linter`、`/typecheck`，而不是顺序调用。并行调用时上下文传递是独立的，不存在顺序依赖。

## 四、具体案例：上下文传递的两种实现对比

### 案例：组装 `/gen-api-doc`（读取文件 → 提取API → 生成Markdown）

#### ❌ 脆弱实现（依赖 AI 记忆）
```markdown
## 执行步骤
1. 调用 /read-file src/routes.js，记住输出内容变量 $content。
2. 调用 /extract-api --code $content，记住输出变量 $apis。
3. 调用 /gen-markdown --apis $apis，输出结果。
```
**问题**：$content 可能很大，撑爆 token；AI 可能“忘记”或格式错误。

#### ✅ 健壮实现（临时文件 + 工具）
使用 MCP 工具 `call_skill` 内置上下文管理：
```python
# 伪代码
ctx = {"files": []}
for file in ["routes.js", "users.js"]:
    content = call_skill("read-file", {"path": file})
    ctx["files"].append({"path": file, "content": content})

apis = call_skill("extract-api", {"files": ctx["files"]})
markdown = call_skill("gen-markdown", {"apis": apis})
print(markdown)
```
如果无法使用工具，可以模拟：大 Skill 生成 shell 脚本来调用 CLI 版本的 Skill 并传递 JSON。

## 五、最佳实践总结表

| 问题                                  | 推荐处理方式                                                 |
| ------------------------------------- | ------------------------------------------------------------ |
| 如何传递大块文本（如代码文件）？      | 写入临时文件，只传递文件路径；或使用 `--file` 参数让小 Skill 自己读取。 |
| 如何避免 token 爆炸？                 | 不在提示词中传递大段数据，改用外部存储（文件/键值存储）。    |
| 如何保证状态一致性？                  | 每个小 Skill 只依赖传入的参数，不依赖外部隐式状态。大 Skill 负责从唯一真理源（如上下文文件）读取和更新。 |
| 如何调试上下文错误？                  | 让大 Skill 输出每个步骤前后的上下文摘要；为每个小 Skill 增加 `--dry-run` 模式。 |
| 如何处理并发？                        | 为每次大 Skill 执行生成唯一 `run_id`，上下文文件按 `run_id` 隔离。 |
| 小 Skill 之间的数据格式不匹配怎么办？ | 在大 Skill 中加入“适配器”步骤：例如将 `/read-file` 的输出转换为 `/extract-api` 期望的格式。 |

## 六、终极建议：用“工作流定义文件”替代硬编码

对于复杂的大 Skill，可以**将组合逻辑外置**为一个 JSON/YAML 工作流定义，然后由一个通用的“工作流引擎 Skill”去解析执行。例如：

```yaml
# workflow.yaml
steps:
  - name: read_sources
    skill: read-file
    with:
      paths: ["src/routes/*.js"]
    output_as: files_content

  - name: extract_apis
    skill: extract-api
    with:
      code: "{{files_content}}"
    output_as: apis

  - name: generate_docs
    skill: gen-markdown
    with:
      apis: "{{apis}}"
    output_to_stdout: true
```

大 Skill `/run-workflow` 读取该文件，按顺序调用小 Skill，并自动处理上下文的存储和传递。这样**上下文传递的复杂性完全被引擎封装**，你只需声明数据流向。

---

## 七、总结

上下文传递是组装大 Skill 的**核心挑战**。记住三句话：

1. **显式优于隐式**：始终通过参数或文件传递上下文，不要依赖 AI 的“记忆”。
2. **结构化优于自然语言**：使用 JSON 作为交换格式，便于工具解析和校验。
3. **外部存储优于长提示词**：临时文件是 token 爆炸的解药。

只要按照上述策略设计，你可以像搭积木一样组合出非常复杂的大 Skill，而不会陷入上下文混乱的泥潭。
