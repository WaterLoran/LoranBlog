# 使用小skill组装为大skill的理论思路

在大型工程中，从**可复用的小 Skill** 开始，然后**组合成更复杂的大 Skill**，是降低复杂度、提高可维护性的核心方法。下面给出**设计理论、组合模式、具体案例和避坑经验**。

---

## 一、核心理念：小 Skill 是乐高积木，大 Skill 是拼装图纸

- **小 Skill**：单一职责，输入输出明确，无副作用或副作用可控。
- **大 Skill**：工作流编排，按顺序调用若干小 Skill，传递中间结果，处理异常，最终产出。

这种设计的好处：
- ✅ 每个小 Skill 容易测试、调试、复用。
- ✅ 大 Skill 可以灵活替换其中的小 Skill（如从本地文件读取换成从数据库读取）。
- ✅ 多人协作时，每个人负责不同的积木。

---

## 二、小 Skill 的设计规范（为了可组合）

小 Skill 要像**函数**一样可以被其他 Skill 调用（在提示词 + 工具环境下，通过约定实现）。

### 1. 统一的输入输出契约
- **输入**：必须能通过**自然语言或 JSON 参数**传入。建议小 Skill 支持两种模式：
  - 直接对话模式（用户触发）
  - 调用模式（被大 Skill 调用，通过约定的格式）
- **输出**：应该返回**结构化结果**，而不是纯人类叙述。例如：

```json
{
  "status": "success",
  "data": { ... },
  "next_action_hint": "如果需要下一步，可调用 /next"
}
```

### 2. 可重入、无隐藏状态
- 小 Skill 不应依赖之前的调用结果（除非通过显式传入上下文）。
- 如果需要保存中间状态，由大 Skill 负责存储和传递。

### 3. 声明自己的“工具依赖”和“权限要求”
- 在 Skill 描述中写明它需要哪些工具（读文件、执行 shell、网络请求等）。
- 例如：`requires: [read_file, search_code]`

## 三、组合模式（3 种经典模式）

### 模式1：流水线模式（Pipeline）
**适用场景**：线性步骤，后一步依赖前一步的输出。

**示例**：大 Skill `/review-pr` = 小 Skill `git-diff` → `code-analyzer` → `comment-generator`

**实现方式**（在提示词中描述）：
```markdown
## 执行流程
1. 调用 /git-diff --cached 获取变更代码（JSON 格式）。
2. 将变更代码逐文件传给 /code-analyzer，收集分析结果。
3. 将所有分析结果合并后调用 /comment-generator 生成评审意见。
4. 输出最终意见（不自动提交）。
```

### 模式2：编排模式（Orchestrator）
**适用场景**：多个小 Skill 并行执行，最后汇总。

**示例**：大 Skill `/full-check` 同时调用 `/linter`、`/typecheck`、`/security-scan`

**实现方式**：
```markdown
## 执行流程
- 同时（或依次）执行以下三个 Skill：
  - /linter --json  # 输出代码规范问题
  - /typecheck      # 输出类型错误
  - /security-scan  # 输出漏洞列表
- 等待所有结果返回后，生成一个汇总报告。
```

### 模式3：选择器模式（Router）
**适用场景**：根据输入条件选择不同的小 Skill。

**示例**：大 Skill `/auto-fix`：如果是 Python 代码调用 `/fix-python`，如果是 JS 调用 `/fix-js`

**实现方式**：
```markdown
## 执行流程
1. 读取当前文件的扩展名。
2. 如果 .py：调用 /fix-python
3. 如果 .js 或 .ts：调用 /fix-js
4. 否则回复“不支持的语言”。
```

## 四、组合的技术手段（如何让 AI 理解“调用另一个 Skill”）

在 Cursor/Claude Code 中，没有内置的函数调用机制，但我们可以通过**提示词约定**来模拟：

### 方法A：显式命令注入
在大 Skill 的提示词中写出“你将依次执行以下命令，并等待每个命令的输出”：
```markdown
步骤1：输出“现在调用小SkillA，参数为...”
用户（或系统）会实际输入 `/SkillA ...`，然后 AI 看到结果后继续。
```
但这需要用户协作，不够自动化。

### 方法B：使用子提示词（Sub-prompt）
将小 Skill 的提示词内容**嵌入**到大 Skill 的提示词中，并让 AI 模拟执行。这种方法不依赖外部调用，但会消耗大量 token。

### 方法C：通过工具调用（最推荐）
如果你能自定义 MCP（Model Context Protocol）工具，可以：
- 注册一个 `call_skill` 工具，参数为 `skill_name` 和 `input_json`。
- 该工具内部管理小 Skill 的调用和结果返回。
这是最接近编程中函数调用的方式。

## 五、实战案例：从三个小 Skill 组装成一个“文档生成”大 Skill

### 小 Skill 1：`/read-file`（读取文件内容）
```yaml
输入：file_path (string)
输出：{"content": "文件文本", "lines": 120}
```

### 小 Skill 2：`/extract-api`（从代码中提取 API 定义）
```yaml
输入：code (string)
输出：{"apis": [{"name": "getUser", "method": "GET", "route": "/user/:id"}]}
```

### 小 Skill 3：`/gen-markdown`（根据 API 列表生成文档）
```yaml
输入：apis (list)
输出：{"markdown": "## API 文档\n\n### GET /user/:id ..."}
```

### 大 Skill：`/gen-api-doc`（为整个项目生成 API 文档）
**提示词**（流水线模式）：
```markdown
你是一个 API 文档生成器。按以下步骤执行：

1. 找到项目中的所有路由文件（可硬编码为 ./src/routes/*.js），对每个文件：
   - 调用内部能力（模拟小 Skill `/read-file`）读取内容，得到 content。
   - 将 content 传入 `/extract-api`（模拟）得到 apis 列表。
   - 将所有 apis 汇总到一个数组中。

2. 将所有汇总的 apis 传入 `/gen-markdown`（模拟），得到最终的 markdown。

3. 输出该 markdown，并询问用户是否保存到 `API.md`。

注意：你必须严格按顺序执行，不要跳过任何步骤。每一步的输出格式必须符合约定。
```

当用户执行 `/gen-api-doc` 时，AI 会按照描述一步步“模拟”调用那些小 Skill（实际上是对 AI 的同一轮思考，但你可以通过要求 AI 输出中间结果来模拟分步）。如果配合 MCP 工具，每一步可以真正调用独立的 Agent。

## 六、常见陷阱与解决方案

| 陷阱               | 现象                                                      | 解决方案                                                     |
| ------------------ | --------------------------------------------------------- | ------------------------------------------------------------ |
| **上下文爆炸**     | 大 Skill 把多个小 Skill 的提示词全塞进来，超过 token 限制 | 小 Skill 只保留接口描述（名称+输入输出），具体实现放在外部（如独立的 `.skill` 文件），大 Skill 通过工具调用它们。 |
| **错误传播**       | 小 Skill 失败，大 Skill 继续执行导致错误结果              | 在每个调用步骤后检查 `status`，若非 `success` 则停止并报告错误。 |
| **结果格式不一致** | 不同小 Skill 输出的 JSON 结构不同，导致大 Skill 解析困难  | 强制所有小 Skill 输出遵循统一 Schema，例如 always `{"ok": bool, "result": any, "error": string}` |
| **顺序依赖**       | 用户在大 Skill 执行中手动干预，打乱了顺序                 | 在设计时声明“本 Skill 全自动，无需用户中间输入”。如果必须中断，使用 `ask_user` 工具。 |
| **调试困难**       | 不知道是哪个小 Skill 出了问题                             | 大 Skill 输出执行日志：`[步骤1] 调用 /read-file -> 成功 (文件大小 2KB)` `[步骤2] 调用 /extract-api -> 失败: 无效的 JSON` |

## 七、总结：从组装到生态

1. **先定义小 Skill 的契约**（输入输出格式、错误码），这是组合的基础。
2. **使用流水线/编排/选择器**三种模式搭建大 Skill。
3. **通过 MCP 工具实现真正的 Skill 调用**，避免纯提示词模拟的脆弱性。
4. **为每个 Skill 编写独立的文档**，包括它的输入输出示例、依赖的其他 Skill 等。
5. **版本管理**：当小 Skill 的契约变更时，需要同步更新所有依赖它的大 Skill。

最终你会得到一个**Skill 生态系统**：小 Skill 像函数库，大 Skill 像脚本，可以快速搭建各种测试、代码生成、分析等自动化任务。这正是应对大型工程的最佳实践。
