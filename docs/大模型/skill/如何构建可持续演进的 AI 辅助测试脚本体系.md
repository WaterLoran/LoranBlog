# 如何构建可持续演进的 AI 辅助测试脚本体系



> 当你的 AI 辅助测试技能从三五个长到十几个，如何编排才能既好上手、又好迭代？本文结合软件测试行业的优秀实践，给出了一套可落地的分层架构方案。

## 引言

在过去一段时间里，我维护了一个 AI 辅助测试的 Skill 仓库，里面陆续积累了十多个用于生成测试脚本的能力。起初，每个 Skill 都解决一个具体痛点——有的负责把录制 JSON 转成 Logic，有的负责把测试用例文档批量落成脚本，有的专攻 UI 自动化。但随着数量增多，我发现自己和团队越来越难回答几个问题：

- 面对一个新需求，到底该用哪个 Skill？
- 多个 Skill 都在写类似的调试闭环、README 回写逻辑，改一处要改四五处；
- 想新加一个入口，不知道该往哪插，很容易长成新的“巨无霸” Skill。

于是我决定把整个 Skill 体系重新梳理一遍，并参考软件测试行业中“测试平台/测试工程体系”的成熟分层思想，设计一套既能保持易用性、又能长期可维护的架构。这篇文章就是我思考和落地过程的总结，希望能给有类似困扰的读者一些启发。

---

## 一、现状盘点：我们有哪些“写脚本”的 Skill？

先按“直接产出测试脚本”的口径来盘点，主要有 5 个核心 Skill，另有 3 个强相关的支撑 Skill。

### 1.1 直接写脚本的 5 个 Skill

| Skill 名称                                 | 定位                            | 输入材料                           | 输出                      | 适用场景                                                  |
| ------------------------------------------ | ------------------------------- | ---------------------------------- | ------------------------- | --------------------------------------------------------- |
| **logic_to_script**                        | 最轻量的 demo/冒烟脚本          | 现成 Logic（1~2 个）               | 基础 pytest 脚本          | 快速验证单个接口、提供示例                                |
| **service_to_script**                      | 通用 API 测试脚本总纲           | 已有 Logic                         | 完整规范的 API 自动化脚本 | 复杂业务编排、多步骤依赖、异步轮询、SQL 对账、Allure 报告 |
| **service_case_to_test_script**            | 测试用例文档→脚本的端到端编排器 | 测试用例文档（MD/Excel）+ 页面 URL | 一批按用例拆分的脚本工程  | 从需求文档批量生成自动化脚本                              |
| **api_record_with_service_to_test_script** | 录制 JSON→脚本的端到端编排器    | 抓包/录制 JSON + 业务文档          | 基于真实流量的脚本工程    | 已有录制数据，希望还原并自动化                            |
| **ui_script**                              | Web UI 自动化脚本               | 页面 URL                           | Playwright + POM 脚本     | API 覆盖不到的前端交互、样式、弹窗等                      |

### 1.2 支撑但不直接产脚本的 3 个 Skill

- **lorantest_logic_encapsulation**：负责将 API 封装成 Logic（common/ 下的公共方法）；
- **api_record_json_to_logic**：把录制 JSON 批量转成 Logic；
- **update_logic_topo**：脚本跑通后，将字段来源、数据关联等信息回写到 Logic README。

### 1.3 直观对比：一句话分清它们

| 维度           | logic_to_script | service_to_script | service_case_to_test_script | api_record_with_service_to_test_script | ui_script      |
| -------------- | --------------- | ----------------- | --------------------------- | -------------------------------------- | -------------- |
| **输入材料**   | Logic 关键字    | Logic             | 测试用例文档 + URL          | 录制 JSON + 业务文档                   | 页面 URL       |
| **脚本复杂度** | 最轻            | 中等到复杂        | 批量工程化                  | 批量工程化                             | UI 交互类      |
| **是否编排器** | 否（基础写法）  | 否（基础写法）    | 是（端到端编排）            | 是（端到端编排）                       | 否（基础写法） |

问题已经很清楚了：这些 Skill 功能有重叠，边界模糊，且公共逻辑四处散落。接下来需要设计一个合理的编排架构。

## 二、四种编排方案对比

为了找到最适合的架构，我设计了 4 种候选方案，从不同角度权衡清晰度、扩展成本和维护成本。

### 方案一：按输入物料分层

**思路**：用户给什么输入，就走哪条专用链路。

- 录制 JSON → `api_record_json_to_logic` → `service_to_script`
- 测试用例文档 → `service_case_to_test_script`
- 页面 URL → `ui_script`
- 现成 Logic → `logic_to_script`

**优点**：最符合用户心智，入口清晰，新人一看就懂。  
**缺点**：公共能力（调试、README 回写、清理等）会在多条链路中重复，后期容易产生“组合爆炸”。

### 方案二：按能力阶段分层

**思路**：按测试脚本的生命周期拆分为固定层次。

- L1 路由层：判断任务类型
- L2 解析层：标准化输入物料
- L3 资产层：构建 Logic、POM、helpers
- L4 脚本生成层：真正写 pytest
- L5 收尾沉淀层：回写拓扑、生成报告

**优点**：结构最工整，复用性最强，新增入口只需补解析层。  
**缺点**：设计成本高，Skill 间依赖多，对使用者不够直观。

### 方案三：双轴结构——外入口 + 内底座

**思路**：对外保留按输入物料划分的入口 Skill，对内按能力阶段拆分为原子底座 Skill。

- **对外入口**：`logic_to_script`, `service_case_to_test_script`, `api_record_with_service_to_test_script`, `ui_script`
- **对内底座**：`input_parse/*`, `logic_build/*`, `script_build/*`, `post_process/*`, `_shared/*`

入口 Skill 只做“编排”（路由、顺序、分支），不实现具体规则；底座 Skill 只做“一件事”。

**优点**：用户入口清楚，内部复用最好，适合渐进演进。  
**缺点**：命名和职责边界必须严格管理。

### 方案四：工作流模板化

**思路**：把常见链路抽象为固定 workflow（如 `record_to_logic_to_script`），Skill 退化为原子节点，workflow 负责串联。

**优点**：极度标准化，适合大规模团队和培训。  
**缺点**：底层 Skill 必须非常稳定，否则 workflow 频繁改动，维护成本高。

### 综合对比

| 评价维度   | 方案一          | 方案二 | 方案三    | 方案四           |
| ---------- | --------------- | ------ | --------- | ---------------- |
| 上手成本   | ⭐ 低            | ⭐⭐⭐ 高 | ⭐⭐ 中     | ⭐⭐⭐ 高           |
| 内部清晰度 | ⭐⭐ 中           | ⭐⭐⭐ 高 | ⭐⭐⭐ 高    | ⭐⭐⭐ 高           |
| 扩展性     | ⭐⭐ 中           | ⭐⭐⭐ 高 | ⭐⭐⭐ 高    | ⭐⭐⭐⭐ 很高        |
| 后期维护   | ⭐⭐ 中（易重复） | ⭐⭐⭐ 好 | ⭐⭐⭐⭐ 很好 | ⭐⭐⭐ 依赖底层稳定 |

**我的推荐**：如果追求快速可用，选方案一；如果追求长期产品化，最佳落地路线是 **“方案三”** ——既保留用户体验，又实现内部复用。

## 三、软件测试行业的最佳实践：四层架构

如果站在测试行业更成熟、更长期可维护的视角，上述方案还可以进一步抽象为 **四层架构**。这是许多大型测试平台和测试工程体系共同采用的设计思想。

### 3.1 四层架构定义

| 层次             | 职责                                                         | 对应示例                                                     |
| ---------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| **能力内核层**   | 提供稳定、原子的测试能力，不关心任务来源                     | `lorantest_logic_encapsulation`, `service_to_script`, `ui_script`, `update_logic_topo`, `mock` |
| **编排层**       | 接收任务，选择能力链，决定顺序和分支，汇总交付物             | `service_case_to_test_script`, `api_record_with_service_to_test_script` |
| **领域适配层**   | 沉淀特定业务域的测试经验（数据构造、API/UI 策略、常见对账方式） | `motion_comic_test_flow`, `book_city_test_flow`              |
| **交付与治理层** | 统一输出规范（README、报告、bug 记录、覆盖率审查、目录规范） | `_shared/` 下的命名、断言、清理、报告契约                    |

### 3.2 为什么这套架构符合行业优秀实践？

它遵循了 5 条核心原则：

1. **单一职责**——每个 Skill 只解决一类问题，不混合解析、封装、编排、报告。
2. **分层解耦**——输入、资产构建、脚本生成、执行、沉淀各层独立变化。
3. **领域优先，而非技术优先**——业务域（如 motion_comic）与测试能力（录制、Logic、UI）正交，各自沉淀。
4. **编排层要薄**——编排器只做路由，不堆积规则细节。
5. **共享规范下沉**——命名、断言、清理等规则统一放到 `_shared`，不在多个 Skill 中重复。

这恰好对应了成熟测试组织中“能力团队维护基础能力、平台团队维护流水线、业务测试团队维护领域实践、质量治理团队维护规范”的分工模型。

## 四、基于现有 Skill 的重构蓝图

结合上面的分析，我给出了具体的重构行动方案。

### 4.1 新的 Skill 分层树

```
.cursor/skills/
├── 01_core/                     # 能力内核层
│   ├── lorantest_logic_encapsulation
│   ├── api_record_json_to_logic
│   ├── service_to_script
│   ├── logic_to_script
│   ├── ui_script
│   ├── update_logic_topo
│   ├── mock
│   └── lorantest-judge-bug
│
├── 02_orchestration/            # 编排层（薄）
│   ├── service_case_to_test_script
│   ├── api_record_with_service_to_test_script
│   ├── swagger-to-logic
│   └── prd-to-case-loop
│
├── 03_domains/                  # 领域适配层（逐步补充）
│   ├── motion_comic/
│   ├── book_city/
│   └── distribution_platform/
│
├── 04_governance/               # 交付与治理层
│   ├── _shared/
│   │   ├── script_naming.md
│   │   ├── assertion_policy.md
│   │   ├── cleanup_policy.md
│   │   └── report_contract.md
│   └── review_checklist.md
│
└── README.md                    # 整体路由指引
```

### 4.2 哪些 Skill 需要合并或拆分？

- **合并**：无。当前 Skill 职责基本清晰，暂不合并。
- **拆分**：`service_case_to_test_script` 和 `api_record_with_service_to_test_script` 需要“瘦身”——将它们内部重复的调试闭环、README 回写、清理逻辑剥离，改为调用 `01_core` 中的原子 Skill 和 `04_governance` 中的规范。
- **下沉**：所有通用的断言规则、命名规范、清理策略、报告模板，从各个 Skill 的描述中抽离，统一放入 `04_governance/_shared/`，各个 Skill 通过引用方式使用。

### 4.3 迁移步骤（分阶段推进）

- **第一阶段**：建立新目录结构，将现有 Skill 按分类移动，不修改内容。
- **第二阶段**：抽取公共规范到 `_shared/`，修改各 Skill 中的引用。
- **第三阶段**：瘦身编排层 Skill，让它们更薄、更像路由器。
- **第四阶段**：为常见业务域（motion_comic、book_city）补充领域适配 Skill，沉淀专属测试经验。

## 五、避免的 4 种坏味道

在落地过程中，需要刻意避免行业里常见的反模式：

1. **巨型 Orchestrator**：一个 Skill 既做输入判断、又写规则、又写报告、又记 bug。结果是看起来很全，实则没人敢改。
2. **同一规范多处重复**：比如“teardown 必须清理”出现在 5 个 Skill 中，长期必然漂移。
3. **按临时需求随意新建 Skill**：今天来一个需求就新建 `xxx_to_script`，明天再来一个 `yyy_to_script`，最终 Skill 爆炸。
4. **技术层与领域层耦合**：在通用 `service_to_script` 中堆满某个业务域的专属逻辑，破坏了通用性。

## 六、结语

当你维护的 AI 辅助测试 Skill 从三五条增长到十几条时，如果没有合理的分层编排，很容易陷入“功能重叠、重复维护、边界模糊”的泥潭。

参考软件测试行业的优秀实践，我们得到了一条清晰的演进路径：

- **短期**：采用“双轴结构”——对外按输入物料保留入口，对内按能力阶段拆分底座。
- **中期**：逐步演进到“四层架构”——能力内核、编排、领域适配、交付治理。
- **长期**：在四层架构稳定后，可进一步将高频链路抽象为 Workflow 模板，实现更标准化的自动化流水线。

最终，优秀的测试 Skill 体系不是靠“大而全”的单个 Skill 取胜，而是靠 **职责单一、层次稳定、编排轻薄、规范下沉** 来获得长期的可持续性。希望这篇文章能给正在搭建或优化 AI 辅助测试工具链的你一些有用的参考。
