### 一、 什么是场景法？

首先，我们需要理解场景法的核心思想。场景法也叫“用例场景法”，它是一种**通过模拟用户真实使用软件的具体情景（即场景）来设计测试用例的方法**。

它的出发点是：软件最终是给用户用的，用户在使用时会触发一系列连续的操作，形成一个完整的“故事”或“流程”。测试这些完整的流程，比孤立地测试单个功能点更能发现那些隐藏的、与流程交互相关的缺陷。

**核心概念：基本流和备选流**
这是场景法的基石。

- **基本流**：也称为“Happy Path”或“主成功场景”。它描述的是最直接、最顺利、没有任何异常的流程，用户一步步达到目标的理想路径。
- **备选流**：也称为“异常流”。它描述的是在执行基本流的过程中，可能出现的各种分支情况，比如输入错误、操作中断、条件不符等。

每一个场景都是由**基本流和若干备选流**组合而成的。

### 二、 场景法的具体操作步骤（附实例说明）

我们以一个非常经典的例子——**“用户在线购物并支付”** 来贯穿整个操作流程。

#### 步骤一：分析需求，确定基本流和备选流

仔细阅读需求文档，找出用户要完成的核心目标，并描绘出最直接的实现路径。

- **基本流（以电商下单为例）**：
  1. 用户登录
  2. 浏览商品，选择商品加入购物车
  3. 进入购物车，点击“去结算”
  4. 填写/确认收货地址
  5. 选择配送方式
  6. 选择支付方式（如信用卡）
  7. 输入正确的支付信息并提交
  8. 系统扣款成功，显示订单成功页面

接下来，思考在这个流程的每一步中，可能出现什么问题或分支。

- **备选流（举例）**：
  - **备选流1**： 用户登录时，用户名或密码错误。
  - **选流2**： 购物车为空时，点击“去结算”。
  - **备选流3**： 在填写地址时，选择使用新地址。
  - **备选流4**： 在支付环节，信用卡信息无效（如卡号错误、过期）。
  - **备选流5**： 在支付环节，信用卡余额不足。
  - **备选流6**： 在支付环节，用户点击“取消”放弃支付。
  - **备选流7**： 在任何一个环节，用户点击“返回”上一步修改信息。

#### 步骤二：根据流生成场景

将基本流和各个备选流进行组合，每一个组合就形成了一个具体的测试场景。通常我们会使用**场景表**来清晰地表示。

| 场景编号 | 基本流 | 备选流1（登录失败） | 备选流2（空购物车） | 备选流4（支付信息无效） | ...  | 场景描述                                         |
| :------- | :----- | :------------------ | :------------------ | :---------------------- | :--- | :----------------------------------------------- |
| 场景1    | √      |                     |                     |                         |      | **成功购物**（理想路径）                         |
| 场景2    | √      | √                   |                     |                         |      | 用户登录失败，然后重新登录成功，完成购物         |
| 场景3    | √      |                     | √                   |                         |      | 用户尝试结算空购物车，被提示后添加商品，完成购物 |
| 场景4    | √      |                     |                     | √                       |      | 用户支付时输入无效信息，更正后支付成功           |
| 场景5    |        |                     |                     | √                       |      | *（特殊场景）* 用户直接跳到支付环节但信息无效    |

**说明**：

- **场景1**： 只包含基本流，是最核心的测试场景。
- **场景2**： 基本流在“步骤1”时转入备选流1（登录失败），处理完备选流1后，继续完成基本流的剩余步骤。
- **场景5**： 这是一个可能不经过完整基本流的异常场景，用于测试系统的鲁棒性。

#### 步骤三：为每个场景设计详细的测试用例

现在，我们需要把抽象的场景变成可执行的、具体的测试用例。每个测试用例应包括：

1. **用例ID**： 唯一标识符，如 TC_EC_001。
2. **测试场景**： 引用场景编号。
3. **用例标题**： 简洁地描述测试目的。
4. **前置条件**： 执行测试前系统应处的状态（如：商品A有库存，用户已注册）。
5. **测试步骤**： 详细、可操作的动作描述。
6. **测试数据**： 具体输入的数据（如：用户名`testuser01`，密码`Password123`，信用卡号`4111111111111111`）。
7. **预期结果**： 每一步或最终系统应有的正确反应。

**示例：针对“场景4”设计测试用例**

- **用例ID**: TC_EC_004
- **测试场景**: 场景4（支付信息无效后更正成功）
- **用例标题**: 验证用户支付时输入无效信用卡有效期，更正后能成功下单
- **前置条件**:
  1. 用户已登录。
  2. 购物车中有有效商品。
  3. 已进入支付页面。
- **测试步骤**:
  1. 在支付页面，选择“信用卡支付”。
  2. 输入正确的卡号（如 `4111111111111111`）。
  3. 输入**已过期**的有效期（如 上个月 `01/2023`）。
  4. 输入正确的CVV码。
  5. 点击“立即支付”按钮。
  6. 检查系统提示：应出现“信用卡有效期无效”或类似错误提示。
  7. 将有效期修改为**未来的日期**（如 `12/2025`）。
  8. 再次点击“立即支付”按钮。
- **预期结果**:
  1. 第6步：系统明确提示“信用卡有效期无效”，支付不成功，停留在支付页面。
  2. 第8步：系统处理支付，跳转至订单成功页面，并生成订单号。

#### 步骤四：评审和优化测试用例

与开发、产品经理等角色一起评审这些场景和测试用例，确保：

- 场景覆盖了所有重要的用户操作路径。
- 没有遗漏关键的备选流（特别是异常情况）。
- 测试数据和步骤是准确且可执行的。

#### 步骤五：执行测试用例并记录结果

按照设计的测试用例执行测试，详细记录实际结果。如果实际结果与预期结果不符，则提交缺陷报告。

### 三、 场景法的优点和局限性

**优点：**

1. **贴近用户**： 测试的是用户真实的使用流程，价值高。
2. **发现深层缺陷**： 能有效发现单个功能点测试难以发现的、与业务流交互相关的缺陷。
3. **提高效率**： 一个场景可以覆盖多个功能点，避免重复测试。
4. **易于理解**： 业务人员和非技术人员也能看懂场景描述，便于沟通。

**局限性：**

1. **可能遗漏边界条件**： 场景法侧重于流程，可能忽略单个功能的边界值、特殊输入等。因此，它需要与**等价类划分、边界值分析**等方法结合使用。
2. **场景数量可能爆炸**： 如果系统非常复杂，备选流众多，组合出的场景数量会非常庞大。这时需要根据风险和经验对场景进行优先级排序，重点测试核心场景。

### 总结

场景法是一种非常实用且强大的黑盒测试技术。其核心操作流程可以概括为：**“识别流 -> 组合场景 -> 细化用例”**。它完美地弥补了单纯测试功能点的不足，确保软件不仅在“点”上正确，更在“线”和“面”上流畅可靠。在实际工作中，一定要将其与其他测试设计方法结合使用，以达到最佳的测试效果。

### 方法命名：**“用户旅程推演法”**

这个名字比“场景法”更贴近您的实践，它强调**动态推演**和**连续视角**。

### 核心思想

**像导演一样思考，而不是像检票员一样检查。** 您的角色不再是简单地验证某个按钮是否有效，而是构想用户在这个“数字舞台”上会如何行动、如何思考、会遇到什么、以及最终能否达成目标。

### 操作流程的四个层次

根据您的描述，我们可以将这个推演过程分为四个逐层深入的层次。

#### **第一层：主干场景构建（讲述一个“理想故事”）**

这是您描述中的第一步：**“描述清楚那些个页面的各个行为的预期, 以及可能的后续事件”**。

- **操作：**
  1. **确定主角与目标**：用户是谁？（例如：首次购物的新用户）他的核心目标是什么？（例如：成功购买一台新手机）
  2. **勾勒主路径**：抛开所有意外，描述用户达成目标最直接、最理想的步骤序列。这就是“基本流”或“Happy Path”。
     - 例如：打开APP -> 搜索“手机” -> 浏览商品列表 -> 点击目标商品 -> 查看详情 -> 选择规格 -> 加入购物车 -> 去结算 -> 登录/注册 -> 填写地址 -> 选择支付 -> 付款成功 -> 查看订单。
- **关键产出：** 一个连贯的、无中断的“理想用户故事”。这是所有讨论的基准。

#### **第二层：分支场景探索（思考“故事的各种曲折”）**

这是您描述中的核心：**“昨晚这个操作之后，下一步会预期期望什么变化...以及用户...又会分别做什么。”**

- **操作：**
  1. **事件-反应推演**：在主干路径的**每一个步骤**后，停下来问：
     - **数据变化**：后台数据库发生了什么？（例如：加入购物车后，购物车表的商品数量是否+1？库存是否被预占？）
     - **界面反馈**：用户立刻能看到什么？（例如：按钮变灰？弹出提示？页面跳转？购物车图标上数字增加？）
  2. **用户意图推演**：站在当前节点，思考用户接下来**可能想做什么**（而不仅仅是“应该”做什么）。
     - **并行意图**：用户是会继续主流程，还是可能做点别的？（例如：在购物车页面，用户可能“继续购物”，也可能“删除商品”或“修改数量”）。
     - **回溯意图**：用户会不会后悔？会不会想修改之前的信息？（例如：在支付页面，突然想修改收货地址）。
- **关键产出：** 一张详细的“决策树”或“流程图”，覆盖了所有合理的用户选择。

#### **第三层：多维度用户建模（赋予“故事角色生命”）**

这是您方法中最精彩的部分：**“用户如果说, 他假设不同的智商程度, 不同的目的, 不同的背景, 不同的知识储备, 他又会分别做什么。”**

- **操作：** 创建典型的用户画像，并推演他们的独特旅程。
  - **按熟练度（智商/知识储备）**：
    - **小白用户**：会误操作吗？（连续点击提交按钮）、会看不懂术语吗？（什么是CVV？）、需要更多的引导和提示吗？
    - **专家用户**：会寻求快捷键吗？会觉得步骤繁琐吗？会期望更高效的流程吗？
  - **按目的**：
    - **目标明确型**：直奔主题，流程顺畅。
    - **闲逛比较型**：大量使用收藏、对比功能，可能频繁跳转页面。
  - **按背景**：
    - **网络环境差**：图片加载慢时，页面会崩吗？提交请求超时怎么办？
    - **使用不同设备**：在手机小屏幕上和PC大屏幕上，交互方式有何不同？
- **关键产出：** 一组覆盖不同维度的、有血有肉的“用户画像”及其专属场景列表。

#### **第四层：协作与压力测试（“故事的试映会”）**

您提到了关键一点：**“但是, 有时候是自己考虑不足, 得要其他人或者角度来补充。”** 这是将个人思考转化为团队智慧的过程。

- **操作：**
  1. **公开讲述**：就像您今早做的一样，拿着您的推演结果（最好是可视化的流程图）去给开发、产品、甚至客服同事讲解。
  2. **激发挑战**：主动询问：
     - “从这个技术实现角度看，我推演的这一步会不会有问题？”
     - “如果用户在这里连续发疯点提交，服务器扛得住吗？”（这就是压力测试的雏形）
     - “客服同事，你们平时接到最多关于这个流程的投诉是什么？我们模拟一下那个场景。”
  3. **查漏补缺**：记录下所有来自不同视角的反馈，补充到您的场景库中。
- **关键产出：** 一份经过团队评审、更加健壮和完整的场景集合。
