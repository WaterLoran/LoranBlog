# 工具调用的幂等性设计与重复执行防护

在 Agent 系统中，**幂等性** 指的是：同一个工具调用请求，无论执行一次还是多次，产生的副作用（如数据库修改、发送消息、扣款）都与执行一次相同。  
**重复执行** 的常见来源包括：网络超时重试、用户手动刷新、Agent 决策循环重复调用、分布式环境下的消息重复投递等。

解决这个问题的核心思路是：**让每个工具调用请求携带唯一标识，并在工具端或代理层进行去重**。下面从设计原则、具体实现、Agent 层防护、非幂等操作处理四个维度展开。

---

## 一、设计原则：区分“幂等”与“非幂等”操作

| 操作类型         | 示例                                          | 天然幂等性 | 需要额外防护           |
| ---------------- | --------------------------------------------- | ---------- | ---------------------- |
| **查询（读）**   | `get_user_info`, `search_documents`           | ✅ 是       | 基本不需要，但可做缓存 |
| **无副作用的写** | `update_status` (将状态改为相同值)            | ✅ 是       | 较少需要               |
| **有副作用的写** | `send_email`, `transfer_money`, `delete_file` | ❌ 否       | **必须实现幂等**       |
| **资源创建**     | `create_order` (同一订单号创建多次)           | ❌ 否       | **必须实现幂等**       |

**原则**：所有可能产生副作用或改变状态的工具，都应该设计为幂等或提供防重复机制。

---

## 二、工具端实现幂等性（推荐方案）

### 2.1 幂等键（Idempotency Key）模式

这是业界最成熟的做法（被 Stripe、AWS 等广泛采用）。  
**流程**：
1. **调用方（Agent）** 为每次请求生成一个唯一的幂等键（如 UUID 或 `session_id + step_index + timestamp`）。
2. 将该键作为工具调用参数之一（例如 `idempotency_key`）发送给工具。
3. **工具端**：
   - 检查该键是否在存储（如 Redis、数据库表）中存在。
   - 若存在：直接返回上次执行的结果（或忽略本次请求）。
   - 若不存在：执行业务逻辑，将结果与幂等键一起存储，设置过期时间（如 24 小时）。
   - 存储操作必须与业务操作在同一个事务中（或使用原子操作）。

**示例代码（工具端）**：

```python
class IdempotentTool:
    def __init__(self, redis_client):
        self.redis = redis_client
        self.ttl = 86400  # 24小时

    def run(self, arguments):
        idem_key = arguments.pop("idempotency_key", None)
        if not idem_key:
            raise ValueError("Missing idempotency_key for non-idempotent operation")

        # 检查是否已处理过
        cached = self.redis.get(idem_key)
        if cached:
            return json.loads(cached)  # 返回上次结果

        # 执行真正的业务逻辑（需原子性）
        result = self.do_business_logic(arguments)

        # 存储结果（应在业务事务内，或使用 Lua 脚本保证原子性）
        self.redis.setex(idem_key, self.ttl, json.dumps(result))
        return result
```

**幂等键的设计要点**：
- 全局唯一，不可预测（用 UUID v4 或 `ulid`）。
- 应包含足够信息区分不同调用（例如 `agent_session_id + tool_name + natural_key`）。
- 超时时间应大于可能的最大重试窗口（通常 24h 或 7d）。

### 2.2 数据库唯一约束

对于创建资源的操作（如 `create_order(order_no=xxx)`），可以直接使用业务唯一键（如订单号）作为数据库唯一索引，重复插入会抛出唯一冲突异常，工具捕获后返回已有结果。

```sql
CREATE TABLE orders (order_no VARCHAR(64) UNIQUE, ...);
```

**优点**：无需额外存储。  
**缺点**：仅适用于创建类操作，且需要工具能返回已有结果（可能需要额外查询）。

### 2.3 乐观锁或版本号

对于更新操作，可使用条件更新（如 `UPDATE table SET count = count + 1 WHERE id = ? AND version = ?`），通过检查影响行数判断是否重复。但这更多是防止并发覆盖，不是幂等的完整解决方案。

## 三、Agent 层的重复调用防护

即使工具端已经幂等，Agent 层也应该主动减少无效重复调用，以节省资源和时间。

### 3.1 调用去重中间件

在 Agent 的工具执行器（Tool Executor）中，维护一个**正在执行中的调用表**（in-flight deduplication）。

```python
class ToolExecutor:
    def __init__(self):
        self._pending_calls = {}  # key -> future

    async def execute(self, tool_name, arguments):
        # 生成调用唯一标识（根据工具+参数内容哈希）
        call_key = hash((tool_name, frozenset(arguments.items())))
        
        if call_key in self._pending_calls:
            # 等待已有调用完成，避免重复发起
            return await self._pending_calls[call_key]
        
        future = asyncio.Future()
        self._pending_calls[call_key] = future
        try:
            result = await self._do_call(tool_name, arguments)
            future.set_result(result)
        except Exception as e:
            future.set_exception(e)
        finally:
            del self._pending_calls[call_key]
        return await future
```

**注意**：这只能防止 Agent 内部同一时刻的重复调用，无法跨进程或跨 Agent 实例。

### 3.2 状态机跟踪步骤

在 Plan-and-Execute 模式中，记录每个计划步骤的执行状态（pending, running, completed, failed）。重试某个步骤前，先检查状态，避免重复执行已完成步骤。

### 3.3 用户交互层面的去抖（Debounce）

如果用户可能快速多次点击“发送”按钮，Agent 前端应做去抖（如 500ms 内忽略重复请求），或由后端检测相同会话的连续相同消息。

## 四、处理非幂等操作（无法改造工具时）

有些遗留工具无法修改（不支持幂等键），且操作不是幂等的（如“发送短信”）。此时 Agent 层面需要更谨慎：

### 4.1 人类确认环（Human-in-the-loop）
对于高风险、非幂等操作，强制要求用户二次确认。用户确认后，Agent 才发起调用，并确保只调用一次。

### 4.2 补偿事务（Compensating Action）
设计反向操作来回滚副作用。例如：
- 原操作：`send_email`
- 补偿：无法撤回，只能记录日志并通知管理员。
- 原操作：`transfer_money`  
- 补偿：`reverse_transfer`（但可能因余额不足失败，不完美）。

**最佳实践**：尽量避免在 Agent 中自动执行非幂等、不可补偿的操作；改为生成操作草案，由用户点击执行。

### 4.3 分布式锁

在调用非幂等工具前，针对资源标识（如 `user_id`）加锁，确保同一时间只有一个 Agent 实例在执行该操作。这能防止并发重复，但不能防止重试（锁释放后重试仍会执行）。

```python
from redis import Redis
r = Redis()
with r.lock(f"lock:send_sms:{user_id}", timeout=10):
    # 执行操作
    tool.run(...)
```

## 五、常见陷阱与最佳实践

| 陷阱                                             | 解决方案                                               |
| ------------------------------------------------ | ------------------------------------------------------ |
| 幂等键存储与业务操作不在同一事务中，导致重复执行 | 使用数据库事务（同一连接），或先插入幂等记录再执行业务 |
| 幂等键过期时间太短，重试窗口后请求被视为新请求   | 设置足够长的 TTL（至少比最大重试间隔长 10 倍）         |
| 使用参数哈希作为幂等键（参数可能相同但意图不同） | 使用客户端生成的唯一 ID（如 UUID）                     |
| 忘记在错误重试时携带相同幂等键                   | 在重试逻辑中明确复用原始请求的幂等键                   |
| Agent 内部去重导致跨请求干扰（不同用户相同参数） | 在 call_key 中加入 `session_id` 或 `user_id`           |
| 幂等键存储无限增长                               | 设置 TTL 并定期清理                                    |

## 六、总结：分层防护体系

```text
用户请求
    ↓
[前端去抖]  → 避免用户快速连点
    ↓
[Agent 内部去重] → 同一 Agent 实例内重复调用合并
    ↓
[工具调用中间件] → 生成幂等键，传递给工具
    ↓
[工具端幂等存储] → Redis/DB 去重，原子执行
    ↓
[补偿/告警]  → 极少数情况下的人工介入
```

**核心建议**：
- 对于所有写操作工具，**强制要求实现幂等键**（如增加 `idempotency_key` 参数）。
- 在 Agent 的 HTTP 客户端层，自动为每次请求生成 UUID，并在重试时保持相同键。
- 对于无法改造的旧系统，通过分布式锁 + 人类确认来降低风险。
- 记录所有幂等键的使用情况，用于审计和问题排查。

通过上述设计，可以将重复执行带来的副作用降到接近零，同时保证系统的健壮性。
