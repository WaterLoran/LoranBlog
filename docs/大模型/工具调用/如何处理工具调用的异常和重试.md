# 如何处理工具调用的异常和重试

在 Agent 系统中，工具调用（Tool Call）是连接 LLM 与外部世界的桥梁，但外部环境充满不确定性：网络抖动、API 限流、参数错误、服务超时、数据格式异常等。一个健壮的 Agent 必须系统化地处理这些异常，并智能地决定**何时重试、如何重试、何时放弃并回退**，甚至**将错误信息反馈给 LLM 让它自我修正**。

下面从**异常分类**、**重试策略**、**错误反馈与自我修正**、**超时与熔断**、**工程落地建议**五个维度展开。

---

## 一、工具调用的异常分类

不同类型的异常需要不同的处理策略。建议在代码层面显式区分：

| 异常类型          | 典型场景                                                  | 是否可重试                    | 示例                                    |
| ----------------- | --------------------------------------------------------- | ----------------------------- | --------------------------------------- |
| **临时性错误**    | 网络超时、服务暂时不可用、速率限制（429）                 | ✅ 是，且通常使用指数退避      | `requests.exceptions.Timeout`, HTTP 503 |
| **参数错误**      | LLM 生成的参数不符合工具 schema（缺少必填字段、类型错误） | ❌ 否，需 LLM 重新生成参数     | `KeyError`, `ValidationError`           |
| **业务逻辑错误**  | 查询的资源不存在（如“城市名错误”）、权限不足              | ❌ 否，需 LLM 调整输入或换工具 | `CityNotFound`, `PermissionDenied`      |
| **工具自身崩溃**  | 工具内部抛出未捕获异常（如除零、空指针）                  | ⚠️ 视情况，可重试一次          | `ZeroDivisionError`                     |
| **认证/授权失败** | API Key 过期、token 无效                                  | ❌ 否，需人工或系统级更新凭证  | HTTP 401                                |

**实践建议**：封装工具执行层，将底层原始异常统一转换为 Agent 可理解的 `ToolException` 子类，并携带错误码和人类可读的消息。

```python
class ToolException(Exception):
    def __init__(self, message, error_type="temporary", retryable=True):
        self.message = message
        self.error_type = error_type   # "temporary", "param", "business", "auth"
        self.retryable = retryable
```

## 二、重试策略的设计

对于**临时性错误**，需要自动重试。但重试不是简单的循环，必须考虑以下要素：

### 2.1 重试条件判断

只有满足以下条件才重试：
- 异常标记为 `retryable=True`
- 当前重试次数 < 最大重试次数（通常 3~5 次）
- 未超过总超时时间预算

### 2.2 退避算法

避免加剧服务端压力，同时提高成功率：

| 策略               | 算法                                        | 适用场景                            |
| ------------------ | ------------------------------------------- | ----------------------------------- |
| **固定间隔**       | 每次等待 1s                                 | 对延迟不敏感的内部服务              |
| **线性退避**       | wait = base * attempt                       | 一般场景                            |
| **指数退避**       | wait = min(max_wait, base * (2 ** attempt)) | 云端 API、限流场景（推荐）          |
| **抖动（jitter）** | wait = random_between(0, base * 2^attempt)  | 防止雷暴效应（大量 agent 同时重试） |

示例（指数退避 + 抖动）：
```python
def calc_backoff(attempt: int, base=1, max_wait=60) -> float:
    sleep_time = min(max_wait, base * (2 ** attempt))
    # 添加 ±25% 抖动
    sleep_time = sleep_time * random.uniform(0.75, 1.25)
    return sleep_time
```

### 2.3 幂等性保障

重试可能导致工具被多次调用，必须确保工具是**幂等**的，或者 Agent 能处理重复副作用。例如：
- 查询类工具（GET）天然幂等，可直接重试。
- 写操作（如发送邮件、扣款）必须在工具层实现幂等键（idempotency key），或由 Agent 避免重试。

**实践**：在工具执行上下文中传递 `request_id`，工具内部检查该 id 是否已处理。

## 三、错误反馈与 LLM 自我修正

Agent 的独特优势在于 **LLM 可以读取错误信息并调整行为**。这是传统 RPC 重试无法比拟的。

### 3.1 将结构化错误返回给 LLM

不要只抛出异常，而应将错误信息以 `tool` 角色消息追加到对话历史中，让 LLM 看到并重新决策。

```python
try:
    result = tool.run(arguments)
    return result
except ToolException as e:
    error_message = {
        "error": True,
        "type": e.error_type,
        "message": e.message,
        "suggestion": "请检查参数或使用其他工具"  # 可选
    }
    return json.dumps(error_message)   # 作为工具返回值返回，而非抛出
```

**关键点**：Agent 框架必须捕获所有异常，并将其**转换为字符串形式的错误返回**，而不是让执行链中断。这样 LLM 就能在下一轮看到类似：

```
Observation: {"error": true, "type": "param", "message": "城市名 'New Yrok' 不存在，有效城市示例：New York"}
```

### 3.2 LLM 自我修正的典型流程

1. **LLM 发起调用**：`tool: get_weather, args: {city: "New Yrok"}`
2. **工具返回错误**：`Error: City not found. Did you mean 'New York'?`
3. **LLM 观察错误**：在下一轮推理中，LLM 看到错误提示。
4. **LLM 修正参数**：重新调用 `get_weather(city="New York")`。
5. **成功**：返回天气数据。

**需要配合的 prompt 工程**：在 system prompt 中明确要求 LLM 遇到工具错误时，必须先阅读错误信息，修正后再调用，而不是重复相同的错误参数。

### 3.3 针对参数错误的自动修复

对于 schema 校验失败（如缺少必填字段），可以编写一个**自动修复层**，利用小型 LLM 或规则将原始参数补全/转换，而不必让主 LLM 重新生成。例如：

```python
def auto_fix_parameters(tool_schema, raw_args):
    # 若缺少必填字段，尝试从上下文中提取（如对话历史）
    # 或使用默认值
    # 若类型错误（如 string 传成了 array），尝试转换
    return fixed_args
```

但注意：自动修复可能引入新错误，建议仅用于明确安全的场景，并记录日志。

## 四、超时与熔断机制

工具调用可能永远阻塞（如网络挂起），必须设置超时。

### 4.1 超时分层

| 层级                 | 超时值                  | 作用                         |
| -------------------- | ----------------------- | ---------------------------- |
| **单次工具调用超时** | 5~30s（取决于工具性质） | 防止单次调用卡死 Agent       |
| **整体任务超时**     | 2~5 分钟                | 防止 Agent 陷入无限循环      |
| **重试总时间预算**   | 例如 60s                | 所有重试的累积时间不超过该值 |

实现时，对工具执行函数使用 `asyncio.wait_for` 或 `signal.alarm`（同步环境）。

### 4.2 熔断器（Circuit Breaker）

当某个工具持续失败时，应**暂时熔断**，避免浪费资源和加重后端负担。例如：

- 连续失败 5 次 → 熔断器打开，后续调用直接返回错误（不实际调用）
- 经过 30 秒冷却期 → 熔断器半开，允许一次试探调用
- 试探成功 → 熔断器关闭；失败 → 继续打开

熔断器可以按工具名维护状态，适用于依赖外部不稳定 API 的场景。

## 五、回退机制（Fallback）

当重试耗尽或遇到不可重试错误时，Agent 应有一套回退策略：

### 5.1 降级工具

如果主工具不可用，尝试使用功能相似但更鲁棒的工具。例如：
- 主工具：`get_precise_weather`（调用第三方 API，易超时）
- 回退工具：`get_approx_weather`（从缓存或更稳定的源获取）

在代码层面，可以在工具注册表中定义每个工具的 `fallback_tool`。

### 5.2 向用户求助

对于需要外部信息才能继续的错误（如缺少权限、需要人工输入），Agent 应暂停并询问用户：

```python
if error_type == "auth":
    return "⚠️ 无法访问您的邮箱，请在设置中重新授权。"
```

### 5.3 放弃并总结

如果所有尝试都失败，Agent 应向用户诚实说明无法完成任务，并给出失败原因，而不是假装成功或无限循环。

## 六、工程落地示例：带重试和错误反馈的工具执行器

以下是一个 Python 伪代码实现，融合了上述策略：

```python
import asyncio
import logging
from tenacity import retry, stop_after_attempt, wait_exponential, retry_if_exception_type

class RobustToolExecutor:
    def __init__(self, tool, max_retries=3, base_delay=1, timeout=30):
        self.tool = tool
        self.max_retries = max_retries
        self.base_delay = base_delay
        self.timeout = timeout

    @retry(
        stop=stop_after_attempt(3),
        wait=wait_exponential(multiplier=1, min=1, max=10),
        retry=retry_if_exception_type(TemporaryToolError),  # 仅重试临时错误
        reraise=True
    )
    async def _call_with_retry(self, arguments):
        return await asyncio.wait_for(
            self.tool.run(arguments),
            timeout=self.timeout
        )

    async def execute(self, arguments):
        try:
            result = await self._call_with_retry(arguments)
            return {"success": True, "data": result}
        except TemporaryToolError as e:
            # 重试耗尽后，返回可读错误供 LLM 处理
            return {
                "success": False,
                "error_type": "temporary",
                "message": f"服务暂时不可用（已重试{self.max_retries}次）: {str(e)}"
            }
        except ParamValidationError as e:
            return {
                "success": False,
                "error_type": "param",
                "message": f"参数错误: {str(e)}",
                "suggestion": "请修正参数后重试"
            }
        except BusinessError as e:
            return {
                "success": False,
                "error_type": "business",
                "message": str(e)
            }
        except asyncio.TimeoutError:
            return {
                "success": False,
                "error_type": "temporary",
                "message": "工具调用超时（30秒）"
            }
        except Exception as e:
            # 兜底
            return {
                "success": False,
                "error_type": "unknown",
                "message": f"未知错误: {str(e)}"
            }
```

在 Agent 主循环中：

```python
executor = RobustToolExecutor(tool)
observation = await executor.execute(arguments)
# 将 observation 作为字符串添加到对话历史
conversation.add_message("tool", json.dumps(observation))
```

LLM 看到 `"success": false` 后，会尝试修正或询问用户。

## 七、高级话题：预测性重试与自适应策略

- **基于历史成功率的动态重试**：记录每个工具的错误率，如果某工具错误率超过阈值，自动增加重试次数或切换到备选工具。
- **预测性重试**：使用轻量级模型预测当前调用是否可能失败（例如根据参数特征），提前调整策略。
- **带上下文的退避**：如果错误信息包含 `Retry-After` 头部，直接使用该值作为等待时间。

这些更适合大规模生产环境，初期可先实现基础重试。

---

## 总结

处理工具调用的异常和重试，核心原则是：

1. **分类清晰**：区分临时错误（可重试）与逻辑错误（需 LLM 修正）。
2. **重试有度**：指数退避 + 抖动 + 最大次数限制，避免雪崩。
3. **错误即反馈**：所有异常都转化为结构化错误消息返回给 LLM，让它参与修正。
4. **超时熔断**：避免单次调用拖垮整个 Agent。
5. **优雅回退**：降级、询问用户或诚实放弃，永远不要死循环。

通过上述设计，Agent 可以从容应对现实世界的不完美，显著提升鲁棒性和用户体验。
