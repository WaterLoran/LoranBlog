# 工具调用链中的上下文污染与隔离

在工具调用链中，**上下文污染** 指的是：前一个工具的输出（或中间状态）包含了无关、错误或敏感的信息，被后续工具当作正常输入使用，导致后续工具行为异常、泄露隐私或产生错误结果。**隔离** 则是要确保每个工具只看到它应该看到的数据，不受到其他工具输出的干扰。

下面从**污染来源**、**隔离原则**、**具体实现策略**三个层面展开。

---

## 一、上下文污染的典型来源

| 来源             | 示例                                                         | 后果                                   |
| ---------------- | ------------------------------------------------------------ | -------------------------------------- |
| **工具输出冗余** | `search_web` 返回完整网页文本，其中包含广告、导航栏等噪音    | 后续 `extract_info` 工具提取到错误内容 |
| **敏感数据泄露** | `get_user_profile` 返回包含身份证号、手机号，被传递给 `log_analytics` 工具 | 隐私泄露                               |
| **错误传播**     | `validate_address` 返回“地址无效”，但后续 `send_package` 仍收到该错误字符串作为地址 | 业务失败                               |
| **格式不匹配**   | 工具 A 返回 JSON，工具 B 期望纯文本，但未做转换直接传入      | 解析失败                               |
| **指令残留**     | 工具输出中包含了给 LLM 看的指令（如“请调用下一个工具时使用参数 X”），被后续工具当作数据 | 工具逻辑混乱                           |

---

## 二、隔离的核心原则

1. **最小数据暴露**：每个工具只接收其执行所必需的最小字段集。
2. **显式数据流**：工具之间的数据传递必须通过明确定义的变量或字段，而不是隐式地共享整个上下文对象。
3. **类型与格式强制**：每个工具的输出在传递前应被转换为后续工具期望的 schema。
4. **敏感标记与过滤**：对敏感数据打标签，禁止跨工具传递或在日志中记录。

---

## 三、具体实现策略

### 3.1 结构化状态容器（State Container）

不要将工具输出直接追加到对话历史中让 LLM 或后续工具自由读取，而是维护一个结构化的 `state` 字典，每个工具的输出写入特定键，后续工具通过键名引用所需数据。

```python
state = {
    "weather_bj": {"temp": 25, "unit": "celsius"},
    "user_address": "123 Main St",
    "sensitive_data": {"ssn": "***"}  # 已脱敏或禁止传递
}
```

**关键点**：
- 工具只能读取其声明中允许的键（白名单）。
- 工具写入时，只能覆盖自己负责的键，不能修改其他键。

### 3.2 输出清洗与投影（Projection）

每个工具在返回结果前，应返回一个**清洗后的子集**，只包含后续步骤可能需要的字段。可以使用 JSON Schema 的 `output` 定义。

```python
def get_weather(city):
    raw = weather_api.fetch(city)  # 返回 {"temp":25, "humidity":80, "wind":10, "raw_html":"..."}
    # 只保留后续需要的字段
    return {"temp": raw["temp"], "unit": "celsius"}
```

对于无法修改的工具，可以在调用链中增加一个**适配器**，对输出进行投影。

### 3.3 上下文隔离的两种模式

#### 模式 A：管道式（Pipeline）—— 每个工具的输出只传给下一个工具
适用于线性工作流。工具之间不共享全局状态，前一个输出直接作为下一个输入。

```python
result1 = tool1.run(input1)
result2 = tool2.run(result1)   # 仅接收 result1
result3 = tool3.run(result2)
```

**优点**：天然隔离，无污染。  
**缺点**：无法支持分支或多输入工具。

#### 模式 B：状态库模式（State Store）—— 工具从状态库中按需读取
适用于复杂 DAG 工作流。每个工具声明它需要哪些输入键，执行器从 state 中提取对应值，工具输出更新到新的键。

```python
# 执行器伪代码
def execute_step(step, state):
    inputs = {k: state[k] for k in step.required_inputs}
    output = step.tool.run(inputs)
    state[step.output_key] = output
```

**隔离保证**：
- 工具无法访问未显式声明的 state 键。
- 工具的输出不会覆盖已有键（除非允许）。

### 3.4 敏感数据标记与传播控制

- 在 state 中，为每个值附加元数据标签（如 `sensitive: true`, `pii: true`）。
- 工具执行前，检查其是否被授权处理敏感数据（例如，`log_tool` 不允许读取敏感字段）。
- 在将数据传递给外部工具或记录日志时，自动脱敏。

```python
class SensitiveValue:
    def __init__(self, value, tag):
        self.value = value
        self.tag = tag
        self.redacted = "***"

    def __str__(self):
        return self.redacted  # 禁止直接输出
```

### 3.5 错误隔离与断路器

如果某个工具的输出格式错误或包含异常值，不应直接传给后续工具，而应：
- 抛出明确错误，中断调用链。
- 或者返回一个特殊的 `ErrorValue` 对象，后续工具检查该类型后跳过处理。

```python
class ToolError:
    def __init__(self, message):
        self.message = message

# 后续工具
def process(data):
    if isinstance(data, ToolError):
        return data  # 传递错误，不处理
    # 正常逻辑
```

### 3.6 测试与验证

- 为每个工具编写**输入输出契约测试**，确保输出符合预期 schema，不包含无关字段。
- 在集成测试中，模拟上下文污染场景（如传递超大文本、特殊字符），验证隔离机制是否生效。

## 四、工程落地建议

| 措施                               | 优先级 | 说明                   |
| ---------------------------------- | ------ | ---------------------- |
| 使用结构化 state，禁止自由文本传递 | 最高   | 从根源上控制数据流     |
| 工具声明明确输入/输出 schema       | 高     | 强制开发者思考数据依赖 |
| 输出清洗（只返回必要字段）         | 高     | 减少冗余和敏感数据泄露 |
| 敏感数据标记与自动脱敏             | 中高   | 符合安全合规要求       |
| 错误值类型隔离                     | 中     | 防止错误传播           |
| 定期审计工具输出内容               | 中     | 发现意外泄露           |

---

## 五、总结

解决工具调用链中的上下文污染与隔离问题，核心思路是 **从“隐式共享”转向“显式数据流”**：
- 不要将工具输出随意拼接到对话历史或全局变量中。
- 使用结构化的状态容器，并为每个工具明确指定可读写的键。
- 对输出进行清洗、投影和敏感标记，避免冗余和隐私泄露。
- 采用管道或状态库模式，实现自然隔离。

通过这些措施，可以确保每个工具只获得它真正需要的数据，不受其他工具输出的干扰，从而提升 Agent 的可靠性和安全性。
