# 工具输出结果的结构化提取困难

工具输出结果的结构化提取困难，指工具返回的是自然语言、半结构化文本（如 Markdown、HTML）或自由格式，而后续步骤需要其中的特定字段（如温度值、城市代码、错误码）。依赖 LLM 再次解析会产生额外延迟、成本，并可能引入新的幻觉。下面从 **输出规范设计、解析策略、轻量提取器、LLM 辅助提取、混合方案** 五个层面给出解决方案。

---

## 一、源头控制：要求工具输出结构化格式（最佳实践）

在工具设计阶段，就强制要求所有工具返回**机器可读的结构化数据**，如 JSON、XML、YAML。这是最彻底的解决方式。

- **规范**：为每个工具定义输出 schema（与输入 schema 类似），例如：
  ```json
  {
    "type": "object",
    "properties": {
      "temperature": {"type": "number"},
      "unit": {"type": "string", "enum": ["celsius", "fahrenheit"]},
      "condition": {"type": "string"}
    },
    "required": ["temperature", "unit"]
  }
  ```
- **实施**：在工具实现中，返回 JSON 字符串而非自然语言。对于第三方 API，可以封装一个适配层将其响应转换为统一 JSON。

**优点**：提取零成本，无需解析。  
**缺点**：不是所有工具都能修改（如遗留系统、外部 API）。

---

## 二、规则驱动的轻量解析（正则、JSON Path、XPath）

当工具返回结构相对固定时，使用确定性解析器。

### 2.1 正则表达式提取
适用于简单模式，如 `"温度：(\d+\.?\d*)°C"`。

```python
import re
pattern = r"温度[：:]\s*(\d+\.?\d*)°C"
match = re.search(pattern, tool_output)
if match:
    temperature = float(match.group(1))
```

**优点**：快速、无额外成本。  
**缺点**：对格式变化敏感，维护成本高。

### 2.2 JSON / YAML 解析
如果工具输出是 JSON 字符串（但可能不标准），先用 `json.loads()` 尝试解析，失败则用 `yaml` 或 `ast.literal_eval`。

### 2.3 JSON Path / XPath
对于嵌套的 JSON 或 XML 输出，使用 `jsonpath-ng` 或 `lxml` 定位字段。

```python
from jsonpath_ng import parse
expr = parse("$.weather[0].temperature")
matches = expr.find(data)
```

---

## 三、基于 Schema 的解析器（结合 JSON Schema 与校验）

定义一个输出 schema，然后使用 `pydantic` 或 `jsonschema` 不仅校验，还能进行类型转换和默认值填充。这实际上也是一种“提取+验证”工具。

```python
from pydantic import BaseModel, ValidationError

class WeatherOutput(BaseModel):
    temperature: float
    unit: str
    condition: str

try:
    # 假设 tool_output 已经是 dict（若为字符串需先 json.loads）
    parsed = WeatherOutput(**tool_output)
except ValidationError as e:
    # 处理提取失败
    pass
```

**优点**：类型安全、自带错误报告。  
**缺点**：要求输出接近 JSON。

---

## 四、利用 LLM 进行二次提取（灵活但昂贵）

当规则无法覆盖，或输出格式多变（如用户自由文本、PDF、HTML）时，让 LLM 提取字段。

### 4.1 少量样本提示（Few-shot）
给 LLM 一个提取指令 + 几个示例，要求输出固定 JSON。

```text
从以下文本中提取温度数值和单位，以 JSON 格式输出：
文本： "今天北京最高气温25摄氏度，体感舒适。"
输出： {"temperature": 25, "unit": "celsius"}
```

### 4.2 使用结构化输出 API
如 OpenAI 的 `response_format` 配合 `strict: true`，强制 LLM 输出符合 schema 的 JSON。

### 4.3 注意点
- 增加了一次 LLM 调用，带来延迟和成本。
- 可缓存常见格式的提取结果，或用小模型（如 3.5 级）执行提取。

## 五、混合策略：规则优先，LLM 兜底

在实际系统中，最稳健的做法是组合多种方法：

1. **快速路径**：若工具已返回 JSON，直接解析。
2. **规则匹配**：尝试预定义的正则或 JSON Path。
3. **相似度模板**：维护常见输出格式的模板库，动态匹配。
4. **LLM 提取**：当以上都失败时，调用 LLM 进行提取，并**缓存该格式的解析规则**供后续使用（自我学习）。

**示例流程**：

```python
def extract_structured_output(tool_output, output_schema):
    # 1. 尝试 JSON 解析
    if isinstance(tool_output, str) and tool_output.strip().startswith(('{', '[')):
        try:
            data = json.loads(tool_output)
            return validate_against_schema(data, output_schema)
        except:
            pass
    
    # 2. 规则引擎
    for pattern in compiled_patterns:
        match = pattern.search(tool_output)
        if match:
            return extract_by_pattern(match, output_schema)
    
    # 3. LLM 提取
    extracted = llm_extract(tool_output, output_schema)
    # 可选：将新规则存入缓存
    cache_rule(tool_output, extracted)
    return extracted
```

## 六、工程建议与最佳实践

| 场景                       | 推荐方案                         |
| -------------------------- | -------------------------------- |
| 工具由自己团队开发         | 强制要求输出 JSON + 提供 schema  |
| 第三方 API 返回 JSON       | 直接解析 + 使用 Pydantic 校验    |
| 第三方 API 返回 HTML/XML   | 先用 XPath/CSS 提取，封装为 JSON |
| 自由文本（如搜索引擎片段） | 正则 + LLM 兜底                  |
| 需要高吞吐、低延迟         | 避免 LLM 提取，尽量用规则        |
| 格式频繁变化               | 考虑微调一个小型序列标注模型     |

**关键指标**：
- 提取成功率（应 >95% 如果规则覆盖良好）
- 平均提取耗时（规则 <1ms，LLM 可能 1-3s）

---

## 七、总结

解决工具输出结构化提取困难的核心思路是 **“规范优先，解析次之，LLM 兜底”**：
1. 尽可能让工具输出结构化数据（JSON）。
2. 对无法控制的输出，编写鲁棒的正则或 XPath 规则。
3. 引入 Schema 校验库（Pydantic/jsonschema）确保数据质量。
4. 将 LLM 作为最后的手段，并配合缓存和模板学习。

通过这种分层策略，可以在成本、延迟和准确性之间取得平衡。
