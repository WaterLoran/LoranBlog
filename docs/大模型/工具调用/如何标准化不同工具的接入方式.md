# 如何标准化不同工具的接入方式

针对 Agent 设计中“如何标准化不同工具的接入方式”，核心思路是**定义一套统一的工具抽象层**，将具体工具（API、代码函数、数据库查询等）封装成符合该抽象的“标准工具”。这样 Agent 只需依赖抽象接口，无需关心底层实现差异。

以下是业界成熟且可落地的标准化方案，以 **OpenAI Function Calling / Tool Use** 格式为蓝本（已被 LangChain、Semantic Kernel、AutoGen 等主流框架采用）：

### 1. 定义统一工具描述规范

每个工具都需要提供机器可读的元数据，通常用 JSON Schema 定义输入参数。

```json
{
  "name": "get_weather",                      // 唯一标识
  "description": "获取指定城市的当前天气信息",   // 自然语言描述，供 LLM 理解用途
  "parameters": {                             // 参数 schema（JSON Schema 子集）
    "type": "object",
    "properties": {
      "city": {
        "type": "string",
        "description": "城市名，如 Beijing"
      },
      "unit": {
        "type": "string",
        "enum": ["celsius", "fahrenheit"],
        "default": "celsius"
      }
    },
    "required": ["city"]
  }
}
```

### 2. 统一工具执行接口

无论底层是什么工具，Agent 只调用同一个执行方法：

```python
# 伪代码示例
class BaseTool(ABC):
    @property
    def schema(self) -> dict:
        """返回上述 JSON 描述"""
        pass

    @abstractmethod
    def run(self, arguments: dict) -> str:
        """执行工具，输入为已验证的参数字典，输出为字符串（供 LLM 阅读）"""
        pass
```

**关键点**：
- **输入归一化**：所有工具都接收 `dict` 类型的参数（由 LLM 生成或用户提供）
- **输出归一化**：所有工具返回 `str`（或可序列化为 JSON 的结构化数据），便于 Agent 将结果返回给 LLM
- **错误处理**：统一捕获异常，返回明确的错误信息字符串（如 `"Error: City 'xyz' not found"`）

### 3. 工具接入适配器模式

对于异构工具（REST API、数据库、本地函数），通过适配器转换为统一接口：

| 底层工具类型   | 适配方式                                            |
| -------------- | --------------------------------------------------- |
| **本地函数**   | 直接调用，将参数解包后传入，返回值转字符串          |
| **REST API**   | 根据参数构造请求 URL/body，发送 HTTP 请求，解析响应 |
| **数据库查询** | 参数转为 SQL 或查询条件，执行后格式化结果           |
| **第三方 SDK** | 调用 SDK 方法，处理特有认证、分页等逻辑             |

示例：封装一个 REST API 工具

```python
class RESTTool(BaseTool):
    def __init__(self, name, description, url_template, method="GET"):
        self._name = name
        self._description = description
        self.url_template = url_template   # 如 "https://api.weather.com/{city}"
        self.method = method

    def run(self, arguments: dict) -> str:
        url = self.url_template.format(**arguments)
        response = requests.request(self.method, url)
        return response.text   # 或 JSON 转字符串
```

### 4. 工具注册与发现机制

Agent 持有一个工具注册表，可动态增删工具：

```python
class ToolRegistry:
    def __init__(self):
        self.tools = {}   # name -> tool instance

    def register(self, tool: BaseTool):
        self.tools[tool.name] = tool

    def get_schemas(self) -> list[dict]:
        return [tool.schema for tool in self.tools.values()]

    def execute(self, name: str, arguments: dict) -> str:
        return self.tools[name].run(arguments)
```

### 5. 与 LLM 的标准化交互流程

1. **构造 LLM 请求**：将 `registry.get_schemas()` 作为 `tools` 参数传入（格式需符合 LLM 厂商要求，可通过适配层转换）
2. **LLM 决策**：返回要调用的 `tool_name` 和 `arguments`
3. **执行与反馈**：`result = registry.execute(tool_name, arguments)`，将结果以 `tool` 角色消息追加到对话历史
4. **循环**：LLM 可根据结果决定是否继续调用工具或生成最终答案

### 6. 高级标准化考量（可选但推荐）

- **权限与审计**：在 `run` 方法外层增加钩子，记录谁在何时调用了哪个工具及参数
- **流式工具输出**：对于长耗时工具，定义 `run_streaming` 返回生成器，支持 SSE 或 token 级输出
- **异步支持**：`async def run(...)` 适应高并发场景
- **工具链/组合**：通过工作流 DSL 将多个标准工具串联为一个“元工具”

### 实际案例对比

| 框架/协议                        | 标准化方式                                    |
| -------------------------------- | --------------------------------------------- |
| **OpenAI Assistant API**         | `tools` 数组 + `function` 对象（JSON Schema） |
| **LangChain**                    | `BaseTool` 类 + `name`/`description`/`_run`   |
| **Anthropic Claude**             | `tool_use` 块 + `input_schema`                |
| **Model Context Protocol (MCP)** | 通过 JSON-RPC 统一暴露工具列表及调用          |

### 总结

标准化接入的核心就是**三层统一**：
- **描述统一**：名称 + 描述 + JSON Schema
- **调用统一**：`run(dict) -> str`
- **管理统一**：注册表 + 错误处理

这样，新增一个工具只需要实现 `BaseTool` 并注册，Agent 无需改动任何内部逻辑。对于已有大量异构系统的团队，建议先构建一个轻量级的适配器工厂，逐步将所有工具封装进该标准层。
