# 如何实现工具的智能选择与组合

在 Agent 中实现工具的**智能选择与组合**，核心目标是让 Agent 能够像人类一样：面对复杂任务，自主决定“用哪些工具、按什么顺序、如何传递中间结果”，并在失败时调整策略。下面从**决策机制**、**规划方式**、**执行与状态管理**、**组合模式**以及**工程落地建议**五个层面展开。

---

## 一、工具选择的智能决策机制

### 1. 基于 LLM 推理的动态选择（最主流）

利用 LLM 的语义理解能力，将工具描述（名称、功能、参数 JSON Schema）与用户问题一同送入模型，让模型输出要调用的工具及参数。

**关键优化点：**
- **工具检索增强**：当工具数量超过 20~30 个时，LLM 容易混淆或遗漏。需要先用检索模型（如 embedding + 向量库）从全量工具中召回最相关的 Top-K 工具，再提供给 LLM。
- **Few-shot 示例**：在 system prompt 中给出典型的工具调用示例，显著提升选择准确性。
- **约束解码**：对参数 JSON 使用结构化输出（如 OpenAI 的 `strict` 模式或 Outlines 库），避免格式错误。

```python
# 伪代码：带检索的工具选择
relevant_tools = tool_retriever.retrieve(user_query, top_k=10)
llm_input = {
    "tools": [t.schema for t in relevant_tools],
    "query": user_query
}
response = llm.chat(llm_input)  # 返回 tool_call
```

### 2. 基于强化学习的预训练选择（特定领域）

对于工具数量固定且任务类型有限的场景（如机器人控制），可以训练一个策略网络直接输出工具的概率分布。但此方法泛化能力差，通用 Agent 中较少使用。

## 二、工具组合的规划方式

单一工具调用无法解决复杂任务，需要**多步规划**。主流有三种实现路径：

### 2.1 隐式规划（ReAct / Chain-of-Thought）

Agent 通过“思考-行动-观察”循环逐步推理，每一步决定下一步要用的工具。优点是灵活，适合不确定性高的任务；缺点是步骤长、容易陷入循环。

```text
用户：帮我对比北京和上海本周的天气，并推荐更适合旅游的城市。
思考1：需要先获取两个城市的天气数据。行动1：调用 get_weather(city="北京", days=7)
观察1：北京本周晴，气温5~15°C...
思考2：再获取上海天气。行动2：调用 get_weather(city="上海", days=7)
观察2：上海本周阴雨，气温10~18°C...
思考3：根据天气比较，晴天更适合旅游，推荐北京。
```

**实现要点**：在 prompt 中强制要求输出 `Thought:` 和 `Action:` 字段，并解析执行。

### 2.2 显式规划（Plan-and-Execute）

先让 LLM 生成一个完整的步骤计划（JSON 或自然语言），再由执行器按计划调用工具。优势是可解释性强，便于人工干预；缺点是计划可能不符合实际执行结果，需要 re-plan 能力。

```json
{
  "goal": "对比北京上海本周天气并推荐旅游城市",
  "steps": [
    {"id": 1, "tool": "get_weather", "params": {"city": "北京", "days": 7}, "output_var": "weather_bj"},
    {"id": 2, "tool": "get_weather", "params": {"city": "上海", "days": 7}, "output_var": "weather_sh"},
    {"id": 3, "tool": "compare_weather", "params": {"city1_data": "$weather_bj", "city2_data": "$weather_sh"}, "output_var": "comparison"},
    {"id": 4, "tool": "recommend_city", "params": {"comparison": "$comparison"}, "output_var": "final_answer"}
  ]
}
```

**执行器**需要支持：
- 变量引用（如 `$weather_bj`）
- 步骤依赖（有向无环图，并行执行无依赖的步骤）
- 条件分支与循环

### 2.3 基于图的规划（LLM + 图工作流）

使用 LangGraph 或自研的状态机，将工具调用建模为节点，条件边表示逻辑分支。LLM 负责决定走哪条边。这种方式兼具灵活性和可控性。

```python
# LangGraph 示例
workflow = StateGraph(AgentState)
workflow.add_node("get_weather", tool_node)
workflow.add_node("recommend", llm_node)
workflow.add_conditional_edges("get_weather", should_recommend)  # 根据天气结果决定是否推荐
```

## 三、执行时的状态管理与依赖传递

组合多个工具时，必须解决**中间数据如何传递**的问题。

### 方案 A：上下文窗口传递（简单但受限）

每个工具的输出直接追加到对话历史中，后续工具通过 LLM 从上下文中提取所需信息。缺点：长对话容易超 token 限制，且数据提取不可靠。

### 方案 B：显式变量存储（推荐）

Agent 维护一个 `state` 字典（或结构化存储），每个工具执行后可以将结果存入某个 key，后续工具通过引用 `$key` 来获取输入。

```python
state = {}
# 执行 step1
result1 = tool1.run(params)
state[output_var1] = result1
# 执行 step2，解析参数中的 $ 引用
resolved_params = resolve_references(step2.params, state)
result2 = tool2.run(resolved_params)
```

对于复杂嵌套引用（如 `$weather.temperature`），可以结合 JSONPath 或 JMESPath 解析。

### 方案 C：数据流引擎

采用 Apache Beam、Dask 等数据流框架，将每个工具视为一个算子，自动处理依赖和并行。适合高吞吐场景，但实现较重。

## 四、智能组合的高级模式

### 1. 流水线组合（Pipeline）

输出作为下一个工具的输入，无需 LLM 中间决策。例如：`search_web(query) -> extract_text() -> summarize()`。

**实现**：预定义工具链，或让 LLM 生成顺序列表。

### 2. 条件分支（Conditional）

根据某工具的输出结果决定下一步调用哪个工具。例如：调用 `check_weather` 后，如果 `rain_probability > 0.6` 则调用 `send_umbrella_reminder`，否则调用 `recommend_outdoor_activity`。

**在 prompt 中实现**：要求 LLM 输出 `if` 逻辑，或使用图工作流的条件边。

### 3. 并行调用（Parallel）

两个工具互不依赖，可同时发起，减少总耗时。例如：同时获取北京和上海的天气。

**实现**：在 Plan-and-Execute 中，识别出无依赖的步骤，放入线程池并发执行。

### 4. 迭代/循环（Loop）

反复调用同一工具直到满足条件。例如：`poll_task_status` 每隔 5 秒调用一次，直到返回 `completed`。

**实现**：在 prompt 中定义循环终止条件，或使用 `while` 节点。

### 5. 工具间的“委托”（Delegation）

一个工具的输出可能触发新的子任务，需要将子任务传递给另一个 Agent（多 Agent 协作）。例如：主 Agent 调用 `write_code` 工具生成代码，然后将代码交给 `execute_code` 工具运行。

## 五、工程落地建议与示例架构

### 推荐架构：Plan-and-Execute + 工具检索 + 状态机

```text
[用户输入] 
    ↓
[任务理解 & 工具检索] → 召回相关工具（embedding + 向量库）
    ↓
[规划模块]（LLM 生成 JSON 计划，包含步骤、依赖、变量）
    ↓
[执行器]（解析依赖，并行/串行执行工具，更新 state）
    ↓
[重规划触发器]（如果某步骤失败，调用 re-plan 模块修改后续步骤）
    ↓
[最终答案生成]
```

### 示例：实现“对比天气并推荐旅游城市”

```python
# 简化代码框架
class SmartAgent:
    def __init__(self, tools, retriever, llm):
        self.registry = ToolRegistry(tools)
        self.retriever = retriever
        self.llm = llm

    def run(self, task):
        # 1. 工具检索
        relevant_tools = self.retriever.retrieve(task, k=10)
        tool_schemas = [self.registry.get_schema(t) for t in relevant_tools]

        # 2. 生成计划
        plan_prompt = build_plan_prompt(task, tool_schemas)
        plan_json = self.llm.generate(plan_prompt, response_format="json")
        
        # 3. 执行计划（带状态）
        state = {}
        for step in plan_json["steps"]:
            # 解析变量引用
            params = resolve_variables(step["params"], state)
            # 调用工具
            result = self.registry.execute(step["tool"], params)
            if step.get("output_var"):
                state[step["output_var"]] = result
            # 若步骤失败且定义了 fallback，触发重规划
            if "error" in result and step.get("fallback"):
                plan_json = self.replan(task, state, step)
                # 重新执行当前步骤
        
        # 4. 生成最终答案
        final_answer = self.llm.generate(
            f"基于以下执行结果回答用户问题：\n任务：{task}\n状态：{state}"
        )
        return final_answer
```

### 常见陷阱与对策

| 陷阱                               | 对策                               |
| ---------------------------------- | ---------------------------------- |
| 工具数量过大导致 LLM 混淆          | 工具检索 + 只给 Top-K              |
| 参数引用解析错误                   | 使用强类型变量 + JSON Schema 验证  |
| 计划步骤过多超过上下文长度         | 压缩历史观察结果（只保留关键信息） |
| 工具调用失败导致整个任务失败       | 实现 re-plan 模块，允许局部修正    |
| 陷入无限循环（如反复调用同一工具） | 设置最大迭代次数 + 检测重复调用    |

## 六、成熟框架参考

无需从零实现，可基于以下框架快速构建：

- **LangGraph**：支持图状态、条件边、循环，非常适合实现复杂的工具组合逻辑。
- **AutoGen**：多 Agent 对话框架，天然支持工具调用与 Agent 间委托。
- **Semantic Kernel**：微软出品的规划器（Planner）支持 Stepwise 和 Sequential 规划。
- **DSPy**：用声明式方式定义工具组合的“程序”，并通过优化器提升选择准确率。

---

## 总结

智能选择和组合工具的核心在于**三层能力**：
1. **选择**：基于 LLM + 工具检索，从大量工具中精准定位当前所需。
2. **规划**：使用 Plan-and-Execute 或 ReAct 模式，生成可执行的步骤序列。
3. **状态与依赖**：维护变量存储，解析引用，支持并行和条件分支。

当任务复杂性超过单一工具能力时，务必引入显式规划模块，并结合重规划机制。最终，通过工程化封装（如 LangGraph）可以大幅降低实现难度。
