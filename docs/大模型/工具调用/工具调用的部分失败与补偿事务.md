# 工具调用的部分失败与补偿事务

在 Agent 系统中，**部分失败** 指的是一个复合任务（由多个工具调用组成）中，部分工具调用成功、部分失败，导致整体处于不一致状态。例如：转账任务中，`debit(from_account)` 成功扣款，但 `credit(to_account)` 失败，钱被扣了却没到账。**补偿事务** 就是通过执行一系列反向操作，撤销已成功的工具调用，使系统恢复到一致状态（或至少达到业务可接受的状态）。

下面从**识别补偿场景**、**补偿事务设计模式**、**实现步骤**、**补偿失败处理**及**工程建议**展开。

---

## 一、哪些操作需要补偿？

并非所有工具调用都需要补偿。只有那些**已经产生持久副作用且无法通过简单重试解决**的操作才需要补偿。

| 操作类型                 | 是否需要补偿 | 示例                                                         |
| ------------------------ | ------------ | ------------------------------------------------------------ |
| 查询（只读）             | 否           | `get_user_info`                                              |
| 幂等写操作（可重复执行） | 否           | `set_status("inactive")` 多次执行结果相同                    |
| 非幂等写操作（有副作用） | **是**       | `send_email`, `transfer_money`, `create_order`, `delete_file` |
| 资源锁定                 | **是**       | `reserve_seat`, `lock_inventory`                             |

**原则**：任何会产生不可逆变更或消耗资源的操作，都应该设计补偿逻辑。

---

## 二、补偿事务的核心模式

### 2.1 Saga 模式（最常用）

Saga 将一个长事务拆分为多个本地事务，每个事务有一个对应的**补偿事务**。Saga 按顺序执行事务，如果某个事务失败，则逆序执行已成功事务的补偿操作。

**两种协调方式**：
- **编排式（Orchestration）**：中央协调器（Agent 自身或专门 Saga 引擎）负责决策和执行补偿。
- **事件式（Choreography）**：每个工具完成后发布事件，下一个工具监听事件触发；失败时也发布补偿事件。适合分布式、解耦场景。

对于 Agent 系统，**编排式**更直观：Agent 知道整个计划，可以捕获异常并调用补偿。

### 2.2 补偿操作的设计

每个非幂等工具都应提供对应的**补偿工具**（或补偿接口）。例如：

| 正向操作                     | 补偿操作                                       |
| ---------------------------- | ---------------------------------------------- |
| `transfer(from, to, amount)` | `transfer(to, from, amount)` 或单独的 `refund` |
| `send_email(message_id)`     | 无法撤回，通常记录日志或发送“撤销”邮件         |
| `reserve_seat(flight, seat)` | `release_seat(flight, seat)`                   |
| `create_file(path, content)` | `delete_file(path)`                            |

**注意**：补偿操作本身也可能失败，需要设计重试或人工介入。

## 三、实现步骤（以编排式 Saga 为例）

### 3.1 定义带有补偿信息的步骤

```json
{
  "steps": [
    {
      "id": "step1",
      "tool": "debit",
      "params": {"account": "A", "amount": 100},
      "compensate_tool": "credit",
      "compensate_params": {"account": "A", "amount": 100}
    },
    {
      "id": "step2",
      "tool": "credit",
      "params": {"account": "B", "amount": 100},
      "compensate_tool": "debit",
      "compensate_params": {"account": "B", "amount": 100}
    }
  ]
}
```

### 3.2 执行与补偿引擎

```python
class SagaExecutor:
    def __init__(self):
        self.history = []  # 记录已成功执行的步骤

    def execute(self, steps):
        for step in steps:
            try:
                result = call_tool(step.tool, step.params)
                self.history.append(step)  # 记录成功
            except Exception as e:
                # 步骤失败，触发补偿
                self.compensate()
                raise e  # 或返回失败
        return "success"

    def compensate(self):
        # 逆序补偿
        for step in reversed(self.history):
            try:
                call_tool(step.compensate_tool, step.compensate_params)
            except Exception as e:
                # 补偿失败，记录到死信队列，人工介入
                log_critical(f"Compensation failed for {step.id}: {e}")
                send_alert_to_admin()
```

### 3.3 补偿事务的幂等性

补偿操作本身也应该是幂等的，防止重复执行产生副作用。例如 `release_seat` 重复调用不应报错，而是返回“已释放”。

## 四、补偿失败的处理策略

补偿操作也可能失败（如网络故障、服务宕机）。必须设计**最终一致性**方案：

| 策略            | 描述                                             | 适用场景                     |
| --------------- | ------------------------------------------------ | ---------------------------- |
| **重试 + 退避** | 自动重试补偿操作，直到成功                       | 临时性故障（网络、超时）     |
| **死信队列**    | 将失败的补偿任务放入队列，后续人工或定时任务处理 | 业务逻辑错误、需人工决策     |
| **日志 + 告警** | 记录失败详情，触发告警，由运维手动修复           | 高价值操作（如资金）         |
| **跳过并标记**  | 对于非关键操作，允许不一致，但标记状态供后续审计 | 低风险操作（如记录日志失败） |

**工程建议**：将补偿任务持久化到数据库，设置最大重试次数和指数退避。若最终失败，写入“待人工补偿”表并提供管理界面。

---

## 五、与幂等性和重试的关系

- **幂等性**：防止重复执行正向操作造成副作用。是补偿的前提。
- **重试**：适用于临时性错误，重试成功则无需补偿。
- **补偿**：适用于业务逻辑错误或重试耗尽后的回滚。

**典型流程**：
1. 调用正向工具，若遇到临时错误 → 重试。
2. 若重试耗尽或遇到业务错误 → 触发补偿事务。
3. 补偿失败 → 持久化并告警。

---

## 六、工程实践建议

1. **最小化需要补偿的操作**：尽量设计幂等工具，避免依赖补偿。例如，使用“预订-确认”两阶段模式替代直接扣款。
2. **补偿操作必须实现幂等**：多次调用补偿不应产生额外副作用。
3. **记录 Saga 执行日志**：将每个步骤的状态（成功、失败、补偿中、补偿完成）写入数据库，便于恢复和审计。
4. **设置超时**：对于长时间未完成的补偿，应超时并告警。
5. **避免嵌套补偿**：补偿操作不应再触发新的 Saga，否则复杂度爆炸。补偿应尽量简单。
6. **测试补偿逻辑**：编写故障注入测试，模拟正向步骤失败，验证补偿是否正确执行。

---

## 七、示例：转账失败补偿

**步骤**：
1. `debit(from="A", amount=100)` → 成功
2. `credit(to="B", amount=100)` → 失败（账户B不存在）

**补偿**：调用 `credit(from="A", amount=100)`（即退款给A）

**如果补偿也失败**：记录日志，发送告警，人工处理。

---

## 八、总结

解决工具调用部分失败的关键是**为每个非幂等工具预定义补偿操作**，并采用 Saga 编排模式管理执行与回滚。核心要点：

- **识别需要补偿的操作**（有副作用的写操作）。
- **设计补偿工具**（反向操作），并保证补偿幂等。
- **实现 Saga 执行器**，记录历史，逆序补偿。
- **处理补偿失败**（重试、死信、人工介入）。

通过补偿事务，Agent 可以从部分失败中恢复，维持业务一致性，避免留下“半完成”状态。虽然增加了设计复杂度，但对于金融、订单等关键场景是必不可少的。
