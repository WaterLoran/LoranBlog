# 工具调用的契约演化

在 Agent 系统中，**工具调用的契约演化** 指的是工具接口（输入参数、输出格式、错误码、行为语义）随着时间发生变化，而 **向后兼容测试** 则确保新版本工具仍然能被基于旧契约开发的 Agent 正确使用。契约演化不可避免（修复缺陷、增加功能、优化性能），但若处理不当，会导致已有 Agent 调用失败或行为异常。

下面从**兼容变更判断**、**设计原则**、**版本管理**、**兼容性测试方法**以及**工程实践**五个方面展开。

---

## 一、什么是兼容/不兼容变更

| 变更类型         | 示例                                    | 是否兼容                       |
| ---------------- | --------------------------------------- | ------------------------------ |
| 添加可选输入参数 | 增加 `?timeout=30`，有默认值            | ✅ 兼容                         |
| 添加新的输出字段 | 返回值中增加 `"cached": true`           | ✅ 兼容（旧客户端忽略）         |
| 放宽输入约束     | 枚举 `["red","blue"]` 增加 `"green"`    | ⚠️ 语义上兼容，但需客户端未禁止 |
| 缩小输入约束     | 删除某个支持的枚举值                    | ❌ 不兼容                       |
| 修改输入字段类型 | `user_id` 从 `string` 改为 `int`        | ❌ 不兼容                       |
| 删除输入字段     | 移除必填参数 `city`                     | ❌ 不兼容                       |
| 修改输出字段类型 | `temperature` 从 `string` 改为 `number` | ❌ 不兼容                       |
| 修改错误码含义   | 将 `404` 从“未找到”改为“禁止访问”       | ❌ 不兼容                       |
| 增加新的必填参数 | 新增 `api_version` 必填字段             | ❌ 不兼容                       |

**核心原则**：任何会破坏旧客户端假设的变更都是不兼容的。

---

## 二、契约演化设计原则

为了支持平滑演化，工具设计时应遵循以下原则：

1. **使用可选字段**：所有新字段都应设计为可选（optional），并给与合理的默认值。
2. **不要删除字段**：标记为 `deprecated`，保留至少两个主版本后再考虑移除。
3. **不要改变字段类型**：如需改变，新增一个字段（如 `temperature_f`），旧字段保留。
4. **容忍未知字段**：工具解析输入时，忽略未在 schema 中声明的字段（`additionalProperties: true`）。
5. **输出字段只增不减**：新版本可以添加新字段，旧客户端会忽略它们。
6. **使用语义化版本（SemVer）**：
   - **Patch**：向后兼容的 bug 修复（不改变行为）。
   - **Minor**：向后兼容的功能增加（新增可选参数、输出字段）。
   - **Major**：不兼容的变更（删除字段、修改类型）。

## 三、契约的显式管理

### 3.1 工具注册表中的契约存储

每个工具在注册时，应附带其契约描述（OpenAPI / JSON Schema），并标记版本号。Agent 在调用前可以查询工具的当前版本，或声明自己支持的版本。

```json
{
  "name": "weather",
  "version": "1.2.0",
  "input_schema": {...},
  "output_schema": {...}
}
```

### 3.2 使用适配器模式进行版本转换

如果工具发生了不兼容变更，但 Agent 无法立即升级，可以在工具端或网关层增加一个**版本适配器**，将旧版契约转换为新版。

```python
def adapter_v1_to_v2(request_v1):
    # 将 v1 参数转换为 v2 格式
    return {
        "city_name": request_v1["city"],   # 字段改名
        "units": "metric"                   # 新增默认值
    }
```

### 3.3 多版本共存

最稳妥的方式是让工具同时提供多个版本端点（如 `/v1/weather` 和 `/v2/weather`），Agent 根据自身能力选择调用。这种方式需要维护多个版本代码，但隔离风险最好。

## 四、向后兼容测试方法

### 4.1 单元测试级别：契约一致性测试

为每个工具版本编写测试，验证其输入/输出符合特定版本的契约。使用 `jsonschema` 或 `pydantic` 进行校验。

```python
def test_weather_v1_compatibility():
    # 使用 v1 契约的输入
    input_v1 = {"city": "Beijing"}
    output = tool_v2.run(input_v1)   # 调用新版本工具
    # 校验输出是否符合 v1 输出 schema
    validate(instance=output, schema=V1_OUTPUT_SCHEMA)
```

### 4.2 消费者驱动的契约测试（Consumer-Driven Contract）

使用 **Pact** 或 **Spring Cloud Contract** 框架。Agent 作为消费者，定义它期望的工具行为；工具作为提供者，验证自己的实现是否满足所有消费者的期望。

流程：
- Agent 编写 Pact 文件：描述给定输入应返回的输出（示例）。
- 工具侧运行 Pact 验证：使用真实工具实例，针对 Pact 中的每个请求检查响应是否匹配。

这样，当工具要发布新版本时，可以自动运行所有已有消费者的 Pact 测试，确保没有破坏旧契约。

### 4.3 兼容性测试套件

维护一组**黄金用例**，覆盖所有历史版本的典型调用场景。每次工具升级后，运行这些用例：
- 使用旧版契约的输入调用新工具。
- 检查输出是否符合旧版契约的预期（忽略新增字段）。
- 检查旧版中存在的字段值是否与之前一致。

可以自动化：将用例保存为 JSON 文件，脚本批量执行并对比。

### 4.4 OpenAPI 差异检测

使用 `oasdiff` 或 `swagger-diff` 等工具，比较两个版本的 OpenAPI 规范，自动检测不兼容变更（如删除路径、修改参数类型）。在 CI 流程中加入检查，阻止破坏性的 Major 变更被意外合并到 Minor 版本。

```bash
oasdiff diff base.yaml new.yaml --fail-on-incompatible
```

### 4.5 金丝雀测试与灰度发布

在生产环境中，先让一小部分流量（例如 1% 的 Agent 调用）使用新版本工具，同时监控错误率和输出格式异常。如果旧版 Agent 调用新版工具时出现大量解析错误，说明存在未发现的兼容性问题，立即回滚。

## 五、工程实践建议

| 阶段       | 措施                                                         |
| ---------- | ------------------------------------------------------------ |
| **设计**   | 字段默认可选；输出只增不减；使用语义化版本                   |
| **开发**   | 编写契约测试；使用 Pact 记录消费者期望                       |
| **CI**     | 自动运行兼容性测试套件；检测 OpenAPI 差异；阻止不兼容的 Minor 变更 |
| **发布**   | 先发布向后兼容的 Minor 版本；对于 Major 版本，提供适配器或多版本共存 |
| **运行时** | 工具网关可进行版本协商（Agent 声明版本，网关路由到对应适配器） |
| **监控**   | 记录工具版本号与调用成功率的关系；按版本聚合错误日志         |

## 六、示例：兼容性测试套件（简化）

```python
# compatibility_test.py
import json
from jsonschema import validate

OLD_CONTRACT = {
    "input_schema": {...},
    "output_schema": {...}
}

def test_compatibility():
    with open("test_cases.json") as f:
        cases = json.load(f)  # [{"input": {...}, "expected_output": {...}}]
    
    for case in cases:
        result = call_tool(case["input"])
        # 校验输出符合旧契约
        validate(result, OLD_CONTRACT["output_schema"])
        # 校验旧契约中关注的字段值一致
        for key, expected in case["expected_output"].items():
            assert result.get(key) == expected, f"Field {key} changed"
```

## 七、总结

解决工具调用的契约演化与向后兼容测试，核心是 **显式契约 + 自动化验证 + 多版本策略**：

- **契约显式化**：使用 OpenAPI/JSON Schema，并遵循兼容变更原则。
- **语义化版本**：严格区分 Major（不兼容）、Minor（兼容新增）、Patch。
- **自动化测试**：消费者驱动契约（Pact）、OpenAPI 差异检查、兼容性测试套件。
- **运行时隔离**：适配器或多版本共存，避免强制升级。

通过上述方法，可以在不中断现有 Agent 服务的前提下，安全地演进工具能力。建议在 CI 流水线中强制加入兼容性检查，将契约破坏扼杀在合并之前。
