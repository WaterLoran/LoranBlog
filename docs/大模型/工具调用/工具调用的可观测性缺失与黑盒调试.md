# 工具调用的可观测性缺失与黑盒调试

针对工具调用的可观测性缺失与黑盒调试问题，需要建立一套覆盖 **调用前、调用中、调用后** 的可观测性体系，让每一次工具调用都变得可追踪、可度量、可复现。以下是系统性的解决方案，围绕**结构化日志、分布式追踪、指标聚合、调试工具链**四个核心支柱展开。

---

## 一、结构化日志：让每个调用留下痕迹

传统的文本日志难以解析和关联。应强制采用结构化日志（JSON 格式），并为每次工具调用生成唯一的 **调用 ID**。

### 1.1 统一的日志字段

每条工具调用日志至少包含：

| 字段          | 示例                   | 说明                |
| ------------- | ---------------------- | ------------------- |
| `trace_id`    | `a1b2c3`               | 跨服务的全局追踪 ID |
| `span_id`     | `d4e5f6`               | 当前调用段 ID       |
| `tool_name`   | `get_weather`          | 工具名称            |
| `call_id`     | `uuid()`               | 单次调用唯一标识    |
| `session_id`  | `sess_123`             | Agent 会话 ID       |
| `user_id`     | `user_456`             | 发起用户            |
| `input_args`  | `{"city":"Beijing"}`   | 调用参数（需脱敏）  |
| `output`      | `{"temp":25}`          | 返回结果或错误信息  |
| `duration_ms` | `342`                  | 耗时（毫秒）        |
| `status`      | `success` / `failure`  | 调用结果            |
| `retry_count` | `1`                    | 重试次数            |
| `timestamp`   | `2025-04-11T10:00:00Z` | 时间戳              |

### 1.2 日志收集与聚合

- 将日志输出到标准输出，由采集器（Fluentd、Logstash）发送到集中存储（ELK、Loki、Splunk）。
- 在日志平台中建立以 `trace_id` 和 `call_id` 为索引的视图，支持快速检索和关联。

### 1.3 敏感信息脱敏

在记录日志前，对参数和输出中的敏感字段（密码、Token、身份证号）进行自动脱敏（如替换为 `***`）。可以使用正则匹配或基于 schema 的字段标记。

## 二、分布式追踪：还原完整调用链路

Agent 调用工具往往涉及多个服务（Agent → 工具网关 → 工具实现 → 外部 API）。分布式追踪可以串联起所有环节。

### 2.1 引入 OpenTelemetry（OTel）

OpenTelemetry 是业界标准，支持自动和手动埋点。

- **Agent 层**：在发起工具调用时，创建一个新的 Span，记录工具名称和输入参数。
- **工具执行层**：在工具内部，继续传递 Trace 上下文，创建子 Span 记录内部逻辑（如 HTTP 请求、数据库查询）。
- **网关/代理层**：如果使用工具网关，同样注入 Trace 信息。

### 2.2 关键埋点位置

| 层级         | 埋点内容         | 示例属性                          |
| ------------ | ---------------- | --------------------------------- |
| Agent 规划器 | 决策调用哪个工具 | `tool.name`, `decision.reason`    |
| 参数构造     | 参数生成过程     | `input.raw`, `input.normalized`   |
| 调用前       | 准备发起调用     | `retry.attempt`                   |
| 网络请求     | HTTP/gRPC 详情   | `http.url`, `http.status_code`    |
| 工具业务逻辑 | 内部处理步骤     | `db.query`, `cache.hit`           |
| 返回后       | 结果处理         | `output.size`, `output.truncated` |

### 2.3 使用 Jaeger 或 Tempo 作为后端

将 Trace 数据发送到 Jaeger、Tempo 或 Zipkin，通过 UI 查看火焰图，定位耗时瓶颈和错误发生点。

---

## 三、指标采集：量化工具调用健康度

除了单次调用的详细追踪，还需要聚合指标来发现趋势和异常。

### 3.1 核心指标（Prometheus 格式）

| 指标名称                     | 类型      | 说明                                       |
| ---------------------------- | --------- | ------------------------------------------ |
| `tool_call_total`            | Counter   | 调用总数，按 `tool_name`, `status` 分组    |
| `tool_call_duration_seconds` | Histogram | 调用耗时分布                               |
| `tool_call_retries_total`    | Counter   | 重试次数统计                               |
| `tool_call_error_total`      | Counter   | 错误类型计数（超时、参数错误、业务错误等） |
| `tool_call_inflight`         | Gauge     | 当前正在进行的调用数                       |

### 3.2 告警规则示例

- 某工具错误率 > 5% 持续 2 分钟 → 告警
- 某工具 P99 延迟 > 10 秒 → 告警
- 工具调用重试率 > 20% → 提示可能 API 不稳定

### 3.3 仪表盘（Grafana）

创建按工具、用户、会话维度聚合的仪表盘，实时监控工具调用情况，并支持下钻到日志和追踪。

## 四、调试工具链：让黑盒变白盒

生产环境的可观测性用于监控和事后分析，但开发调试时需要主动探测和复现。

### 4.1 录制与回放（Record & Replay）

- **录制**：在 Agent 执行过程中，将所有工具调用的输入参数、输出结果、中间状态序列化保存到本地文件或数据库。
- **回放**：离线加载录制文件，模拟 Agent 环境，重新执行工具调用（可 mock 外部依赖），观察行为差异。
- **用途**：复现生产 bug，测试工具升级的影响，对比不同版本 Agent 的决策。

### 4.2 模拟工具（Mock Server）

为每个工具提供一个可配置的模拟实现，能够：
- 根据输入返回预设响应
- 注入延迟、错误、超时
- 记录调用次数和参数

在开发或测试环境中，Agent 可以无缝切换使用模拟工具，避免依赖真实外部服务。

### 4.3 可视化调用链浏览器

开发一个简单的 Web UI，输入 `trace_id` 或 `session_id`，展示：
- 时间线视图：每个工具调用的开始、结束、耗时
- 参数和返回值（折叠/展开）
- 错误高亮
- 支持跳转到相关日志

### 4.4 远程调试端口

对于本地难以复现的问题，可以在生产环境的工具服务中开启调试端点（如 `/debug/pprof`），但需严格权限控制。更安全的做法是使用 **影子模式**：将生产流量复制一份到测试环境，同时执行并对比结果。

## 五、工程落地最佳实践

### 5.1 统一工具 SDK/客户端

所有工具调用通过一个统一的客户端 SDK 发起，该 SDK 内置了：
- 自动生成 `call_id` 和 `trace_id`
- 记录耗时和状态
- 上报日志、指标、追踪
- 自动脱敏

这样确保所有工具调用都具备一致的可观测性，无需每个工具单独实现。

### 5.2 关联 Agent 的思考过程

将 LLM 的“思考”（Thought）与工具调用关联起来。可以在日志中记录 `thought_id`，或者将 LLM 的输入提示也作为 span 的一个事件（event）附加。这样可以看到 LLM 是基于什么推理决定调用工具的。

### 5.3 成本可观测性

除了性能指标，还要记录每次工具调用消耗的 token 数（若涉及 LLM 二次处理）、API 费用等。将成本作为指标，用于优化调用策略。

### 5.4 错误分类与聚合

不要只记录错误字符串，而是定义错误类型枚举（`timeout`, `rate_limit`, `param_validation`, `business_error`, `internal_error`），便于聚合分析。错误堆栈应单独存储（如 Sentry）。

---

## 六、总结：建立三层可观测性模型

| 层次       | 目标           | 工具示例            | 解决的黑盒问题               |
| ---------- | -------------- | ------------------- | ---------------------------- |
| **日志**   | 记录详细信息   | ELK, Loki           | 查看具体某次调用的参数和结果 |
| **追踪**   | 还原调用链路   | Jaeger, Tempo       | 定位性能瓶颈和跨服务错误     |
| **指标**   | 聚合统计和告警 | Prometheus, Grafana | 发现趋势异常和系统健康度     |
| **调试链** | 主动复现和模拟 | 录制回放, Mock      | 开发调试、回归测试           |

通过以上组合，工具调用不再是黑盒：每次调用都有迹可循，每个错误都可被诊断，每个性能问题都可被量化。建议从**结构化日志 + 统一 SDK** 起步，逐步引入追踪和指标，最终建立完整的调试工具链。
