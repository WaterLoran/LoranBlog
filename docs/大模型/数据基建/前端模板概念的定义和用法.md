# 前端三种模板概念的定义和用法

它们共同描述了**页面长什么样、如何识别、以及可能发生哪些变化**。下面逐一详解，并用“实物订单详情页”贯穿举例。

---

## 1. 标题模板（Title Template）
**定义**：  
对页面文档标题（`<title>` 标签内容）的抽象描述，其中用 `{参数名}` 占位符表示动态部分。

**作用**：  
- 验证页面是否加载正确：实际标题与模板匹配，说明页面大概率属于该类型。
- 将 URL 规约中的参数名（如 `orderId`）与页面显示文本关联，便于后续数据绑定。

**示例**：  
URL 规约为 `/order/{orderId}`，页面类型的标题模板为：  
`"titleTemplate": "订单详情 - {orderId}"`  

当实际访问 `/order/982301` 时，预期标题应为 `"订单详情 - 982301"`。如果获得 `"订单详情 - 982301"` 则匹配成功；若获得 `"系统错误"`，则可能发生了异常。

**更多例子**：  
- 虚拟订单：`"虚拟订单 - {orderId}"`  
- 审批详情：`"审批详情 - {approvalId}"`  
- 任务面板：`"任务详情 - {missionId}"`

---

## 2. DOM 指纹模板（DOM Fingerprint Template）
**定义**：  
对页面关键区域 DOM 结构的抽象摘要，通常用“标签序列”或“选择器骨架”表示，忽略细节内容和样式。形式如：  
`main{section#order-info,section#status-bar,section#logistics,section#actions}`  

**作用**：  
- **快速识别页面类型**：无需完全渲染或解析所有文本，仅通过页面主要区块的选择器/标签结构就能判断当前页面属于哪种类型。
- **检测页面切换**：当指纹发生显著变化（超过差异度阈值）时，可认为页面发生了跳转或重大重构。
- **指导快照策略**：指纹中的区块可用于增量快照或哈希计算，只关注核心变化区域。

**如何生成**：  
通常是取主内容区域（如 `<main>`）下的一级语义区块（`<section>`、`<div role="...">`）的选择器或数据属性，按顺序组成字符串，并计算哈希。实际应用中会配合可见性、节点数量等做更精细的摘要。

**示例**：  
实物订单详情页的指纹模板：  
`main{section#order-info,section#status-bar,section#logistics,section#actions}`  
虚拟商品订单详情页的指纹模板：  
`main{section#order-info,section#virtual-product,section#actions}`  

对比可见，虚拟订单缺少 `#logistics`，多了 `#virtual-product`，二者结构不同，因此被判定为不同页面类型。

**更多例子**：  
- 差旅审批：`main{section#approval-info,section#travel-detail,section#budget,section#actions}`  
- 限时挑战：`main{section#mission-brief,section#countdown-timer,section#leaderboard,section#actions}`  

**关键点**：  
- 模板是**类型级别**的，不包含具体内容值。
- 实际匹配时，会将当前页面的指纹与模板比较，计算编辑距离或差异百分比。

## 3. 演变模板集（DomEvolution Templates）
**定义**：  
页面类型下所有可能发生的**行为序列模板**的集合。每个演变模板描述了一条典型的交互流程，由有序的变更节点（ChangeNode）组成，每个节点包含触发器（Trigger）和 DOM 变化描述（DomChange）。

**作用**：  
- 预定义该页面类型上用户和系统可能触发的所有状态变化路径。
- 作为自动化监控、回归测试、行为回放的基础：实际会话中触发的事件可以被映射到某个演变模板，判断是否偏离预期。
- 支持行为聚合分析：例如统计“确认收货流程”的成功率、平均耗时。

**结构**：  
演变模板集是一个数组，每项是一条独立的流程，例如：
- 确认收货流程
- 申请退货流程
- 轮询状态流程（定时器触发）

每条流程内包含多个**变更节点**，每个节点定义：
- **触发器**：什么导致了变化（用户动作/网络响应/定时器/滚动等）
- **DOM 变化**：变化前后的类型描述（文本类型变化、属性变化、结构变化等），不包含实际值。
- **可选快照模板**：是否在此节点记录 DOM 指纹快照（完整/增量/仅哈希）。

**示例——实物订单详情页的演变模板集**：

**模板 1：确认收货流程**
- 节点1：用户点击 `button[data-testid='confirm-receipt']`  
  → DOM 文本变化：`#order-status` 从 `文本类型A（待发货）` 变为 `文本类型B（已收货）`
- 节点2：网络响应 `POST /api/order/{orderId}/confirm` 成功（2xx）  
  → DOM 属性变化：按钮 `disabled` 从 `false` 变为 `true`  
  → 快照策略：增量快照，指纹更新为 `main{...section#status-bar.text=已收货}`

**模板 2：申请退货流程**
- 节点1：用户点击 `button[data-testid='request-refund']`  
  → DOM 结构变化：`#actions` 从 `元素类型：按钮组` 变为 `元素类型：退货表单`
- 节点2：用户在 `textarea[data-testid='refund-reason']` 输入文本（`inputValueType: text`）  
  → 无直接 DOM 变化（或仅记录输入属性变化）
- 节点3：网络响应 `POST /api/order/{orderId}/refund` 成功  
  → DOM 文本变化：`#order-status` 从 `文本类型A（待发货）` 变为 `文本类型C（退款中）`

**模板 3：定时轮询订单状态**
- 节点1：定时器 `polling`，间隔 `every 5s`  
  → DOM 无变化（`changeType: no_change`）  
  → 快照策略：仅哈希对比

**注意**：所有模板中的目标元素选择器、请求 URL 模式、值类型都使用了占位符（`{orderId}`）或抽象类型（`文本类型A`），不包含具体订单号或真实文本内容，完全符合“抽象描述”的要求。

## 三者如何协同工作
在“页面类型”中，这三个属性形成一个完整的识别与行为描述体系：

1. **标题模板**和**DOM 指纹模板**共同负责**静态识别**：  
   当一个新的 URL 被访问，系统首先提取实际标题和 DOM 指纹，与所有页面类型进行匹配，确定当前属于哪个 `typeId`。

2. **演变模板集**负责**动态行为描述**：  
   一旦确定了页面类型，系统就知道这个页面可能会发生哪些交互序列。当用户操作或网络事件发生时，实时事件会与模板中的节点进行比对，判断行为是否符合预期，并记录偏差。

**举例完整联动**：  
- 访问 `https://shop.com/order/123`  
- 实际标题 “订单详情 - 123” 匹配 `typeId=physical_order_detail` 的标题模板。  
- 实际 DOM 指纹 `main{section#order-info,section#status-bar,section#logistics,section#actions}` 与实物订单指纹模板完全一致。  
- 因此确定页面类型为 `physical_order_detail`。  
- 系统加载该类型下的三个演变模板（确认收货、申请退货、轮询）。  
- 当用户点击“确认收货”按钮，系统检测到该点击目标选择器与“确认收货流程”的节点1匹配，预期后续会发生节点2的网络请求。如果实际网络请求失败，则产生行为异常告警。

这就是三个模板概念的定义和用法，它们使我们对页面的抽象既保留了结构性，又具备表达复杂交互行为的能力。
